## Open questions the planners left

Each probe question is marked with what the round-4 probes and their independent check showed (2026-11-24;
`rewrite/spike/probes-round-4/CHECK.md`). Item numbers are those of the platform record,
`rewrite/spec/topics/platform-proven-2.md`. Everything was seen on Claude Code 2.1.331, macOS, with a plugin
loaded by `--plugin-dir`.

- (records (packages S2a, S2b, S4): record stores, run lock and caller identity, flush, decisions) Probe: item 27 showed allow-plus-rewrite only in the auto permission mode. If the VSDD_CALLER rewrite is not applied in the default mode, caller() returns None and every survey refuses to start; the first headless run (E2) will show which. **Answered, item 38:** yes. In the default mode, inside a workflow step, `allow` with the rewrite ran the rewritten Bash command (`CALLER=t42`) and a rewritten `StructuredOutput` reached the script, while the silent-hook control in the same session was refused. `caller()` gets its marker (PR4C-03).
- (records (packages S2a, S2b, S4): record stores, run lock and caller identity, flush, decisions) Probe: does the PreToolUse hook on StructuredOutput run before the platform's own schema check? This decides whether the same-agent replacement in store_step (D4) is ever needed, or whether a flat step_exists refusal would be safe. **Answered, item 40:** yes, the hook runs first, and the platform then checks the input as the hook left it. So a result the hook stored can still be refused by the platform, and the agent's corrected return arrives with the same `agent_id` (item 36): D4's same-agent replacement is needed and a flat `step_exists` refusal would wedge the agent. The store keeps its own schema check. Records builds both (PR4C-05).
- (records (packages S2a, S2b, S4): record stores, run lock and caller identity, flush, decisions) Probe: does a workflow survive /clear (SessionEnd with reason clear)? This decides whether H1 should call lock_release on that reason (finding P3OPS-20). **Still open, item 46:** round 4 sent SIGTERM to the session, which is a different event (after `/clear` the process lives on). It needs an interactive probe under tmux (B8; PR4C-15). hook-runner-b.md D3, release on every reason, stays the unproven choice.
- (records (packages S2a, S2b, S4): record stores, run lock and caller identity, flush, decisions) Person: the offer to replace the lock heartbeat with liveness by process (blueprint 11.2) is still open. Item 29 is proven for one case only (macOS, no sandbox, from a Bash call), so the heartbeat is built.
- (S3 first part: survey, checkpoint and story admission for one story) Probe needed: rewrite/spec/packaging/sandbox-needs.md lists write access to .factory/ and .worktrees/ only, but creating a story branch and worktree (and flush) writes under .git/ (refs, .git/worktrees/). Whether a sandboxed Bash call inside a workflow step allows that has not been tested; if it does not, vsdd survey cannot admit a story with the sandbox on. **Answered, item 41:** it does not. With the sandbox on every write under `.git/worktrees/` is refused with `Operation not permitted`: `git worktree add` (which has by then created its branch), and `git add` and `git commit` in an existing linked worktree and in `.factory`. Ref writes and main-checkout commits work. No allowance was shown to work, so a factory run needs the sandbox off for now (`rewrite/spec/platform.md`, "Headless runs"). What the units do is `ORDER.md` rule 11: the survey's worktree library names the sandbox and reuses the branch a refused call left (survey.md D20; PR4C-07), and a flush from a sandboxed call ends `failed` with a cause that names the sandbox (records; PR4C-08).
