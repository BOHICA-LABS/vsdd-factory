# Step 3 plan: hook runner, second part: path classes and lock liveness (H1)

Paths are under `next/`. `P` is `plugins/vsdd-factory`. Spec files are under `rewrite/spec/`. This plan
continues `hook-runner.md`, the first part, which is built and reported before it. Names it does not
define (`Ctx`, `registry`, `EVENTS`, the HD decisions) are that plan's.

## 1. Scope

Two things the first part could not build, because they rest on units built after it:

- `ctx.classes` and `classes_of`, the path classes of a call's target. They need S1's `path_class` and
  `glob_regex`. Step 4's `tests-first` (H5) and `step-results` (H7) read them.
- Lock liveness. The runner refreshes the run lock on calls that belong to a locked run and releases a
  session's lock when the session ends. They need records' `lock_seen` and `lock_release`. Without them
  every lock of the slice goes stale 20 minutes into a run, a second session's survey can then take the
  lock over and end the run, and a session that ended leaves a lock that blocks a re-run for 20 minutes.

Left for when the build widens: everything `hook-runner.md` lists; of `lifecycle-log` (H9) the agent
records, the pruning of event files and stopping an agent's products; the `clear` question of D3; the
refresh on calls that no rule or duty wires yet (D2).

## 3. Interfaces this unit provides

### 3.1 Path classes

- `ctx.classes -> tuple[str, ...]`: `ctx.classes_of(target)`; `()` without a target.
- `ctx.classes_of(path, where=None) -> tuple[str, ...]`, the same function as `paths.classes_of`:
  - In the state directory: the matching classes of `classes.toml`, innermost first (a contained class
    before its container, so `brief` before `spec-product`). Each glob is compiled with S1's
    `vsdd.globs.glob_regex` and matched against the path relative to the project root.
  - Elsewhere: S1's `vsdd.project.path_class(path, root=ctx.project.root, config=ctx.project.config)`, or
    `unclassified` when it answers `None`.
  - Then the computed classes of `classes.toml`'s closing comment: `project`, `own-worktree` (by `where`,
    which defaults to the payload `cwd`), `tmp`, `outside`.
- A policy table that does not load raises `PolicyInvalid`: `policy_invalid` for the rule that read the
  field (hook-runner.md 3.4). This unit writes no second precedence list and no second glob matcher.

### 3.2 Lock liveness (the seam with records)

Two core duties, wired with no rule as the marker is (HD2). `liveness.py` imports `vsdd.state.locks`
directly, not the `vsdd.state` facade.

- `liveness.refresh(ctx) -> bool`. `main.run` calls it once on every `PreToolUse` call, after the rules
  and whatever they decided. It calls
  `lock_seen(ctx.project, session_id=<id>, agent_id=<id>, run=<run>, story=ctx.story or "")`: the ids are
  the payload's, `""` when absent; `<run>` is the value after `--run` (or in `--run=<id>`) of a segment
  whose program is `vsdd`, or `tool_input.step.run` of a `StructuredOutput` call, else `""`. Records
  decides whether the call belongs to a lock; the runner only passes facts.
- `liveness.release(ctx) -> list[dict]`. `main.run` calls it on `SessionEnd`, which is wired in `notify`
  mode. It calls `lock_release(ctx.project, session=<session_id>, wait=0.5)`, whatever the payload's
  `reason`, and logs each released entry as `lock.released` with its `run` and the reason.

Neither blocks a call or changes its output. An exception from either, an import error included, is
caught, logged as `runner.liveness_error` with severity `error`, and the call goes on.

### 3.3 Wiring after this unit

`hooks.json` wires `SessionStart` (as before), `PreToolUse` with the matcher `Bash|StructuredOutput`
(the `gate` guard, timeout 10, `onFailure: "block"`) and `SessionEnd` (no matcher, the `notify` guard, no
`timeout` key: HD4).

## 5. Design decisions

- D1. Liveness is a core duty, not a rule. As a rule it would arrive with H9, after every workflow of the
  slice (P3BLD-14).
- D2. The duty names two atoms, `Bash` and `StructuredOutput`: a `vsdd` call that carries `--run`, and a
  step's result. `refresh` runs on every `PreToolUse` call the runner handles, so each atom a later rule
  wires (`Edit`, `Read`) refreshes too, through `ctx.story`. Until then an agent that only reads refreshes
  when it returns its result. Wiring `Read` now would put a launch on every read for this duty alone.
- D3. `SessionEnd` releases whatever the reason, as `topics/run-lock.md` says. Whether a workflow survives
  `/clear` is unproven (P3OPS-20), still so after round 4, which tested SIGTERM and not `clear` (platform
  item 46). If one does, its run is ended and its next gate refuses `run_not_live`,
  out loud. Keeping the lock on `clear` would instead block the common case, a re-run after `/clear`, for
  20 minutes.
- D4. `wait=0.5` keeps the release inside HD4's 1 s `SessionEnd` deadline, itself inside the platform's
  1.5 s. A release that times out is logged; the lock then goes stale by time.
- D5. Liveness never blocks. It is not a gate, and a fault in a lock file must not wedge every tool call
  of a session. It is not silent either: the error event, and a test that imports the real `locks`
  module, so a renamed function fails the build.
- D6. An empty `agent_id` (the main session) is passed as it is: records returns false for it, so a run
  that stopped inside a session that stays open goes stale like any other.
