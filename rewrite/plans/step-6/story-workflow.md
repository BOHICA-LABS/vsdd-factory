## 3. Interfaces this unit provides

### 3.1 Starting a run (the interface first-run.md builds on)

- **A person**, in a session that loaded the plugin, types `/vsdd-factory:story <story-id>` in the
  project. **A headless driver** gives that text as the whole prompt of `claude -p`, in the project
  root. No skill or command file is built: the platform makes the typed command from the workflow
  file (item 31).
- **The main session** then makes one tool call: `Workflow` with `name: "vsdd-factory:story"` and
  `args: "<story-id>"` (an object `{story: "<id>"}` works too). The script runs in the background and
  its return value (3.3) reaches the main session as a notification.
- **What the session must have**, set by first-run.md 3.5 and shown by probe (items 50 to 52): the
  `Workflow` tool allowed (item 30; `Skill` is not needed); the steps' Bash, Read,
  Edit and Write calls allowed by the session's own settings, because `auto-allow` (H6) is not on the
  slice and the hook runner approves only an agent's single `vsdd` call; the Bash sandbox off (item
  41); `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0` (item 47); a block read by `num_turns == 0`, not
  `is_error` (item 46).
- **Proof that the shipped script ran** (item 49) is the driver's check `named_workflow_ran`
  (first-run.md 3.6), on the platform's run record: each session has exactly one run record, and its
  `script` and the file at its `scriptPath` equal `P/workflows/story.js` byte for byte. This unit
  guarantees that file: a build product, `tools/build.py --check` clean. No hook on `Workflow` is
  built: the wired matcher never names the tool, and the `PostToolUse` input of a named call carries
  `script` too.

### 3.2 Arguments

`parseArgs(args, 'story', ['repo'])`. `story` is required and must pass `safe()`; `repo` goes to the
survey. A parent also passes `position`, `run_id`, `project_dir`, `plugin_root`, `tier` and `limits`,
as `runStories()` sends them; the script then runs no survey and no checkpoint (the child form).

### 3.3 Result

One object: `workflow: "story"`, `subject`, `status`, `summary` (at most 600 characters), `agents`,
`spikes`, `counts: {agents, spikes}`, `passes`, `advisory`, `deferred`, `pr`, `merged_sha`, and `verdicts`:
one entry per review loop this run ended, in order, `{loop, outcome, reason, passes, rounds_used,
head, coverage_missing}` from `converge()`'s verdict (D19). Standalone it also has `progress`,
`decisions` and `next`, and these and `status` are the checkpoint's (D1). As a child, `status` is the
script's own word: `done`, `needs_human`, `blocked` or `failed`.

Ends before any stage:

| Case | Result | Clerk steps |
|---|---|---|
| No valid story id | `failed`, "No valid story id was given." | 0 |
| The survey answers `ok: false`, or an unmet precondition, with no `run_id` | `blocked`; `summary` is its `error`, else the unmet rows; `next` is the survey's | 1 |
| The survey prints nothing or refuses on usage (`workflow` empty) | asked once more (D3), then the row above | 2 |
| The survey answers `ok: false` with a `run_id` (a defence, D4) | closed with `--outcome failed` | 2 |

### 3.5 The paths

`end(word, summary)` is the one way out once a run id is known: standalone it runs the close and
returns 3.3; as a child it returns at once. Paths 1 to 4, 7 and 9 are the skeleton's.

1. **Fresh story.** Survey; `tests`; `implement`; loop 1 (`review(1, u.base, '', limits.passes, u.acs,
   u.rounds_used)`); `evidence` if `demo`; `deliver-1` answers `merged`; `end('done')`.
2. **Start at a position.** `red`: from implement. `green`: from review, with the unit's `diff_patch`,
   `test_output` and `rounds_used`. `reviewed`: from evidence. `evidenced`: deliver. `delivered`: only
   `end('done')`. `u.dirty` reaches the first builder step.
3. **A gate fails.** `gated()` retries once with the gate's `failures` (`tests-retry1`,
   `implement-retry1`); a second failure is `blocked`, kind `gate`, and `end('blocked')`.
4. **A wrong frozen test**, when `u.red_gate`: `test-defects`, then `implement-2`, once.
5. **A finding, the fix, convergence.** `fix` asks the test-writer first for the findings it owns, then
   `fixer` for the rest, and `fixer` also when the test-writer's result holds no passing `green` entry.
   Each fix moves `head`, patch and test output (D8).
6. **No convergence.** At the cap `arbitrate-l1`, one more fix and pass; still open: `blocked`, `cap`.
   `spec_gap` and `reviewer_blocked` end `blocked` too; `no_result` (a lens with no result, or one
   whose `reviewed_sha` is not `head`) ends `failed`.
7. **A dispute.** A `disputed` resolution reaches the arbiter with its note; `not_defect` dismisses the
   finding. No reviewer prompt holds a fixer's note or summary.
8. **A repair that touches a frozen test.** `repair-1`'s green gate fails on it, twice:
   `end('blocked')`, no review, no second delivery (PL4-19).
9. **Demo.** Only with `u.demo_required` does a demo-recorder run; else delivery builds the table.
10. **Delivery.** `ok: false` (`refused`, `checkout_dirty`, no state): no repair, `end('blocked',
    d.error)`; with `needs_person` the error names the kind. `ci_failed`, `conflict`: `repair-<r>`, then
    `review(r + 1, sha, sha, 2, <the repair's changed_files>, 0)`, evidence again for a `demo` story,
    `deliver-<r+1>`. `review_stale`: no repair; items and patch are the delivery data's (D17). After
    `limits.delivery_rounds` rounds: `end('blocked')`. `awaiting_merge`: `end('needs_human')`.
11. **A step returns `blocked`.** `end('blocked', its summary)`, no `--outcome failed`. A reviewer:
    `reviewer_blocked`. A fixer: D10. A spike request: `blocked`, `spike_limit` from `step()` (D18).
12. **No JSON, or moved to the background.** The clerk follows D11's text. Survey: 3.3. Deliver: path
    10; the next run re-attaches. Close: asked once more, then `status: "failed"` and a summary saying
    the lock may still be held.
13. **A result the `step-results` rule blocks.** The agent returns again; the script sees only the stored
    result, and a finding marked `grounded: false` is advisory. A dead agent (`null`, retried once) or
    a throw (caught) ends `failed`, with `--outcome failed`.

## 5. Design decisions

- D1. **Standalone, the status is the checkpoint's** (`topics/workflow-shape.md`); the skeleton returned
  its own. A script `blocked` with no decision open would have a driver wait for nobody: survey-2.md
  3.2 calls that `partial`. The script's word shapes `summary` and D2 only. No answer is `failed`.
- D2. `--outcome failed` is sent exactly when the script's word is `failed`: no usable result, a
  review with none, an exception (universal test 7b).
- D3. **The two ends of the lock are asked twice.** A survey with `workflow` empty, or a close with
  `ok: false` and no `status`, printed nothing and is asked once more: a lost answer there strands
  the lock. Delivery is not repeated: the next run re-attaches to its job.
- D4. An `ok: false` survey with a `run_id` is not expected: as built (`survey.py`, lines 142 to 164;
  survey-2.md 3.1) a failure after `run_begin` releases the lock and empties `run_id`. The branch
  stays as a defence, with its test. Left over is a release that itself failed ("the lock release left
  a fault"): the lock is held with no `run_id`, and the script cannot close it. The next survey takes
  the run over once the lock is stale; the driver releases it (first-run.md 3.4, refusal 7).
  `ok: true` with no unit ends `failed` inside `try` (P3BLD-17).
- D5. Everything after `RUN.id` is set, `applyLimits` included, is inside `try`; `catch` calls
  `end('failed', ...)` with the error's text. Inside `try`, `end()` is returned, never awaited, so a
  close that throws is not run twice. A `position` outside the six throws.
- D6. **The fixer and the repairer are `u.impl_agent` with `fix-findings`** (S5P-N10). The test-writer
  fixes the findings whose `owner` it is only when `u.red_gate`; for a kind without one every finding
  goes to `fixer`, because its re-freeze fails (gates.md D16), and the review task names `fixer` as the
  owner of every category. One literal method, no kind table (L2-c2-1). ORDER-6 asks step 5 for both.
- D7. `coverage_missing` is the items the adversary's `coverage` does not mark `checked` or
  `not_checkable` (S5P-N9), the test of verdicts.md rule 7.
- D8. **A later loop stays on its range.** Its items are the `changed_files` of `repair-<r>`'s `--since`
  result (VSA-03). The schema leaves that field optional, so a passing entry without the array is no
  usable result: the run ends `failed`, naming the field (an empty list would converge on nothing
  while the tool names files). Its fixes close with `gate green --since <from>` and the test-writer's
  green command carries `--since <from>`, so a second pass still reads the range patch. `test_output`
  is replaced wherever the patch is (P3BLD-16), both only from a `green` entry that `passed` with
  `sha` equal to the step's `head`.
- D9. **Evidence is recorded again after a repair** for a `demo` story (`evidence-<r+1>`). ORDER-4
  section 7 says the script does not; ORDER-6 asks for that sentence to be struck: by gates.md D14's
  file check the old recording would pass at the new head.
- D10. A fixer that returns `blocked` ends the run `blocked` with its summary, which `fix` keeps:
  `converge()` says only `failed`, `no_result`, and `--outcome failed` would then cover a decision
  the checkpoint opens.
- D11. **`relay()`'s text** (probes-4-apply-C2-1, C2-3). Its last sentence becomes: "If a call that
  finished printed no JSON, return `<the empty object>` with "error" set to what it printed. If a `vsdd
  story deliver` call is moved to the background, run the same command again: it re-attaches to its
  job. A moved call of any other command: wait for it, as the notice says." Survey and checkpoint are
  not jobs (item 43). The clerk file holds the last two sentences word for word (ORDER-6).
  `return {...} with "error" set` stays: a universal test matches it.
- D12. `u.guidance` goes into `where`, so every non-clerk step reads it (P3OPS-09); `used` is
  `u.rounds_used` for loop 1 and 0 later.
- D13. Standalone, the run's agent limit is the smaller of `agents` and `story_agents`.
- D14. The checkpoint is called without `--subject` (P3BLD-18, PL3-22).
- D15 to D17. Known limits, each loud, each listed in ORDER-6. D15: the result carries `agents`
  and `spikes` for `runStories()` beside the schema's `counts`. D16: a full review with
  `u.rounds_used` at the cap is `blocked`, `cap` with no pass, until `direct` grants one. D17:
  `review_stale` is reviewed at the script's own `head`, because delivery data names none; a head
  moved by anything but a step of the script is never covered, and the run ends `blocked` after
  `limits.delivery_rounds`. No step on the slice moves it.
- D18. **No spike on the slice.** After `applyLimits` the script sets `RUN.limits.spikes_per_run = 0`,
  with a comment naming A3, S6 and H8: a `needs_spike` result then ends `blocked`, `spike_limit` in
  `step()` and never reaches `runSpike()`, whose agent type has no file (agents.md D20; what `agent()`
  does then is unproven). A fixture cannot do it: `config.py` refuses 0 for `spikes.per_run`. The line
  and its test go with those packages.
- D19. **The result names each loop's verdict** (`verdicts`). Delivery merges on the verdict G3
  rebuilds from the stored records, so the script and the tool meet only there; what the script acted
  on can now be compared with that rebuild, in the cross test and in a real run.
- D20. **The `survey` step runs at the clerk tier under any override**: the override is its answer.
  `contract` and first-run.md's `tier_applied` exempt that one call and no other.

## 7. Tests

`story_scenario.mjs` exports `unit`, `finding`, `gateEntry`, `contract(run, unit)`, `SCENARIOS` and
`runStory({unit, args, limits, config, deliveries, steps, close})`, which runs `P/workflows/story.js`
with stubs. The clerk answers by the command in its prompt. A step answers from its identity line, by
default `done` with a new head and a passing entry of its closing gate, shaped as the gate prints
it: `green` with `diff_patch` and `test_output`, and after `--since` with `changed_files` (the
scenario's files) and the range patch; `steps[<name>]` overrides one.
`node tests/workflows/story_scenario.mjs dump <name>` runs `SCENARIOS[<name>]` and prints `{subject,
cap, waived, acs, changed: {"<since>..<head>": [path]}, calls: [{agent_type, result}], verdicts}`.
`contract` runs on every scenario and fails a call that: has no `vsdd-factory:` agent type; matches no
row of 3.4 by name, agent and method; differs in `model` or `effort` from its agent's roster tier, or
from the override (the `survey` call excepted: D20); lacks `agents/<agent>.md`, `methods/<method>.md`,
the method in the agent's list, a `data` key in the method's `## Result` or the gate in its `## Finish`;
or, a clerk's, lacks D11's text. Tests:

- Paths 1, 2: `a fresh feature story runs six steps in order`; `each position starts at its stage`;
  `a delivered story only closes`; `dirty work is announced`.
- Paths 3, 4: `a failing red gate is retried with its failures`; `two failing red gates end the run`;
  `a failing green gate is retried`; `a wrong frozen test goes to the test-writer and back`.
- Paths 5 to 7: `a finding is fixed and the next pass converges`; `the second pass reads the new log`;
  `a test finding goes to the test-writer first, then the builder`; `a review at the cap ends blocked`;
  `a disputed finding is arbitrated and dismissed`; `no reviewer reads a fixer's note`;
  `a security checked does not cover an adversary skipped`; `a blocked reviewer ends blocked`;
  `a reviewer on another commit ends failed`; `a blocked fixer ends blocked, not failed`;
  `guidance reaches every step`; `paths reach the steps`.
- Paths 8 to 10: `a repair that touches a frozen test ends the run`; `a conflict is repaired, reviewed
  and delivered`; `a repair that adds a file`;
  `a later loop fixes close with --since` (the closing, and the test-writer's green command);
  `a repair result without changed_files ends failed`; `a stale review runs a scoped loop`;
  `a demo story records evidence, and again after a repair`; `a story without demo starts no recorder`;
  `delivery refused ends the run`; `delivery refused for a person names the kind`;
  `delivery rounds are bounded`; `awaiting merge ends needs_human`.
- Paths 11 to 13: `a blocked step ends the run through the checkpoint`; `survey prints nothing`;
  `a refused survey starts nothing`; `a failed survey that opened a run closes it`;
  `deliver prints nothing`; `close prints nothing once`; `close never answers`;
  `every clerk prompt carries the relay text`; `an ungrounded finding does not block`;
