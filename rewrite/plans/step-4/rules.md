# Step 4 plan: delivery-order rules and step-result rules (H5, H7)

Paths are under `next/` unless they start with `rewrite/`. `P` is `plugins/vsdd-factory`. Spec files are
under `rewrite/spec/`; step 3 plans under `rewrite/plans/step-3/` are cited by file name. `ORDER.md` is
this directory's.

## 1. Scope

Three rules, each one module with `check` and one row in the hook registry (hook-runner.md 3.2):
`tests-first` and `merge-guard` (H5) and `step-results` (H7), to spec `rules/<id>.md`. With their rows
`hooks.json` wires the four edit tools. Two helpers come with them: the paths a shell segment writes,
and the grounding check, the only one in the product (PL4-1). Depth is what one story on the sample project
in local mode exercises: source and frozen tests in a story worktree, git around the integration branch,
and every step result of `story.js` stored with its agent type, its passing gate entries checked against
evidence and its review findings grounded.

Left for when the build widens:

- Walled findings beyond a loud refusal (3.4): the evaluation file and walled keys (H7). Spike-runner
  results (`spike-bounds`, H8).
- The `decisions` rule with its `UserPromptExpansion` wiring (H7; PL4-18): it cannot fire before K1
  ships the `decide` skill and is built with it. Until then a person settles with `vsdd decide` in a
  terminal (records).
- `hooks/records.py`, `hooks/edits.py` (D1); `vsdd explain` (H9); recorded payloads (E2).
- What H2, H3 and H6 enforce: at slice depth an implementer is kept from frozen tests, not from every
  test, and git inside a story worktree is unrestricted, though the step 5 agent files say "(enforced)".
- `tests-first`: `@method` grants (H3). `merge-guard`: hotfix branches, hub repositories.

### 3.2 `tests-first` (spec `rules/tests-first.md`)

Block codes: `no_red_evidence`, `red_already_recorded`, `red_test_frozen`. What the spec leaves open:

- Paths checked: `ctx.target` for a file tool; for `Bash`, `write_targets(seg)` of every segment.
- For each path, stopping at the first "no": its story (`ctx.story_at` of its directory); its class
  (`ctx.classes_of(path)` holds `source` or `tests`); the kind has a red gate (D4); then the red record,
  `vsdd.state.gate_evidence.evidence(ctx.project, "red", story)`.
- `source`: a row whose `write` holds `source:before-red` is blocked when a record exists; every other
  caller is blocked when none exists (D2).
- `tests`: blocked when a record exists, the path relative to its worktree root (POSIX; literal or
  resolved) equals a `frozen[].file`, and the row's `write` lacks `tests:frozen`.
- The fix names `vsdd gate red --story <id>`; for a frozen test, returning `blocked` with
  `data.test_defects`.

### 3.3 `merge-guard` (spec `rules/merge-guard.md`)

`GOVERNED = ("story deliver", "release")` is a constant of `merge_guard.py` until H6 moves it (D8). The
guarded branches are `branches.integration` and `branches.release` of the segment's project. Codes:

| Code | Blocks |
|---|---|
| `direct_merge` | `gh pr merge` |
| `integrate_on_guarded` | `git merge`, `rebase`, `cherry-pick`, `revert`, `am` while a guarded branch is checked out in `seg.where`; `git rebase <upstream> <guarded>` |
| `commit_on_guarded` | `git commit` there; `git reset` with a mode flag, or a revision other than `HEAD` before any `--` |
| `push_to_guarded` | `git push` with a guarded destination (`b`, `src:b`, `+src:b`, `:b`, `refs/heads/b`; `HEAD` when on one), with `--all` or `--mirror`, or with no refspec from a guarded branch |
| `moves_guarded_branch` | `update-ref` or `symbolic-ref` naming one; `branch` with `-f -m -M -c -C -d -D` (or the long forms) naming one, or renaming the current one; `switch -C`, `checkout -B` naming one; a `fetch` or `pull` refspec with that destination |
| `where_unknown` | any verb above in a segment whose `where` is `""` |
| `opaque_git` | an opaque segment whose own program is not `git` and whose text holds `gh pr merge`, or `git` then one of those verbs (`branch`, `switch`, `checkout` only with the flags above) |

A segment is judged only when `vsdd.project.find_project_root(seg.where)` finds a project (D7); the
branch names come from `ctx.project_at(seg.where).config`. Git's global options (`-C`, `-c`, `--git-dir`,
`--work-tree`, `--no-pager`) are skipped to find the verb. The fix names the `GOVERNED` commands, and
`/vsdd-factory:feature` when `ctx.row.name` is `main`.

### 3.4 `step-results` (spec `rules/step-results.md`)

Codes: `gate_result_mismatch`, `findings_ungrounded`, `tree_unknown`, `walled_not_built`, the store's
refusals as they are (`run_not_live`, `bad_identity`, `schema_invalid`, `over_cap`, `step_exists`), and
`step_store_failed` for any other `StoreError`. In order:

1. No identity (`tool_input.step` is not an object with a non-empty string `run`): nothing (D10).
2. Walled: a result whose `ctx.agent_type` is `vsdd-factory:scenario-reviewer` and holds findings, or a
   finding located under `.factory/holdout/`, blocks `walled_not_built`, every time.
3. Gates: each entry of `gates` with `passed: true` needs
   `gate_evidence.evidence_read(project, entry.subject, entry.gate, entry.sha)` to return a record whose
   `gate`, `subject`, full `sha` and `passed` equal the entry's; else `gate_result_mismatch`, every time.
   A malformed entry and a `StoreError` are a mismatch. The entry's `evidence` path is never opened.
4. Grounding: every object in `data.findings`, with `ground(finding, tree=<tree>,
   project_root=ctx.project.root)` (3.5), which exempts category `holdout` and an empty path. The tree
   is `vsdd.state.worktrees.unit_tree(project, step.workflow, step.subject)`; if that raises and a
   finding has a path to ground, `tree_unknown`.
5. A finding fails and the step has no marker (D12): the marker is written, `step.rejected` logged and
   the call blocked `findings_ungrounded`, one line per finding (`finding <key>: <reason>`). The blocks
   of 2 to 5 are returned together, and nothing is stored.
6. With no block, store. The stored result is the input with every agent-supplied `grounded` key removed and
   `grounded: false` set on each failing finding. The call is
   `steps.store_step(project, result, ctx.agent_type, head, agent_id=ctx.agent_id)`, `head` being
   `gitfs.head_sha(tree)` or `""`. A refusal blocks, stores nothing and is logged as `step.rejected`
   with its code. On success the marker is removed, `step.recorded` is logged with the identity, and
   when the stored result differs from the input the rule returns `Rewrite(<the stored result>, reason)`.

Promises to G3 and the second part of S3, who read the records:

- `agent_type` is the payload's, unchanged: `<plugin>:<agent>` for a typed step, `workflow-subagent` for
  an untyped one, `""` for the main session, whose payload has no such key (platform item 36; PL4-22).
- A stored finding is grounded unless it carries `grounded: false`; no other value of the key is
  stored, and the tool does not ground again (VSA-07).
- A stored gate entry with `passed: true` matched its evidence record when it was stored. A result
  with no identity, or one the rule blocked, is not on disk.

### 3.5 Helpers

```python
# vsdd/hooks/writes.py
def write_targets(seg: Segment) -> tuple[str, ...]
# vsdd/grounding.py      (module level imports pathlib only; nothing from vsdd.hooks or vsdd.state)
def ground(finding: object, *, tree: Path, project_root: Path) -> str   # "" when grounded or exempt, else why
```

`write_targets` returns absolute paths and never raises: every redirect that writes (not `<`, not
`/dev/null`, not `&N`); the non-option arguments of `tee`, `rm`, `touch`, `truncate`; the files of `sed`
with `-i` or `--in-place` and of `perl` with `-i`; the destination of `cp`, `mv` and `ln` (inside an
existing directory, or with `-t`, the source's base name there) and the sources of `mv`; `dd`'s `of=`.
Relative paths resolve against `seg.where`. An argument with `*`, `?` or `[` is expanded with `glob`,
200 paths at most. One holding `$` or a backtick, or a relative one with an unknown `where`, is left out.

`ground` never raises, whatever the finding's shape. Exempt, returning `""`:
category `holdout`, and an empty or missing `location.path`, which `judge()` already holds advisory. A
path whose first segment is `.factory` is taken from `project_root` (`finding.schema.json`), any other
from `tree`. Reasons:
`path is outside the reviewed tree: <path>` (absolute, or outside its root once resolved);
`file not found: <path>`; `lines <a>-<b> are outside <path> (<n> lines)` (1-based,
`1 <= line_start <= line_end <= n`; one bound given stands for both); `quote not found in <path>`
(whitespace runs made one space; sought in the range widened by three lines each way, or in the whole
file with no line given; the file is read as UTF-8 with replacement).

## 5. Design decisions

- D1. No `hooks/records.py`: rules import `vsdd.state.<module>` themselves (step 3's `ORDER.md`,
  section 7).
- D2. Only a `source:before-red` row is held to "before red"; every other caller is held to "after
  red". Whether it may write source at all is H3's.
- D3. A shell write belongs to the story whose worktree holds the path written, not the segment's
  directory.
- D4. A kind that cannot be read counts as having a red gate, and the reason says so: the red gate
  then names the fault, where a crash would only say `rule_error`.
- D5. A shell target that cannot be resolved passes, as the spec says: the green gate needs a red record
  and unchanged frozen files. Globs are expanded so `sed -i … src/*.py` is still caught.
- D6. `revert` and `am` join the verbs blocked on a guarded branch: each adds a commit. A bare
  `git pull` there passes: the spec lists refspecs only.
- D7. A segment in no factory project is not judged, so a commit on `main` of an unrelated repository
  passes. An unknown directory, or a guarded verb the parser cannot see into, blocks: the actions are
  irreversible and the fix is a plain `cd <dir> && git …`.
- D8. `GOVERNED` lives in the rule module: `model.py` is step 3's file.
- D9. A rule's blocking case needs `[paths]`, a story worktree, a checked-out branch or records, and
  the hook runner's case runner builds a bare `factory.toml`. So this unit runs its own tables and its
  own per-row coverage test: a gate rule with no
  blocking case through the real launcher is not proven.
- D10. "No step identity" is the spec's test, unchanged: a result with no `step.run` passes unstored,
  and an unstored result counts for nothing in the tool's verdict or at delivery.
- D11. The evidence record is found by subject, gate and commit, never by the entry's path (VSA-11).
- D12. "Once per step" is a marker file, `<hooks_dir>/steps/<32 hex of sha256("run/workflow/subject/name.attempt")>`,
  written before the block and removed at the store. The event log cannot carry it: its writes may be
  dropped. A stale marker is H9's to prune.
- D13. The rule's mark is the one grounding decision: an agent's own `grounded` key is removed, and a
  `Rewrite` is returned whenever the stored result differs, so the script judges what was stored.
- D14. An invalid result is blocked every time and never stored (P3OPS-21 says once): a stored invalid
  record could be counted as done. The platform's retry limit bounds the loop.
- D15. Walled findings refuse out loud, the scenario-reviewer's too: no walled text is stored before
  the wall exists.
- D16. An agent reads a block inside the platform's wrapper (platform item 40), never as the first
  characters it sees: a reason or fix stands alone, naming its finding, gate or path.
