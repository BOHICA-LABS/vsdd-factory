## D33-31 (minor; decision D33, design; left-for-builder)

Earlier outcome: Package M1 adds the field to the job specification and sets it for the sync, with G1's owner, when the build widens. Nothing built today is a sync, so the job layer as built is right for every command that uses it.

Files: commands/sync.md, rules/decisions.md, topics/long-commands.md

Where it was found: next/plugins/vsdd-factory/py/vsdd/gates/jobs.py (attach, _serves); rewrite/spec/topics/long-commands.md (Team use); rewrite/spec/commands/sync.md

The job layer serves a finished result that nobody collected to the next call with the same key (_serves: not collected, or the caller's own nonce). That is right for a gate, whose result belongs to a commit. vsdd sync is keyed by the command and the state branch with no commit, so a sync that the decisions rule started detached, or one whose caller did not come back after a pending answer, would hand its old outcome to a later vsdd sync, and no sync would run.

Proposed resolution: Package M1 adds one field to the job specification, with G1's owner: the worker marks its own result as collected when it writes it. A call that started the job, or attached while it ran, is still given the result through its nonce; any later call starts a new sync. Only the sync sets the field, so no gate or delivery changes. The sync the decisions rule starts is a job of its own, keyed by the command and settle:<decision id>, which also names the one record its flush may commit. Test: a commit pushed to the remote after a detached sync has ended is in the mount after the next vsdd sync; a settlement typed while a vsdd sync job runs is published by its own job.

## PR4-2 (minor; platform probes, round 4; left-for-builder)

Earlier outcome: G1: the job record, not the tool's timeout, is what reaps a job. E2: its eleven-minute gate must measure that a call moved to the background is followed by a re-run of the same command, which re-attaches.

Files: packaging/e2e-story-tier.md, topics/long-commands.md

Where it was found: rewrite/spec/topics/long-commands.md; the G1 open probe in rewrite/plans/step-3/RESOLUTIONS.md; items 43 and 6 of the platform record; rewrite/plans/step-5/agents.md M3 and the clerk

The design worded the Bash timeout as a kill ('the tool stops a foreground command', 'a call killed by a timeout'). Observed on Claude Code 2.1.331, macOS, default mode, sandbox off and on: a foreground call past its Bash timeout is not killed at the timeout. It is moved to the background (timedOutAfterMs, a backgroundTaskId, backgroundEndsWithFinalResponse true), and it is killed when the step agent gives its final response (its task output reads '[killed]'). The platform does reap it, at the step's end. The notice the agent reads at the move tells it to wait for the result before its final response and not to start a second copy while the call runs (item 43 quotes it): the opposite of what a job command needs, so an agent told only to run the command again gets two contradicting instructions. A double-forked worker in its own session (fork, setsid, fork) survived that kill and the session's exit and wrote its file about 40 s later, sandbox off and on, so a job outlives its step only because it is detached: detachment is necessary, not a precaution. Linux is untested. Evidence: rewrite/spike/probes-round-4/CHECK.md (reruns C and D); round 4's own legs did not show survival.

Proposed resolution: long-commands.md states the premise as observed: backgrounded at the timeout, killed at the step's final response, the job surviving because its worker is detached. The job record covers what outlives the step. An agent whose call is moved to the background runs the same command again, which re-attaches, and does not wait for or read the background task. Because the platform's notice says the opposite at that moment, the agent is given the rule with its reason (the re-run re-attaches to the job already running and is not a second copy) in the builder methods' common text and the clerk's rules (step 5), and a lint test checks that the sentence is there. The Linux leg stays an open probe (platform.md, open leg 43). E2's eleven-minute gate reads its transcripts: wherever a call shows the backgrounding signature (timedOutAfterMs, a backgroundTaskId), the step's next Bash call is the same command. A run in which no call was moved says that this was not measured.

## step3-jobs-fix-4-C2-1 (minor; step3-jobs-fix-4, confirmation; left-for-builder)

Earlier outcome: No fifth round is run. Four rounds on the overlapping-starts logic of env start each closed the case named and the next check found another narrow race, all minor and none on the first story's path (it starts no product). Left for G1 when the build widens, with one instruction beyond the proposed fix: do not patch this branch again. Rewrite the held-state handling of env start as one loop with one rule, that a decision is taken only on a record read after the lock probe it depends on and is re-read before anything is stopped, and add a stress test that runs many overlapping starts of one subject and asserts that exactly one product is left and every call answers with it.

Files: commands/env-start.md

Where it was found: next/plugins/vsdd-factory/py/vsdd/gates/env.py (_wait_for_running, the new dead-settler branch)

New, from the step3-jobs-fix-4-C1-1 fix. The branch _wait_for_running gained for a settling start call that died reads the record and then probes the settle lock. It calls stop_products on that read. This is the snapshot class S3R-jobs-C2-1 named, and the C2-1 fix closed it only in _held_answer's first branch, which re-reads after the probe. A live start call writes 'running' and then releases the settle lock (its env.started emit sits between the two). If both happen between the waiter's read and its settle probe, the waiter takes the healthy, settling call for a dead one. stop_products(subject) re-reads the record, finds it 'running' under a held lock, and kills the product the first call has just reported. The waiter then takes the lock and starts a second product. D14 says a second start at the same commit returns the first. Before this round the settle-held wait only polled for 'running' and stopped nothing, so the fix introduced this. Probe in a scratch copy: SETTLE_SECONDS 1.0, a second start joining a first start's settle window, and only the settle probe made from _wait_for_running delayed 1.5 s. The first call returned 0 with pid 74936, which was dead afterwards. The second returned 0 with a new pid 75340, and the record named 75340. With the pre-fix env.py the same probe returned the first pid to both calls, and the product stayed alive.

Proposed resolution: Decide on a read made after the settle probe, as _held_answer's first branch does. In _wait_for_running, when a read says 'starting' and the settle lock is then found free, read the record again. If it now says 'running', go round the loop so the running branch answers it or replaces it. Treat the record as a dead settler's only when the second read is still 'starting' with the same nonce as the first. A different nonce means a new start call wrote it, so keep waiting. Add a test to test_env.py that widens the window by delaying the settle probe made from _wait_for_running. With a start in flight at the same commit, it asserts that both calls return the same pid and that the product is alive.

## step3-jobs-fix-4-C2-2 (minor; step3-jobs-fix-4, confirmation; left-for-builder)

Earlier outcome: No fifth round is run. Four rounds on the overlapping-starts logic of env start each closed the case named and the next check found another narrow race, all minor and none on the first story's path (it starts no product). Left for G1 when the build widens, with one instruction beyond the proposed fix: do not patch this branch again. Rewrite the held-state handling of env start as one loop with one rule, that a decision is taken only on a record read after the lock probe it depends on and is re-read before anything is stopped, and add a stress test that runs many overlapping starts of one subject and asserts that exactly one product is left and every call answers with it.

Files: commands/env-start.md

Where it was found: next/plugins/vsdd-factory/py/vsdd/gates/env.py (_held_answer's first branch: a 'starting' snapshot with the settle lock free); next/tests/unit/test_env.py (the case comment above the held-state tests)

Old code, from the S3R-jobs-C2-1 fix; this round did not touch it. It falls in the work's case list: a start in flight over a stale record with nothing alive. Every case where the record is absent or 'running' now waits for the holder. A stale 'starting' record (the settling call is dead, its orphan is dead, the lock is free) does not. Suppose start Y takes the lock and an overlapping start W reads that record before Y unlinks it. W probes the settle lock and finds it free, because Y has not yet reached _launch. W then assumes that the lock holder is the dead settler's orphan and calls stop_products. But the orphan's group is gone and Y is the holder. stop_products finds nothing it may stop: Y's record is unlinked, or Y holds the settle lock. If it still lists the stale record before Y takes the settle lock, it waits out its 5 s grace on Y's lock. W then gets None, and start()'s single re-probe returns 1, 'the product lock stays held', while Y answers a pid. D14 says W returns Y's product. Probe in a scratch copy: a stale 'starting' record with pid 999999, Y's unlink of it held back until W reached stop_products or _wait_for_running, both starts at the same head commit. W returned 1, 'the product lock stays held', after 0.02 s and after 0.32 s, with the stale record at the head commit and at another commit. The pre-fix env.py gives the same results. The test_env.py case comment (case 5: 'one that has taken the lock but not yet written, record or none - is waited on like a start in flight') claims more than is true. So does commands/env-start.md ('whether the record is absent or still starting'). No test covers a stale 'starting' record under a start in flight.

Proposed resolution: Stop on a 'starting' record only when its orphan is what holds the lock. Send _held_answer's 'starting' snapshot, whether its settle lock is held or free, to _wait_for_running and drop the separate first branch. In _wait_for_running's dead-settler branch (after the re-read of step3-jobs-fix-4-C2-1), call stop_products(subject) and return None only when the record still has the first read's nonce and _group_alive(record['pid']) holds. When the group is gone, the holder is a start in flight (or an escaped holder), so keep waiting: answer its running record at the same commit, replace it at another, take a freed lock, or fail after _STARTING_WAIT. A scratch-copy version of this change (with the C2-1 re-read) passed every test in test_env.py, the C2-1 probe, and this probe at both record commits (W returned Y's pid after 0.42 s). Add tests to test_env.py: a stale 'starting' record (pid 999999) under a start in flight that has yet to unlink it. At the head commit W returns Y's pid. At another commit (env._head split per thread) W returns a new pid, the record names W's commit and Y's product is gone. Both must finish well inside _STARTING_WAIT. Keep test_start_recovers_from_a_start_call_killed_mid_settle and test_start_takes_over_when_the_settling_start_call_dies passing, since there the orphan's group lives and it is stopped. Correct the case comment.
