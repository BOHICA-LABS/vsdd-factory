## D33-11 (major; decision D33, design; left-for-builder)

Earlier outcome: Not at slice depth: evidence stays local in the slice, so the travelling red record (cycles/<cycle>/red/<story>.json) is M3's to add with G2's owner for the lookup fallback, when the build widens to team use (decision D33).

Files: records/closure.md, records/evidence.md, tables/work-claim-checks.toml, topics/evidence-lookup.md, topics/state-layout.md

Where it was found: next/plugins/vsdd-factory/py/vsdd/state/gate_evidence.py (the red lookup reads local records only); next/plugins/vsdd-factory/py/vsdd/state/commits.py (record_kinds); rewrite/plans/step-4/gates.md; rewrite/plans/step-4/ORDER.md section 7 ("red evidence cannot be restored at an earlier commit")

Evidence is local. A clone that continues another clone's story past its red gate has no red record: the story's position reads ready, the tests-first rule blocks every write to source, the green gate fails with "no red record", and the red gate cannot pass again on a branch whose tests already pass. So a story cannot be handed on once it is past red, which decision D33 requires ("picking up work that was begun on another machine continues from what has been pushed"). The record cannot ride inside the story's closure: a story with many tests would pass the closure's cap of 16,000 bytes and could then never be handed on.

Proposed resolution: The checkpoint and vsdd claim release write the story's latest passing red or re-freeze record to a tracked record of its own, cycles/<cycle>/red/<story>.json, with the fields, the schema and the cap of the evidence record it copies (8,000 bytes), so a record that could be written locally can always travel. The flush's record_kinds registers it in the same step. evidence(project, "red", subject) falls back to it when no local record exists, under the same rule: its commit lies between the story's base and its head. The tests-first rule and the green gate already read through that lookup. Green, demo and the review's cover are measured again as designed.

No code reads a decision file's status directly. Tests: a settlement made while the remote cannot be reached, and one made during a live run.

## D33-10 (minor; decision D33, design; left-for-builder)

Earlier outcome: Package M3 makes the change, with S2a's owner, when the build widens. On one clone the id is unique.

Files: records/closure.md, records/run.md, topics/team-records.md

Where it was found: next/plugins/vsdd-factory/py/vsdd/state/runs.py (_new_id: r-<date>-<minute>-<2 of 36>); the closure's admitted_by and delivery.run (rewrite/plans/step-4/delivery.md 3.4); the Run: trailer of a state commit

A run id is unique on one clone: the store retries until the directory name is free there. Two clones can mint the same id in the same minute (one chance in 1,296 for each pair of runs). The id is written into tracked closures (admitted_by, delivery.run) and compared for equality: the checkpoint reads delivery.state where delivery.run is its own run, so a collision makes one clone read another's delivery outcome as its own.

Proposed resolution: When team use is built, every tracked field that names a run stores the clone's id beside it, and the comparisons use both. The alternative, four characters of the clone's id inside the run id, is one function (_new_id); the schema gives the id no pattern, so either can be done at any time.

## D33-15 (minor; decision D33, design; left-for-builder)

## D33-16 (minor; decision D33, design; left-for-builder)

Earlier outcome: Package M3 adds the rule to each minting command as that command exists; S1's owner gives next_id the argument when it builds vsdd new. Nothing on the slice mints an id.

Files: commands/new.md, tables/identifiers.toml, tables/sync-checks.toml, tables/work-claim-checks.toml

Where it was found: rewrite/plans/step-3/state-core.md section 1 (vsdd new with next_id, left for the widening); rewrite/spec/tables/identifiers.toml ("Sequential, by vsdd"); the commands new, story new-fix, spike open, review prepare and the idea register

An id is minted as the next free number in the local tree, and the command file says why that is safe: "there is one state directory". On a team there is one per clone. Two clones mint the same id: S-0.07 in the standing epic from a wave's fix round and from a critical fix beside it; the same CR number for two queued requests; the same spike id; the same report path. Git then sees one path added twice, and for a story two cycles hold closures for one id.

Proposed resolution: With team use on, a command that mints an id which more than one claim could mint (an epic, a story of the standing epic, a change request, an idea, a spike, an on-demand review report) does so inside a sync (T-MINT): it takes the next free number in the fetched tree, builds one commit on the remote's head that adds the new file alone, and pushes it as a claim is pushed; the file reaches the mount with that commit. The push is judged by T-PUSH: a lost race repeats from the sync with the number taken again. After an answer that was lost the clone record lists the commit with its request, the SHA-256 of the kind of id and of every value the caller gave for the new file and of nothing the tool adds (rewrite/spec/records/clone.md), computed by one function for every minting command. The opening sync of any later command settles the commit, so nothing is minted while it is unknown. A command whose own request equals a settled entry's is given the id back when the remote took the commit, and mints when it did not; either way it removes the entry. A command with any other request mints as usual and leaves the entry, so a lost answer does not become two files for one request and a second request of the same kind is never answered with the first one's id. next_id takes the tree to scan as an argument, so a caller can pass the fetched one. Ids of the specification classes are minted only under the spec claim, and the stories of an epic belong to the run that holds its cycle; they need nothing. A number an agent picks for itself is caught at the sync as one path added twice (diverged).

## D33-20 (minor; decision D33, design; left-for-builder)

Earlier outcome: B8 runs the probe before package M3 builds the rule's part with H7's owner, when the build widens.

Files: rules/decisions.md, tables/work-claim-checks.toml

Where it was found: rewrite/spec/rules/decisions.md (the rule runs on UserPromptExpansion with a four-second deadline and runs no git); rewrite/spec/platform.md

A decision typed in a session is settled by a hook that cannot reach the network inside its deadline. To publish it at once the rule would start a sync as a detached job of its own, keyed by the command and settle:<decision id> (rewrite/spec/topics/long-commands.md). Whether a hook on that event can leave a detached job behind has not been tried: the proven case is a job started from a Bash call.

If it does not, the next sync publishes the settlement. The design is correct either way: a settlement is listed as unpublished from the moment it is written, and nothing acts on it until the remote holds it (D33-28).

## D33-7 (minor; decision D33, design; left-for-builder)

Earlier outcome: Package M3 adds the links and changes the functions, with the owners of S4 and S2a, when the build widens. On one clone the built ordering is right.

Files: records/cycle.md, records/decision.md, tables/team-checks.toml, topics/decisions.md

Where it was found: next/plugins/vsdd-factory/py/vsdd/state/decisions.py (latest_decision sorts by opened; spec_approved reads it); next/plugins/vsdd-factory/py/vsdd/state/cycles.py (cycles_open sorts by opened); rewrite/spec/topics/decisions.md ("every approved merge decision that is newer than the latest approved spec decision")

The latest decision of a kind is found by comparing the opened times of records, open cycles are ordered by their opened times, and dependency detection is specified as a comparison of a merge decision's time with a spec decision's. On a team those times are written by different machines whose clocks need not agree, so "the specification is approved" can be read from the wrong record and two open cycles can come out in the wrong order. The 90-day retention of settled decisions in the standing cycle compares a record's time with the local clock in the same way.

Proposed resolution: A decision whose id carries no subject stores follows: the decision of its kind in the same cycle that was latest when it was opened. A decision whose id carries a subject (a story or a wave) stores none: two clones open such decisions at the same moment, and nothing asks for the latest of them. A merge decision stores spec, the spec decision in force. latest_decision returns the record that no other follows, and two such records are a reported state problem. cycles_open orders by the cycle's kind and then its id. Retention by age may keep reading times: pruning early or late changes no decision. Each ordering function, cycles_open included, gets a test whose times contradict the links.
