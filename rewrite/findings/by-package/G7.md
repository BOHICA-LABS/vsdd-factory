## P3REQ-05 (major; review pass 3; open)

Files: records/baseline.md, tables/routes.toml, topics/multi-repo.md, workflows/ingest.md

Where it was found: rewrite/design/pipeline.md 3.2 'Brownfield multi-repo' mapping, 2.9.11 synthesize row, 2.4 ingest route rows, 2.6 whole-set lock, 2.9.6/2.9.7 hub release; rewrite/design/state.md 2.8 closure row and baseline record (single _standing/units/ingest.json, decision spec), 2.5 toolchain row, 2.14, 2.16 survey row; rewrite/BLUEPRINT.md 3.4 'Several repositories' row, 4.8, 4.13

The design maps multi-repository brownfield to 'ingest with repo for each repository', but the second ingest fails at several points. Its done test reads the first ingest's closed ingest.json, so every stage reads as done. Its baseline would overwrite the first one's, and its decision would reuse the identifier spec in _standing. Once the first baseline is approved, the whole-set specification lock refuses its writes, because an ingest holds no amendment. The route never names it, since a baseline already exists. The gates compare against one baseline measured with one repository's commands, and toolchain.toml cannot fill per-repository commands. Which run opens the hub's single release decision is also unstated.

Proposed resolution: In a hub, ingest without repo covers every member in one run, storing one baseline object per repository in the ingest closure (each with its own integration head and measurements, read by the gates for stories with that repo). It writes toolchain.toml with a [[repo]] section per member, whose approval fills that entry's unset commands, and it ends at one spec decision. A member added later is ingested with repo in a run that holds an amendment. The route's ingest row becomes 'a member has no baseline'. In a hub, verify runs once at the hub and opens the one release decision. Apply this in pipeline 2.4, 2.9.8, 2.9.11 and 3.2, state 2.5, 2.8 and 2.14, and blueprint 3.4 and 4.13, and have E4 run (4) ingest two existing repositories.
