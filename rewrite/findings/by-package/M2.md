## D33-6 (major; decision D33, design; left-for-builder)

Earlier outcome: Package M2 inserts the steps, with S3's owner and M1's sync, when the build widens. The unit being built now keeps the planned order; its steps are already separate calls, which is all the insertion needs.

Files: commands/checkpoint.md, commands/survey.md, commands/sync.md, tables/sync-checks.toml, tables/work-claim-checks.toml

Where it was found: rewrite/plans/step-3/survey.md 3.1 and 3.2 (the order of the survey and of the checkpoint); rewrite/spec/commands/survey.md ("Order of the checks")

The survey is planned as: caller marker, every precondition, flush, lock, admission. On a team the preconditions must be read on fetched state, so a sync comes before them, and a claim comes after the lock; the checkpoint gains the hand-off and the removal of claims before its push. The planned order (preconditions, then flush) is right for one clone and wrong for two: a stale clone would pass "the story is admitted" for a story a teammate has delivered.

Proposed resolution: When team use is built the survey becomes: marker, sync (a full one: flush, list, fetch, combine, push), and only if it ended synced (T-FRESH): preconditions, lock, claim (T-CLAIM, through T-PUBLISH), admission. The checkpoint becomes: map results, hand-off (T-HANDOFF), remove claims (T-RELEASE), sync, release the lock; it ends the run whatever the sync's outcome. With team use off the order stays as planned.

## P3OPS-13 (major; review pass 3; left-for-builder)

Earlier outcome: Decision D33 settles the design, and the lease this finding proposed is not built. The fetch before a survey is the opening sync, without which no run starts (T-FRESH, package M1). What stops two machines running one wave is the work claim: a file on the state branch, made by a push the remote accepts from one clone only, with no expiry and no refresh (T-CLAIM and T-PUBLISH, package M2). A push that is not taken is judged by a fetch and ends as the sync's outcome, not as a blocked decision (T-PUSH, T-COMBINE). Nothing on the slice pushes or fetches, so S2b and S3 build nothing for it now.

Files: commands/survey.md, commands/sync.md, topics/state-commits.md, topics/team-claims.md, topics/team-sync.md

Where it was found: rewrite/design/state.md 2.2 rule 6; 2.3 Push; 2.11 two machines and adoption; 2.9 State problems; rewrite/BLUEPRINT.md 4.13, section 7, section 8 OPS-07

Nothing fetches the state branch before the briefing or the survey. An existing second clone routes on stale state and redoes checkpointed work. Two machines can run the same wave at once, both build the same stories, and adoption lets one take over the other's open PR mid-delivery. Both reach conflicting closure-record pushes with no named repair.

Proposed resolution: The survey fetches and fast-forwards, or rebases, the state branch before preconditions, and the briefing reports when state is behind the remote. The survey writes and pushes a lease (scope, run, machine, time); another machine's survey refuses while it is fresh; checkpoints and deliveries refresh it and the checkpoint clears it. A push conflict opens blocked, reason environment, and status --fix retries the rebase.

## D33-32 (minor; decision D33, design; left-for-builder)

Earlier outcome: B4a keeps the reserve readable when it builds runStories(), and package M2 builds the survey's batch function and its test, when the build widens. The slice runs one story and never calls runStories().

Files: tables/team-delivery-checks.toml, tables/work-claim-scopes.toml, topics/prelude-run-stories.md

Where it was found: rewrite/spec/topics/prelude-run-stories.md (runStories: fit, CLOSE_RESERVE); workflow-lib/prelude.js when B4a builds it; rewrite/spec/tables/work-claim-scopes.toml (story.<id>, when)

runStories() starts min(the agent fit, limits.stories_per_wave_run) stories, where the fit is floor((agents - RUN.agents - CLOSE_RESERVE) / story_agents). With team use on the survey claims the free stories of that batch and no others, so it must work out the same number, and CLOSE_RESERVE is a constant that exists only in the prelude. With the default limits the fit (about 21) is already below the story limit (24), so a survey that used the story limit alone would claim stories the run does not start.

Proposed resolution: B4a keeps the reserve where the survey can read it (one value the build writes into the prelude and Python reads, or a lint test that pins the two equal). Package M2 gives the survey one function that returns N = min(limits.stories_per_wave_run, floor((limits.agents_per_run - limits.step_attempts - reserve) / limits.agents_per_story)), claims the free stories among the first N units the script would start, and returns N to the script as the limit stories_per_run, so the script starts no story outside the batch. Test: on a table of limits and unit lists, the stories runStories() starts are the ones claimed or already held. With team use off the survey returns the configured limit as before.
