## D33-29 (major; decision D33, design; left-for-builder)

Earlier outcome: Package M1 adds it, with S1's owner, when the build widens. The slice makes no network call.

Files: commands/sync.md, topics/team-git-facts.md, topics/team-sync.md

Where it was found: next/plugins/vsdd-factory/py/vsdd/state/gitrun.py (one helper: inherited standard input, the caller's session, a time limit that kills git alone)

The git helper is right for local calls. For a call that reaches the network it is not enough. GIT_TERMINAL_PROMPT=0 does not govern ssh, which asks about an unknown host key or a password on the terminal; an askpass program or a credential helper may open a window; and when git is killed at the time limit its child stays, still holding the prompt (checked with git 2.34.1 and OpenSSH 8.9: a call started from a terminal waited until it was killed and left ssh running, and a waiting credential helper outlived git on Linux and on macOS).

Proposed resolution: Package M1 adds a network form of the helper and uses it for every listing, fetch and push: standard input from /dev/null, a session of its own so that there is no terminal to ask on, GIT_ASKPASS and core.askPass empty, SSH_ASKPASS_REQUIRE=never, credential.interactive=false, and at the time limit a kill of the whole process group. The existing form is unchanged for local calls, so nothing the slice runs changes. Test: a fetch over ssh to a local sshd with an unknown host key, started from a pseudo-terminal, fails at once and leaves no process; a credential helper that waits is gone after the limit.

## D33-3 (major; decision D33, design; left-for-builder)

Earlier outcome: Package M1 makes the change to the flush and builds the sync, with S2b's owner, when the build widens. The flush as built is right for one clone.

Files: commands/sync.md, tables/sync-checks.toml, topics/state-commits.md, topics/team-sync.md

Where it was found: next/plugins/vsdd-factory/py/vsdd/state/commits.py (flush); next/plugins/vsdd-factory/py/vsdd/state/store.py (locked: flush.lock with a wait of 3 s); rewrite/spec/topics/state-commits.md (Push); rewrite/plans/step-3/records.md D11; rewrite/plans/step-3/survey.md D19

The flush and the state push were built and planned for one writer. (a) Where the clone has no git identity the flush commits as vsdd-factory <vsdd-factory@example.invalid>, which on a team hides who acted. (b) Its commit carries Run: and Code-Head: but neither the clone nor the plugin version, so nothing says which clone or version wrote state. (c) Code-Head: is the local integration branch's head, which in pr mode lags the remote. (d) It commits every changed file, with no way to publish a settlement or a claim alone while a run is live. (e) The push is designed as a rebase of the mounted state branch, allowed only while the run lock is held; a sync must also run outside a run and while an agent has uncommitted files in the mount, where a rebase cannot run. (f) The record stores and the function that settles a decision take flush.lock with a wait of three seconds, and a second flush waits five and then leaves its work to the holder; a sync that held that lock across a fetch or a push would make a typed settlement and a record write in a live run fail busy, and would leave a checkpoint's closures out of the commit.

Proposed resolution: When the sync is built: the flush takes an optional path filter; with team use on it refuses a clone for which git has no identity (T-WHO) and adds the trailers Clone: and Plugin:; Code-Head: becomes the fetched head of the target branch; state commits stay unsigned (decision D2). The push is vsdd.state.sync (rewrite/spec/commands/sync.md): it builds the combined commit path by path with a temporary index, never by a merge of the whole tree, and fast-forwards the mount. It takes flush.lock for its local steps only (the flush; the check, combine, fast-forward and clone record; the outcome) and never across a listing, a fetch or a push; a local step that finds the mount's head moved repeats. Whole syncs of one clone are serialised by local/sync.lock: a second sync waits for the first inside its own time budget (in a foreground command 60 seconds for the wait and all network calls together) and answers busy at its end, having changed nothing; a command that takes a claim, mints an id or opens a cycle holds the lock for its whole act. Every fetch goes into the remote-tracking ref (git fetch <remote> +refs/heads/<branch>:refs/remotes/<remote>/<branch>) and never into a local branch, and every push of the state branch names the head it was built on (--force-with-lease=refs/heads/<branch>:<that head>), so that it only adds to that head (T-REMOTE, T-PUSH). A branch is looked for on the remote by its exact ref name, through one function, because git ls-remote matches a pattern at the end of a name (the listing rule at the head of rewrite/spec/tables/team-checks.toml). sync.remote_head is the last head of the remote whose arrivals the clone checked and took into its mount: it is written only after the mount holds the commit, by the local step that checked what arrived and fast-forwarded the mount (to the fetched head) and when a push of the clone is accepted (to the pushed commit, not to the remote's head); a fetch made to judge a push writes nothing, so after a lost race the repeated sync checks every commit between the push's base and the new head (T-HISTORY, T-INCOMING). The sync ends synced without a fetch only when the listed head is sync.remote_head, the mount's head is that commit too, sync.unknown is empty and, in a full sync, the clone holds no claim that T-RELEASE has a sync remove (rewrite/spec/commands/sync.md, step 3). With team use off the push changes only as the head of rewrite/spec/tables/team-checks.toml lists: T-SOLO, where a push that finds the remote moved stops where it used to rebase and retry, and T-REMOTE's choice of remote and refs. The slice builds no push, so nothing is built differently now. Tests: a settlement and a closure write succeed while a slow remote holds a sync's fetch open; a survey that starts while a sync job holds the lock answers busy inside its budget; a state branch rewound between a fetch and a push is answered rewritten and the removed commits are not pushed back; a record that fails its check, pushed by the clone that beat this clone's push, is reported by the repeated sync before the mount takes it; a listing answered only by a branch whose name ends in the state branch's ref name is read as missing.

## P3OPS-13 (major; review pass 3; left-for-builder)

Earlier outcome: Decision D33 settles the design, and the lease this finding proposed is not built. The fetch before a survey is the opening sync, without which no run starts (T-FRESH, package M1). What stops two machines running one wave is the work claim: a file on the state branch, made by a push the remote accepts from one clone only, with no expiry and no refresh (T-CLAIM and T-PUBLISH, package M2). A push that is not taken is judged by a fetch and ends as the sync's outcome, not as a blocked decision (T-PUSH, T-COMBINE). Nothing on the slice pushes or fetches, so S2b and S3 build nothing for it now.

Files: commands/survey.md, commands/sync.md, topics/state-commits.md, topics/team-claims.md, topics/team-sync.md

Where it was found: rewrite/design/state.md 2.2 rule 6; 2.3 Push; 2.11 two machines and adoption; 2.9 State problems; rewrite/BLUEPRINT.md 4.13, section 7, section 8 OPS-07

Nothing fetches the state branch before the briefing or the survey. An existing second clone routes on stale state and redoes checkpointed work. Two machines can run the same wave at once, both build the same stories, and adoption lets one take over the other's open PR mid-delivery. Both reach conflicting closure-record pushes with no named repair.

Proposed resolution: The survey fetches and fast-forwards, or rebases, the state branch before preconditions, and the briefing reports when state is behind the remote. The survey writes and pushes a lease (scope, run, machine, time); another machine's survey refuses while it is fresh; checkpoints and deliveries refresh it and the checkpoint clears it. A push conflict opens blocked, reason environment, and status --fix retries the rebase.

## D33-31 (minor; decision D33, design; left-for-builder)

Earlier outcome: Package M1 adds the field to the job specification and sets it for the sync, with G1's owner, when the build widens. Nothing built today is a sync, so the job layer as built is right for every command that uses it.

Files: commands/sync.md, rules/decisions.md, topics/long-commands.md

Where it was found: next/plugins/vsdd-factory/py/vsdd/gates/jobs.py (attach, _serves); rewrite/spec/topics/long-commands.md (Team use); rewrite/spec/commands/sync.md

The job layer serves a finished result that nobody collected to the next call with the same key (_serves: not collected, or the caller's own nonce). That is right for a gate, whose result belongs to a commit. vsdd sync is keyed by the command and the state branch with no commit, so a sync that the decisions rule started detached, or one whose caller did not come back after a pending answer, would hand its old outcome to a later vsdd sync, and no sync would run.

Proposed resolution: Package M1 adds one field to the job specification, with G1's owner: the worker marks its own result as collected when it writes it. A call that started the job, or attached while it ran, is still given the result through its nonce; any later call starts a new sync. Only the sync sets the field, so no gate or delivery changes. The sync the decisions rule starts is a job of its own, keyed by the command and settle:<decision id>, which also names the one record its flush may commit. Test: a commit pushed to the remote after a detached sync has ended is in the mount after the next vsdd sync; a settlement typed while a vsdd sync job runs is published by its own job.

## d33-fix-2-C2-3 (minor; d33-fix-2, confirmation; left-for-builder)

Resolution for the builder, who corrects the spec file in the same change: in T-HISTORY name the starting value of sync.remote_head in a new clone record: the merge base of the mount's head and the fetched head, written once the mount holds it (for T-JOIN, the mounted head); keep T-HISTORY as the one statement of when the field is written, cut record:clone and the schema description to a one-line meaning with a link, have T-PUSH link to T-HISTORY instead of restating it, and add to proof scenario 17 a failing record on the remote when the second clone joins, which its sync reports through T-INCOMING.

Files: packaging/proof-team.md, records/clone.md, schemas/clone.schema.json, tables/sync-checks.toml

Where it was found: rewrite/spec/tables/sync-checks.toml (T-HISTORY, T-PUSH); rewrite/spec/records/clone.md (sync.remote_head); rewrite/spec/schemas/clone.schema.json (remote_head)

New, from the correction of D33R-C-3. T-HISTORY now says sync.remote_head 'is written in two places only': step 4 of the sync, and an accepted push. Neither place covers the moment a clone record is made. vsdd init writes the record when a clone joins (T-JOIN; record:clone, 'Written by'), and the schema requires remote_head. T-SWITCH and T-SOLO's join make the record inside a sync whose T-HISTORY and T-INCOMING read the field before step 4 writes it. A record that is remade has lost it. Before the correction, 'the head at the last listing or fetch that succeeded' gave init's fetch and the switching sync's fetch a value. Now no file says what a new record holds, what the `rewritten` test compares, or which files T-INCOMING checks on a clone's first team sync. The rule is also stated more than once. record:clone says when the field is written 'is T-HISTORY's to say' and then repeats that a judging fetch does not change it. The schema description repeats both halves, and T-PUSH repeats 'That fetch changes nothing in the mount or the clone record' beside T-HISTORY's 'A fetch made to judge a push writes nothing'. Adding a third writer would mean editing four places.

Proposed resolution: In T-HISTORY, name the value a new record starts with: the merge base of the mount's head and the fetched head, written once the mount holds it. For T-JOIN at vsdd init that is the head it mounted; for T-SWITCH, T-SOLO's join and a `remade` record it is what this clone last shared with the remote. A rewrite that happened before then is the case T-HISTORY's `unmeasured` cell already names. Keep T-HISTORY as the one statement of when the field is written. Cut record:clone and the schema description to the field's one-line meaning with a link to T-HISTORY. Drop T-PUSH's copy and have T-PUSH link to T-HISTORY. Add to proof scenario 17 a record that fails its check and is on the remote when B joins at its push: B's sync reports it through T-INCOMING.
