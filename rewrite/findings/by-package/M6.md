## D33-12 (major; decision D33, design; left-for-builder)

Earlier outcome: S1's owner makes the change when the build widens, before or with package M6, whose T-JOIN builds on it. The slice's sample has one remote named origin or none, so nothing it does changes.

Files: commands/init.md, tables/sync-checks.toml, tables/team-checks.toml, topics/state-directory.md

Where it was found: next/plugins/vsdd-factory/py/vsdd/state/mount.py (detect reads refs/remotes/origin/factory-artifacts; mount_state adds origin/factory-artifacts); next/plugins/vsdd-factory/py/vsdd/state/cmd_init.py (_branch_tip); rewrite/spec/topics/state-directory.md (the table of conditions)

A remote is named in code. On a clone whose remote has another name, detect answers none where the truth is unmounted, and vsdd init creates a second, unrelated state branch instead of mounting the one on the remote. Two histories of state then exist that no push or merge can combine. A team's clones need not agree on what they call the remote.

Proposed resolution: detect and init look for the state branch under every remote: the loose ref refs/remotes/<any>/factory-artifacts and the matching lines of packed-refs, still by file reads only. When more than one remote holds it, init mounts nothing and lists them, and the option --remote <name>, which setup passes after asking the person which is the repository the team shares, says which to use. The mount sets the state branch's upstream to that remote, which is all the sync reads afterwards (T-REMOTE). The test mounts from a remote that is not called origin, and from a clone with two.

## D33-14 (minor; decision D33, design; left-for-builder)

Earlier outcome: Package M6 builds it, with S1's owner, when the build widens. The slice initialises a project that has no state yet, which this does not touch.

Files: commands/init.md, records/clone.md, skills/setup.md, tables/team-checks.toml

Where it was found: next/plugins/vsdd-factory/py/vsdd/state/cmd_init.py (mounts an existing remote state branch on any clone); rewrite/spec/skills/setup.md

vsdd init mounts a state branch it finds on the remote without a word about the clone that wrote it. That is how a second clone starts writing a project's state unannounced, which is the case decision D33 exists for. Refusing the mount would change what a project with one clone does (decision D1: one setup per clone), so the clone is told, and the first push that finds a second writer is what stops.

Proposed resolution: T-JOIN: when the state branch is on a remote and not local, init reads team.enabled from the remote's factory.toml without mounting. True: it runs the preflight, mounts, and writes the clone record with how = joined and the label of --label. Otherwise it mounts as it does today and returns a notice, which setup shows: this state was written on another clone, and if both are going to run the factory, team use is turned on first on the clone that has the project. There is no flag that only a person may pass. T-SOLO, in the sync, is the guard at the first push.

## D33-22 (minor; decision D33, design; left-for-builder)

Earlier outcome: Package M6 builds the function when the build widens; T1's owner prints its lines and the rest when T1 is built.

Files: commands/doctor.md, packaging/sandbox-needs.md, tables/sync-checks.toml, tables/team-checks.toml

Where it was found: rewrite/spec/commands/doctor.md; rewrite/spec/packaging/sandbox-needs.md ("Network to the git remote")

vsdd doctor checks git and nothing about the remote. On a team, a clone that cannot list the remote, has no git identity, is shallow, has a git below the floor, or runs a plugin below team.min_plugin fails at its first survey with no earlier warning; and nothing lets people see that two clones push to two different repositories, which no program can measure.

Proposed resolution: Package M6 delivers one preflight function that returns a line for each check: git at 2.34 or newer, this plugin's version against team.min_plugin, not a shallow clone, the identity git would use, the upstream of each factory branch, and whether the remote answers a listing inside the time limit. The sync, vsdd init, vsdd status and the doctor all call it, so they cannot disagree, and M6 does not wait for T1. With team use on the doctor prints those lines, the address each factory branch is pushed to with any user or password part removed, the length of the state branch, and what the factory needs of the repository's rules (direct pushes of unsigned commits to the state branch; no forced push or deletion there). Whether the clone may push stays unmeasured and is said so.

## d33-fix-2-C2-3 (minor; d33-fix-2, confirmation; left-for-builder)

Earlier outcome: Left for the package that builds it, after the two correction rounds this design gets; nothing of D33 is on the thin slice path. Resolution for the builder, who corrects the spec file in the same change: in T-HISTORY name the starting value of sync.remote_head in a new clone record: the merge base of the mount's head and the fetched head, written once the mount holds it (for T-JOIN, the mounted head); keep T-HISTORY as the one statement of when the field is written, cut record:clone and the schema description to a one-line meaning with a link, have T-PUSH link to T-HISTORY instead of restating it, and add to proof scenario 17 a failing record on the remote when the second clone joins, which its sync reports through T-INCOMING.

Files: packaging/proof-team.md, records/clone.md, schemas/clone.schema.json, tables/sync-checks.toml

Where it was found: rewrite/spec/tables/sync-checks.toml (T-HISTORY, T-PUSH); rewrite/spec/records/clone.md (sync.remote_head); rewrite/spec/schemas/clone.schema.json (remote_head)

New, from the correction of D33R-C-3. T-HISTORY now says sync.remote_head 'is written in two places only': step 4 of the sync, and an accepted push. Neither place covers the moment a clone record is made. vsdd init writes the record when a clone joins (T-JOIN; record:clone, 'Written by'), and the schema requires remote_head. T-SWITCH and T-SOLO's join make the record inside a sync whose T-HISTORY and T-INCOMING read the field before step 4 writes it. A record that is remade has lost it. Before the correction, 'the head at the last listing or fetch that succeeded' gave init's fetch and the switching sync's fetch a value. Now no file says what a new record holds, what the `rewritten` test compares, or which files T-INCOMING checks on a clone's first team sync. The rule is also stated more than once. record:clone says when the field is written 'is T-HISTORY's to say' and then repeats that a judging fetch does not change it. The schema description repeats both halves, and T-PUSH repeats 'That fetch changes nothing in the mount or the clone record' beside T-HISTORY's 'A fetch made to judge a push writes nothing'. Adding a third writer would mean editing four places.

Proposed resolution: In T-HISTORY, name the value a new record starts with: the merge base of the mount's head and the fetched head, written once the mount holds it. For T-JOIN at vsdd init that is the head it mounted; for T-SWITCH, T-SOLO's join and a `remade` record it is what this clone last shared with the remote. A rewrite that happened before then is the case T-HISTORY's `unmeasured` cell already names. Keep T-HISTORY as the one statement of when the field is written. Cut record:clone and the schema description to the field's one-line meaning with a link to T-HISTORY. Drop T-PUSH's copy and have T-PUSH link to T-HISTORY. Add to proof scenario 17 a record that fails its check and is on the remote when B joins at its push: B's sync reports it through T-INCOMING.
