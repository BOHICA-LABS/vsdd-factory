Where it was found: topics/worktrees.md (The base of a story branch); topics/evidence-lookup.md; commands/story-deliver.md (What it refuses, verdict binding); commands/gate-green.md; records/evidence.md

## D33-10 (minor; decision D33, design; left-for-builder)

Earlier outcome: Package M3 makes the change, with S2a's owner, when the build widens. On one clone the id is unique.

Files: records/closure.md, records/run.md, topics/team-records.md

Where it was found: next/plugins/vsdd-factory/py/vsdd/state/runs.py (_new_id: r-<date>-<minute>-<2 of 36>); the closure's admitted_by and delivery.run (rewrite/plans/step-4/delivery.md 3.4); the Run: trailer of a state commit

A run id is unique on one clone: the store retries until the directory name is free there. Two clones can mint the same id in the same minute (one chance in 1,296 for each pair of runs). The id is written into tracked closures (admitted_by, delivery.run) and compared for equality: the checkpoint reads delivery.state where delivery.run is its own run, so a collision makes one clone read another's delivery outcome as its own.

Proposed resolution: When team use is built, every tracked field that names a run stores the clone's id beside it, and the comparisons use both. The alternative, four characters of the clone's id inside the run id, is one function (_new_id); the schema gives the id no pattern, so either can be done at any time.

## D33-7 (minor; decision D33, design; left-for-builder)

Earlier outcome: Package M3 adds the links and changes the functions, with the owners of S4 and S2a, when the build widens. On one clone the built ordering is right.

Files: records/cycle.md, records/decision.md, tables/team-checks.toml, topics/decisions.md

Where it was found: next/plugins/vsdd-factory/py/vsdd/state/decisions.py (latest_decision sorts by opened; spec_approved reads it); next/plugins/vsdd-factory/py/vsdd/state/cycles.py (cycles_open sorts by opened); rewrite/spec/topics/decisions.md ("every approved merge decision that is newer than the latest approved spec decision")

The latest decision of a kind is found by comparing the opened times of records, open cycles are ordered by their opened times, and dependency detection is specified as a comparison of a merge decision's time with a spec decision's. On a team those times are written by different machines whose clocks need not agree, so "the specification is approved" can be read from the wrong record and two open cycles can come out in the wrong order. The 90-day retention of settled decisions in the standing cycle compares a record's time with the local clock in the same way.

Proposed resolution: A decision whose id carries no subject stores follows: the decision of its kind in the same cycle that was latest when it was opened. A decision whose id carries a subject (a story or a wave) stores none: two clones open such decisions at the same moment, and nothing asks for the latest of them. A merge decision stores spec, the spec decision in force. latest_decision returns the record that no other follows, and two such records are a reported state problem. cycles_open orders by the cycle's kind and then its id. Retention by age may keep reading times: pruning early or late changes no decision. Each ordering function, cycles_open included, gets a test whose times contradict the links.
