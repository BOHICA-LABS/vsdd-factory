## P3SEAM-01 (blocker; review pass 3; open)

Files: commands/feature-route.md, workflows/feature.md

Where it was found: rewrite/design/pipeline.md 2.9.4 delta-and-route row, 2.6, 2.9.5; rewrite/BLUEPRINT.md 4.9 feature route row, 3.3 step 2; rewrite/design/state.md 2.16 feature route row, 2.4 lock row; rewrite/design/agents-skills.md 2.6 architect and story-writer rows; rewrite/design/hooks.md 2.11.3 artifact_frozen

`vsdd feature route --run <id>` must derive the route from 'the delta record the step just wrote' or 'the stored change analysis', but no document gives that record a path, kind or class. The only candidate, an impact assessment under specs/architecture/assessments, is in spec-arch. That class is locked during the delta step: the latest spec decision is approved, and the run holds no amendment until `feature route` marks one. The route command is the step's closing command, so it runs before the step record exists. The story-writer, the spec packet and plan in delta scope also need the analysis, and the story-writer cannot read runs. Every feature run, and so every brownfield change and bug fix, has no input for its route.

Proposed resolution: Add a file input: `vsdd feature route --run <id> --delta-file <path>`. The architect writes the delta data JSON in the temporary directory. The tool validates it and copies it into the cycle's tracked record (for example cycles/<cycle>/units/feature.json), which becomes the 'stored change analysis' that the story-writer, the packet and plan read. Update pipeline.md 2.9.4, blueprint 4.9, state.md 2.8 and 2.16, agents-skills.md 2.6 and the delta-analysis method.

## P3REQ-01 (major; review pass 3; open)

Files: commands/survey.md, tables/routes.toml, workflows/feature.md

Where it was found: rewrite/design/pipeline.md 2.3 feature row, 2.4 route row 'No cycle is open and a change request is queued', 2.9.4 survey row, 2.9.7 close row; rewrite/design/state.md 2.5 change request row, 2.7 next field, 2.11 lock, 2.16 survey row; rewrite/BLUEPRINT.md 3.4 row 2, 4.9 survey row; rewrite/design/packaging.md 2.6 route and import fixtures

The route names 'feature with the oldest queued request', but nothing defines what next.args carries, and the feature survey can receive a request only as free text in --request-uri, which always writes a new request file. There are three readings and all fail. The request text duplicates the request and leaves the CR queued, so it is offered again after the release. 'CR-NNN' is stored as a new request whose text is the identifier. An empty args fails because request is required on a first run. Whether a request typed while another run holds the lock is recorded before the lock refusal is also unstated.

Proposed resolution: Define next for a queued request as {command: '/vsdd-factory:feature', args: {request: 'CR-NNN'}}. A request argument that is exactly a queued CR id is passed as --subject and activates that file instead of writing a new one. feature with no request and no amend takes the in-flight request, or else the oldest queued one. The survey writes a new request file before any lock check and returns 'queued' without taking the lock when a cycle is active. Apply this in pipeline 2.3, 2.4 and 2.9.4, state 2.5, 2.7 and 2.16, and blueprint 4.9, and add a fixture for a typed request that is queued and later activated once.

## P3REQ-02 (major; review pass 3; left-for-builder)

Earlier outcome: Half-built, recorded again after review: done — there is no cycle base; admission reads the target branch's head at the moment of creation and records it as delivery.base (test_admit_base_is_target_head_at_creation). Remainder, with the owning package: readiness ordering, so the harness chore lands before the stories whose red gate needs it — G5 and the W-feature.

Files: commands/plan-schedule.md, topics/worktrees.md, workflows/feature.md

Where it was found: rewrite/design/pipeline.md 2.9.1 'Where a child's unit comes from', 2.9.4 story-draft and deliver rows, 2.9.5 readiness paragraph; rewrite/design/state.md 2.12 missing-commands bullets, 2.16 gate plan row, 2.8 cycle record (no base field); rewrite/BLUEPRINT.md 3.4 row 4, 4.6

On a fast route the story-writer writes and admits the readiness chores and the change's own story in one step. Admission cuts every branch at once from 'the cycle's base', which is not defined anywhere. The fix story's worktree therefore lacks the test harness that the readiness chore later delivers, and it is never refreshed, because delivery rebases only on a conflict. Its red gate cannot produce a JUnit report, so the story is blocked and then stuck. On the standard route, plan schedule puts only the scaffold alone in the first wave, so a harness chore can share wave 1 with stories whose red gate needs it.

Proposed resolution: Define the cycle's base as the integration head at admission (the release tag for a hotfix). When the route lists readiness stories, the fast route runs story-draft and deliver twice: first the readiness chores alone, then the change's own stories. plan schedule puts the test-harness chore in a first wave of its own, like the scaffold. Apply this in pipeline 2.9.1, 2.9.4 and 2.9.5, state 2.12 and 2.16, and blueprint 4.6, and add an E4 assertion that the fix story's red gate reads a JUnit report.

## CL-R1 (minor; close-out of pass 2; left-for-builder)

Earlier outcome: Not at slice depth: cycle records carry route and cycle_write is the one path that writes them; vsdd feature route itself (which must only write in the run that opened the cycle) is G5's command.

Files: commands/feature-route.md, records/cycle.md, workflows/feature.md

Where it was found: pipeline.md 2.9.4 delta and route row (line 982); state.md 2.16 vsdd feature route row (line 1432); state.md 2.7 writers table (line 720); state.md 2.8 Cycle record row (line 736); pipeline.md 2.6 'Amendments inside an open cycle' (lines 505-513); effects at pipeline.md 2.9.6 (line 1051) and 2.9.7 (line 1063)

Because of N1, vsdd feature route writes the route it derives into cycle.json with no exception. A feature run with amend runs inside a cycle someone else opened and has a delta step that ends with vsdd feature route, so it overwrites that cycle's route. Suppose a product cycle's amendment changes no contract: its route derives as trivial, verify then runs baseline only for the whole product cycle, and the release version is computed from the wrong route. state.md 2.8 says the route is written only 'when a change request opened' the cycle, which contradicts the other three places.

Proposed resolution: State that a run with amend is always on the standard route, and that vsdd feature route writes route only in the run that opened the cycle, so an amendment run leaves cycle.json unchanged. Make the change in pipeline.md 2.9.4 and 2.6, state.md 2.7 and 2.16, and blueprint 4.9. The plan row's amendment clause already re-traces an amended fast-route cycle.
