## PR4-2 (minor; platform probes, round 4; left-for-builder)

Earlier outcome: G1: the job record, not the tool's timeout, is what reaps a job. E2: its eleven-minute gate must measure that a call moved to the background is followed by a re-run of the same command, which re-attaches.

Files: packaging/e2e-story-tier.md, topics/long-commands.md

Where it was found: rewrite/spec/topics/long-commands.md; the G1 open probe in rewrite/plans/step-3/RESOLUTIONS.md; items 43 and 6 of the platform record; rewrite/plans/step-5/agents.md M3 and the clerk

The design worded the Bash timeout as a kill ('the tool stops a foreground command', 'a call killed by a timeout'). Observed on Claude Code 2.1.331, macOS, default mode, sandbox off and on: a foreground call past its Bash timeout is not killed at the timeout. It is moved to the background (timedOutAfterMs, a backgroundTaskId, backgroundEndsWithFinalResponse true), and it is killed when the step agent gives its final response (its task output reads '[killed]'). The platform does reap it, at the step's end. The notice the agent reads at the move tells it to wait for the result before its final response and not to start a second copy while the call runs (item 43 quotes it): the opposite of what a job command needs, so an agent told only to run the command again gets two contradicting instructions. A double-forked worker in its own session (fork, setsid, fork) survived that kill and the session's exit and wrote its file about 40 s later, sandbox off and on, so a job outlives its step only because it is detached: detachment is necessary, not a precaution. Linux is untested. Evidence: rewrite/spike/probes-round-4/CHECK.md (reruns C and D); round 4's own legs did not show survival.

Proposed resolution: long-commands.md states the premise as observed: backgrounded at the timeout, killed at the step's final response, the job surviving because its worker is detached. The job record covers what outlives the step. An agent whose call is moved to the background runs the same command again, which re-attaches, and does not wait for or read the background task. Because the platform's notice says the opposite at that moment, the agent is given the rule with its reason (the re-run re-attaches to the job already running and is not a second copy) in the builder methods' common text and the clerk's rules (step 5), and a lint test checks that the sentence is there. The Linux leg stays an open probe (platform.md, open leg 43). E2's eleven-minute gate reads its transcripts: wherever a call shows the backgrounding signature (timedOutAfterMs, a backgroundTaskId), the step's next Bash call is the same command. A run in which no call was moved says that this was not measured.

## PR4-3 (minor; platform probes, round 4; left-for-builder)

Earlier outcome: E2, and every headless driver: enter a workflow through a typed command or skill and check afterwards that the named workflow is what ran (platform item 49).

Files: platform.md, topics/spikes.md

Where it was found: rewrite/spec/topics/spikes.md; the story-ready fixture, E2's first run and the scheduler recipe (step 6, item 25); item 49 of topics/platform-proven-2.md; rewrite/spec/platform.md, 'Headless runs'

A headless main session told to start a named workflow can pass its own inline script instead: the Workflow tool accepts a script field, and the named plugin workflow never runs. Round 4 lost two probe runs to this. Entering through a typed skill that names the workflow does not prevent it: in the check's rerun E the main session, started through the typed skill, still passed an inline script ('return {}'). Seen in the default mode on Claude Code 2.1.331 with a --plugin-dir plugin. Evidence: rewrite/spike/probes-round-4/CHECK.md (rerun E, E-inline-script).

Proposed resolution: A typed skill or command stays the way in, but it is not the check. Every headless driver (the story-ready fixture, E2's first run, scheduler recipes, probe harnesses) verifies that the named workflow ran, by comparing the run record's scriptPath and script with the plugin's file, or a PreToolUse rule refuses a Workflow call that carries script in a driver session. topics/spikes.md names the inline-script shape as the failure this prevents.

## PR5-1 (minor; platform probes, round 5; open)

Files: platform.md

Where it was found: rewrite/plans/step-6/first-run.md 3.7 (the cause budget_stop), 3.5 (the --max-budget-usd row) and D11 (STEP_EFFORT_PROVEN); rewrite/plans/step-6/ORDER.md section 7 (the row budget_stop and the caps), 8.2 row A4 and the E2 line of 8.4; items 53 and 54 of topics/platform-proven-3.md

The plan read a --max-budget-usd stop as one thing ('what the step that was running left behind'). Observed on Claude Code 2.1.332, macOS, default mode, a workflow of three small typed steps in a row, by the prober (cap 0.05 dollars) and by the independent check's reruns (caps 0.05 and 0.02; rewrite/spike/probes-round-5/CHECK.md, section 3): the stop has two shapes. The session result is the same in both: exit 1, subtype error_max_budget_usd, is_error true, errors ['Reached maximum budget ($<cap>)'], terminal_reason budget_exhausted, and no result key at all (not an empty result text). Shape 1, cap 0.05, seen by the prober and by the check: the spend crossed the cap only with the main loop's second answer, after the workflow had ended; the run record reads status completed and holds the workflow's whole return value, every agent is done, and standard error is empty. No step was running, so this is not a stop in the middle of a workflow. Shape 2, cap 0.02, seen in the check's rerun only: the cap was passed while the first step ran; standard error says 'Budget limit reached ($0.05 of $0.02); stopping background agents.'; the run record reads status killed and result null and adds a key error ('Error: Workflow aborted'); the running step is left in state progress and its result is lost, though the hook log holds that step's StructuredOutput PreToolUse payload with no PostToolUse; the later steps never started. The cap is soft: what is in flight is charged past it (0.0578 and 0.0651 dollars on a 5-cent cap; 0.0544 on a 2-cent cap, 2.7 times); how far a large step overshoots was not measured. A driver that diagnosed from the session result alone could not tell the shapes apart and would discard a usable result in the first; one that indexes result['result'] would raise. Alongside this, leg A settled what the plans flagged as open. The typed workflow command starts the named file byte for byte with no skill and no main-session denial. The plugin's hooks, workflow and bin/ load under --setting-sources project,local --strict-mcp-config, with the sandbox-off --settings flag honoured (a commit under .git/worktrees/ succeeded); the person's user-level CLAUDE.md still reaches the main session and the step under those flags. A step's hook payloads carry the effort the step was dispatched with: low under a session at medium (the prober's run, where the agent file also said low) and, in the check's rerun, low under an agent file at xhigh; a main-session payload carries the session's effort (medium). The plan ships STEP_EFFORT_PROVEN false, so the plan must change: it ships true. Evidence: rewrite/spike/probes-round-5/CHECK.md, which holds where RESULTS.md beside it differs; leg-A/ and leg-B/.

Proposed resolution: first-run.md 3.7 (the cause budget_stop) and ORDER.md section 7 (its row) say: the session reports error_max_budget_usd (exit 1, is_error true, no result key, errors naming the cap), and the driver reads the run record. It is completed with the whole result when the cap was passed after the workflow ended. It is killed, with error 'Workflow aborted', result null and the running step left in progress, when the cap was passed during a step; standard error then says 'Budget limit reached ...; stopping background agents.' The diagnosis names that step; its result may be in the hook capture with no PostToolUse. Resume with --dir. The driver reads result.get('result'), never result['result']. The caps are soft and the plans say so beside them: the session cap, and the total over all attempts, can each be passed by one attempt's in-flight calls. STEP_EFFORT_PROVEN in tests/e2e/probe.py ships True, resting on item 53 with the check's rerun (first-run.md D11; ORDER.md 8.2 row A4 and the E2 line of 8.4), as PR5C-15 says.
