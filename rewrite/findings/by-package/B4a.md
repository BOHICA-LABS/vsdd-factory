## D33-32 (minor; decision D33, design; left-for-builder)

Earlier outcome: B4a keeps the reserve readable when it builds runStories(), and package M2 builds the survey's batch function and its test, when the build widens. The slice runs one story and never calls runStories().

Files: tables/team-delivery-checks.toml, tables/work-claim-scopes.toml, topics/prelude-run-stories.md

runStories() starts min(the agent fit, limits.stories_per_wave_run) stories, where the fit is floor((agents - RUN.agents - CLOSE_RESERVE) / story_agents). With team use on the survey claims the free stories of that batch and no others, so it must work out the same number, and CLOSE_RESERVE is a constant that exists only in the prelude. Proposed resolution: B4a keeps the reserve where the survey can read it (one value the build writes into the prelude and Python reads, or a lint test that pins the two equal). Package M2 gives the survey one function that returns N = min(limits.stories_per_wave_run, floor((limits.agents_per_run - limits.step_attempts - reserve) / limits.agents_per_story)), claims the free stories among the first N units the script would start, and returns N to the script as the limit stories_per_run, so the script starts no story outside the batch. Test: on a table of limits and unit lists, the stories runStories() starts are the ones claimed or already held. With team use off the survey returns the configured limit as before.

## probes-4-apply-C2-1 (minor; probes-4-apply, confirmation; left-for-builder)

Earlier outcome: B4a (the prelude's relay text) with W2: limit relay's 'if it prints no JSON' sentence to a call that finished, and say what the clerk does with a call that was moved to the background. PR4C-13 must not be read as saying relay retries: it retries only on a null return.

Files: topics/prelude-steps.md

Where it was found: rewrite/spec/topics/prelude-steps.md (relay); next/workflow-lib/prelude.js (relay); rewrite/plans/step-5/agents.md (the clerk, section 3); rewrite/plans/step-5/RESOLUTIONS.md (PR4C-13)

The correction limited the clerk's no-JSON rule to 'a finished call', so that a call moved to the background leads to a re-run and not to an error result. But the clerk also reads relay()'s task text (topics/prelude-steps.md, built in prelude.js). That text still says, with no limit: 'If it prints no JSON, return <the empty object> with "error" set to what it printed.' A moved call has printed no JSON, so the clerk again gets two instructions that disagree, which is the fault probes-4-apply-C1-2 was about. Step-5 RESOLUTIONS.md PR4C-13 says the rule 'speaks of a finished call, so a moved call does not trigger it'; that is true of the clerk file only. The corrector's stated safety net is also wrong. relay() makes its second attempt only when the agent returns nothing (`if (r) return r`), so an error object goes straight to the script. Only the next run re-attaches to the job. The case is rare: relay commands carry no --wait, so a job's default 100 s wait lies inside the 600000 ms timeout. A call is moved only if the clerk sets its own timeout under 100 s.

Proposed resolution: Make the two texts agree, in one of two ways. Either B4a's relay() text (prelude-steps.md and prelude.js) limits its no-JSON sentence to a finished call and adds M3's background sentence; whichever unit next edits the prelude does this (left-for-builder, B4a). Or, if the prelude stays as it is, step-5 RESOLUTIONS.md PR4C-13 says that the task text's no-JSON rule still applies to a moved clerk call, that the step then ends with an error, and that the next run's re-attach recovers it. It must not say that relay retries.
