# S-25.05: Cross-File Crash-Atomicity for `rotate_changelog_at` — Archive Never Accumulates Duplicates Under Partial-Rotation Crash

## Narrative

- **As a** factory pipeline operator who relies on BC-INDEX.md's evergreen changelog archive
  (`BC-INDEX-changelog-archive.md`) being an accurate, append-only, no-duplicate record of
  all rotated-out `changelog:` items
- **I want** the `rotate_changelog_at` primitive to be crash-atomic at the archive boundary:
  if the process crashes or the source rewrite fails after the archive write succeeds, the next
  dispatch must self-heal by completing the source trim WITHOUT re-appending the already-archived
  overflow items — for ALL rotations (not just the first) — using a mechanism that correctly
  distinguishes a crash-retry from a legitimate second rotation whose overflow items coincide
  with the archive tail
- **So that** the archive's append-only, no-duplicate guarantee (BC-1.18.009 Inv-6, VP-112)
  holds unconditionally across an arbitrary sequence of rotations and crash points, without
  relying on the operator to notice or manually repair duplicate accumulation

## Context / Feature Summary

**Origin:** S-25.02 cluster-4 (mechanism-B1 hardening), Obs B crash-recovery. BC-1.18.009
v1.6 added Invariant Inv-6 asserting that `rotate_changelog_at` is crash-idempotent via a
"byte-level tail-match dedup." An implementation attempt was made; adversarial re-cascade
(pass-1, cluster-4 hardening) found the proposed mechanism CRITICALLY UNSOUND. The human
directed that the attempt be reverted from S-25.02 and a proper fix deferred to this story.

### The Two-Write Problem

`rotate_changelog_at` performs two sequential file writes:

1. **Write 1 (archive):** Append the overflow items (`move_items`) to the evergreen archive
   `BC-INDEX-changelog-archive.md`.
2. **Write 2 (source):** Rewrite/trim `BC-INDEX.md`'s frontmatter `changelog:` sequence to
   `low_water_mark` items via `write_atomic`.

A crash or `write_atomic` failure between Write 1 and Write 2 leaves:
- Archive: contains the overflow items (Write 1 succeeded).
- Source: still at N items (Write 2 did not complete — `write_atomic`'s temp-file-rename
  failure leaves the original intact per its contract).

On the NEXT dispatch, the item-count trigger re-fires (source is unchanged at N items) and
`rotate_changelog_at` is called again with the SAME `move_items`. Without crash-recovery
logic, it appends the overflow items to the archive a SECOND time — producing DUPLICATES in
an archive that must never contain them (VP-112, BC-1.18.009 Inv-6).

### Failure History (Hard-Won — Do Not Repeat)

#### Attempted Option A: Pure Byte-Level Tail-Match Dedup (ADR-051 v1.12 Draft Option-a) — INTERNALLY UNIMPLEMENTABLE

The naive approach: before appending to the archive, check whether `move_items` are already
present at the archive's tail (byte-level comparison, normalized for trailing `\n`); if yes,
skip the archive write and proceed only with the source trim.

**Why it is unsound:** The tail-match check cannot distinguish two structurally identical
scenarios that require opposite actions:
- **Crash-retry** (archive has `move_items`, source still has N items): must SKIP archive
  append, proceed with source trim → CORRECT action: skip-archive, do-source-trim.
- **Legitimate second rotation with coincident overflow items** (prior rotation was CLEAN —
  archive has `move_items` from R1, source was successfully trimmed after R1, but R2 happens
  to move items with the SAME byte content as R1's overflow): must APPEND to archive (this is
  a new, distinct rotation event), proceed with source trim → CORRECT action: do-archive,
  do-source-trim.

In both scenarios, `move_items` equals the archive tail EXACTLY. A byte-level tail-match
check returns the same verdict for both — it structurally cannot differentiate them. The
check would silently swallow the archive write for legitimate rotation R2 whenever R2's
overflow items happen to be byte-identical to R1's, causing a permanent history gap.

This design was withdrawn from the spec before being shipped to production. It is NOT a
valid implementation path. Do not resurrect it.

#### Attempted Option B: Sentinel Sidecar File (`.{archive}.written`) — BROKEN (F-C4H-P1-001, F-C4H-P1-004)

A sentinel file (`.BC-INDEX-changelog-archive.md.written`) was written atomically after a
successful archive append. On a subsequent dispatch with the trigger firing, the presence of
the sentinel was treated as evidence of a crash-recovery scenario.

**Why it is broken (adv re-cascade pass-1 finding F-C4H-P1-001, CRITICAL):** The sentinel
file is written ONCE and NEVER RESET. After rotation R1 completes cleanly (archive write +
source trim both succeed), the sentinel persists. When rotation R2 triggers:
- R2 checks the sentinel → present (leftover from R1's clean rotation).
- R2 incorrectly concludes crash-recovery → skips its archive write, proceeds with source trim.
- R2's overflow items are NEVER appended to the archive — permanent history gap for all
  rotations after the first.

The sentinel mechanism only correctly handles a crash on the FIRST-EVER rotation. All
subsequent rotations treat the persistent sentinel as a false crash-recovery signal, silently
swallowing their archive writes.

**Additional defects (adv re-cascade pass-1 findings F-C4H-P1-002, F-C4H-P1-003, F-C4H-P1-004):**
- F-C4H-P1-002: The sentinel file was unspecced — no BC clause or invariant governed it,
  making it invisible to the adversarial review process and to the test-writer.
- F-C4H-P1-003: The sentinel was written as a dotfile directly into
  `.factory/specs/behavioral-contracts/`, an unregistered path under the artifact-path-registry.
  This violates the artifact-path-registry governance discipline and would trigger
  `validate-factory-path-staging` if committed on a product branch.
- F-C4H-P1-004: If the sentinel write itself fails (e.g., permissions error after the archive
  write succeeds), the implementation returned `E-SHD-004` (`rotate_changelog invocation
  failure`) — a false-positive that aborts the entire dispatch with the wrong error code for
  what is actually a recoverable post-archive-write state.

This option is BROKEN and must not be re-implemented.

### Likely-Sound Direction (Not Prescriptive — Evaluate Before BC Amendment)

The key observation that makes a sound mechanism possible:

> After a crash between Write 1 and Write 2, the overflow items are at BOTH the archive tail
> AND the source (source was not trimmed). In a legitimate second rotation, the overflow items
> from the prior clean rotation are at the archive tail BUT NOT in the source (the prior
> source trim completed).

A **source-vs-archive consistency check** exploits this invariant:

On each invocation of `rotate_changelog_at` when the item-count trigger has fired:
1. Determine `move_items` (the overflow items to be moved — same calculation as today).
2. Check: are `move_items` already present at the archive tail? (byte-level tail-match, same
   as Option A)
3. **Additionally check:** are `move_items` STILL present in the source (i.e., is the source
   NOT yet trimmed)?
4. If BOTH (2) AND (3) are true → crash-recovery scenario → skip archive write, proceed with
   source trim only. `RotationReport { mutated: true, items_moved: len(move_items) }` (source
   WAS mutated; archive write physically skipped but items logically moved).
5. If (2) is true BUT (3) is false → cannot happen in normal operation (source was trimmed
   but archive was also already written — this is a fully-completed prior rotation); treat as
   normal new rotation with coincident items — append to archive.
6. If (2) is false → normal new rotation — append to archive, then trim source.

This check is SOUND because the combined condition (archive-tail-match AND source-still-has-
items) is uniquely true only for the crash-recovery scenario. The coincident-items scenario
(Option A's failure case) requires that (3) be false — the source was already trimmed in the
prior clean rotation — making the combined check correctly distinguish them.

The product-owner MUST evaluate this direction (and any alternatives) and amend BC-1.18.009
Inv-6 with the chosen mechanism before this story is dispatched. The story-writer records
this direction as the working hypothesis, not as a pre-decided implementation.

### VP-125 Reconciliation Requirement

VP-125's proptest for the no-history-loss invariant currently uses test fixtures with
**byte-identical items per rotation** — a test artifact that masked the design flaw: the
tail-match check (Option A) would "work" for byte-identical items because it never encounters
the coincident-items scenario that breaks it.

VP-125's proptest MUST be updated to use DISTINCT items per rotation (each rotation's overflow
items must differ in content from all prior rotations' overflow items). This is the realistic
operating condition: real `changelog:` entries differ from one another (they contain different
dates, author names, summaries). The byte-identical-items fixture was a property-testing
shortcut that produced misleading coverage. The no-history-loss invariant must hold for ALL
item sequences, including those where different rotations produce different items — which is
the TYPICAL case, not a special case.

## Acceptance Criteria

### AC-001: Sound crash-recovery mechanism distinguishes crash-retry from legitimate second rotation (traces to BC-1.18.009 invariant 6)

The replacement mechanism for `rotate_changelog_at`'s crash-recovery logic correctly
identifies the crash-retry scenario (archive-tail-match AND source-still-has-overflow-items)
and the legitimate-new-rotation scenario (archive-tail-match but source-already-trimmed) and
takes the CORRECT action in each case:
- Crash-retry: skip archive write, complete source trim → archive unchanged, source trimmed.
- Legitimate new rotation with coincident items: append to archive, then trim source → archive
  grows by `len(move_items)` (accumulates new items), source trimmed.

Implemented in `crates/last-amended-migrate/src/rotate.rs`. The mechanism is governed by
BC-1.18.009 Inv-6 (as amended by product-owner before dispatch).

### AC-002: Multi-rotation crash test vector — no duplicates across two rotation crash points (traces to BC-1.18.009 invariant 6, postcondition 5)

A crash-recovery unit test exercises the following sequence:
1. Rotation R1: overflow items `[I-A, I-B]` — Write 1 (archive) succeeds, Write 2 (source)
   crashes. Archive contains `[I-A, I-B]` once. Source still has N items.
2. Recovery from R1's crash: next dispatch re-fires trigger; `rotate_changelog_at` detects
   crash-recovery; skips archive write; completes source trim. Archive still contains
   `[I-A, I-B]` exactly once (no duplicate). Source trimmed to `low_water_mark`.
3. Rotation R2: overflow items `[I-C, I-D]` (DISTINCT from R1's items) — Write 1 crashes.
   Archive now contains `[I-A, I-B, I-C, I-D]` (new items appended once). Source at N items
   again.
4. Recovery from R2's crash: next dispatch; `rotate_changelog_at` detects crash-recovery for
   R2; skips archive write for `[I-C, I-D]`; completes source trim. Archive still
   `[I-A, I-B, I-C, I-D]` — each item once, no duplicates. `RotationReport.mutated == true`.

The test lives in `crates/last-amended-migrate/tests/` and covers the two-rotation crash
scenario absent from prior coverage (the gap that masked F-C4H-P1-001).

### AC-003: VP-112 crash-recovery fixture passes with the new mechanism (traces to BC-1.18.009 invariant 6, postcondition 5)

VP-112's unit test (`bc_10_13_001_pc5_rotation_test.rs` crash-recovery fixture, introduced
in BC-1.18.009 v1.6 cluster-4 hardening) passes with the REPLACEMENT mechanism. The test
must not rely on Option A (pure tail-match without source check) or Option B (sentinel file)
internals — it must pass by verifying the OBSERVABLE outcome only: archive contains overflow
items exactly once after a crash-and-retry cycle. If the test was written against the
sentinel mechanism (Option B), it is updated in this story to be mechanism-agnostic.

### AC-004: VP-125 proptest uses DISTINCT items per rotation; no-history-loss invariant holds for realistic sequences (traces to BC-1.18.009 postcondition 5, invariant 2)

VP-125's proptest generators are updated so that distinct rotations produce distinct overflow
items (e.g., via a per-rotation counter or random UUID suffix injected into each item's
simulated date/summary fields). The proptest demonstrates:
- `len(changelog) <= N` after every operation (bounded-live-sequence facet).
- The post-rotation trim floor equals the configured `low_water_mark`, not `N-1`.
- Total recoverable items (archive + live) equals total prepend count (no-history-loss facet)
  for multi-rotation sequences where items differ between rotations — the case that exposed
  Option A's blind spot.

The byte-identical-items fixture is removed or explicitly annotated as a narrow corner-case
test, not as coverage for the general case.

### AC-005: `rotate_changelog_at` passes existing VP-125/VP-126/VP-131 regression suite with no new failures (traces to BC-1.18.009 postconditions 1, 2, invariants 1, 4, 5)

All existing VP-125 (bounded live sequence + no-history-loss), VP-126 (no-reimplementation,
no gate-side-prepend, guard-arm-presence facet), and VP-131 (two-facet fail-loud: Err-arm
`E-SHD-004` + Ok-arm `E-SHD-014`) tests continue to pass. The crash-atomicity fix is ADDITIVE
to the existing mechanism — it does not alter the item-count trigger logic, the block-and-retry
contract, the `E-SHD-014` counter-divergence guard (Inv-5), or the `E-SHD-004` error path.

## Previous Story Intelligence

**From S-25.02 cluster-4 hardening (the predecessor whose Obs-B attempt is being reverted):**

- The two-write ordering (archive-first, source-second) is CORRECT and LOAD-BEARING — it was
  established in ADR-051 §Decision 11 and matches mechanism A's `E-SHD-006` self-healing
  philosophy: a crash after Write 1 leaves the source intact (no data loss), and the archive
  is the authoritative record. Reversing to source-first would cause data loss if the archive
  write then failed. Do NOT change the write ordering.
- `RotationReport.mutated` was given its "first load-bearing use" in cluster-4 hardening for
  the EC-008/Inv-5 counter-divergence guard. The crash-recovery mechanism will give it a
  second load-bearing use: `mutated: true` when the source was rewritten (even if the archive
  write was skipped in crash-recovery). Keep this semantics clear in the implementation and
  the test.
- The byte-identical-items proptest fixture was the SPECIFIC gap that allowed Option A's flaw
  and Option B's regression to hide in VP-125 coverage. Fixing VP-125 first (T-3) before
  implementing T-4 is the correct TDD sequence — run proptest RED with the wrong mechanism,
  GREEN with the correct one.
- `write_atomic` in `rotate.rs` uses temp-file-rename semantics — a failed rename leaves the
  original file intact (no partial write). The crash-recovery logic RELIES on this: it infers
  "Write 2 crashed" precisely because the source is still at N items. Do not change
  `write_atomic`'s semantics as a side-effect of this story.
- Error code `E-SHD-014` is already allocated (counter-divergence guard). No new error code
  is introduced by this story's crash-recovery mechanism — a detected crash-recovery is a
  successful RECOVERY path, not an error path.

## Architecture Compliance Rules

Extracted from `architecture/module-decomposition.md`, `architecture/dependency-graph.md`,
and ADR-051/ADR-049:

1. **`last-amended-migrate` has no dependency back on `factory-dispatcher`** — the
   dependency is one-directional: `factory-dispatcher → last-amended-migrate`. The
   crash-recovery fix lives entirely within `last-amended-migrate`. Do not introduce any
   import of `factory-dispatcher` types or functions into `last-amended-migrate`.

2. **`rotate_changelog_at` is the only caller-facing function for the rotation primitive.**
   The `rewrite_source_after_rotation` function is `fn` (private). The crash-recovery logic
   is implemented INSIDE `rotate_changelog_at` / `rewrite_source_after_rotation` — not as
   a new caller-facing function. Callers (including `shard_manager.rs`) do NOT need to
   opt into crash-recovery; it is transparent.

3. **`write_atomic` semantics are load-bearing and must not be changed.** The crash-recovery
   mechanism infers crash state from file existence + content (source still at N items). Any
   change to `write_atomic`'s temp-rename semantics would invalidate this inference.
   Flag any `write_atomic` changes for explicit architect review before proceeding.

4. **No new dotfiles in `.factory/specs/behavioral-contracts/` or any `.factory/` spec
   subdirectory.** The failed Option B produced an unregistered dotfile in the specs dir. Any
   crash-recovery state that must persist across invocations MUST be registered in
   `plugins/vsdd-factory/config/artifact-path-registry.yaml` and authorized by the architect
   before implementation. The source-vs-archive consistency check approach (the sound
   direction) requires NO state file — it reads from files that already exist — making this
   constraint trivially satisfiable.

5. **No new error codes without taxonomy registration.** `E-SHD-014` is the highest allocated
   code as of `error-taxonomy.md` v1.14. If the implementation needs a new error for the
   crash-recovery path (e.g., "source-check IO failure"), it MUST be added to
   `prd-supplements/error-taxonomy.md` and routed through the product-owner, not invented
   inline. The current analysis (EC-006) suggests `E-SHD-004` covers the failure case — verify
   against the taxonomy before allocating.
