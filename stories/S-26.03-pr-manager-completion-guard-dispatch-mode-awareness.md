# S-26.03: `pr-manager-completion-guard` Dispatch-Mode Awareness + Stop-Loop Fix

## Narrative
- **As a** `pr-manager` agent dispatched for a SPECIFIC lifecycle mode (merge-only,
  create-only, or full 9-step new-PR lifecycle)
- **I want to** `pr-manager-completion-guard`'s `SubagentStop` check to respect that
  mode, never assert an `AUTHORIZE_MERGE` I was not given, and evaluate my own
  `STEP_COMPLETE`/handback output before re-blocking me
- **So that** I am never forced through the full 9-step lifecycle on a merge-only or
  create-only dispatch, never told to merge when my dispatch explicitly said not to,
  and never stop-looped through repeated identical blocks that ignore what I already
  reported as done

## Problem Statement (GH issue #838, P1, AXIS-2 current-source defect)

`pr-manager-completion-guard` (`crates/hook-plugins/pr-manager-completion-guard/`,
`SubagentStop`; native-ported from bash under S-8.02, BC-7.03.045/046/047/048) was
observed with three distinct failure modes in one dispatch:

1. **False `AUTHORIZE_MERGE=yes` injection.** The guard injected merge authorization
   language into its feedback even when the ORIGINATING dispatch explicitly instructed
   the agent NOT to merge — a safety concern, since a later step or a human skimming
   the transcript could mistake this for a genuine authorization signal.
2. **Stop-loop / re-block without evaluating agent output.** The guard re-blocked the
   agent identically on repeated `Stop` attempts without parsing the agent's own prior
   `STEP_COMPLETE` marker or handback message to check whether the reported
   incompleteness was still accurate. One observed case took 4 identical-looking
   blocks before the agent had to be killed externally.
3. **9-step lifecycle forced onto narrower dispatch modes.** The guard's completion
   checklist assumes every dispatch is a full new-PR creation-through-merge lifecycle,
   even when the dispatch was scoped to "merge this already-reviewed PR" or "create
   this PR only, do not proceed further."

## Required BC Amendment (product-owner routing — NOT authored by this story)

BC-7.03.045/046/047/048 (the `pr-manager-completion-guard` behavioral contract set)
need a coordinated amendment, to be authored by product-owner in consultation with
architect and the `pr-manager` agent's own dispatch-contract owner:

1. **Dispatch-mode taxonomy.** Define an explicit, machine-checkable dispatch-mode
   signal (e.g., a `dispatch_mode: merge-only | create-only | full-lifecycle` field
   the orchestrator sets when dispatching `pr-manager`) that the guard reads and
   branches its completion checklist on, instead of assuming full-lifecycle
   unconditionally.
2. **`AUTHORIZE_MERGE` non-fabrication invariant.** State explicitly that the guard
   MUST NEVER inject `AUTHORIZE_MERGE=yes` (or equivalent) language that was not
   present in, or derivable from, the actual originating dispatch instructions.
3. **Stop-loop prevention via prior-output parsing.** Require the guard to parse the
   agent's own `STEP_COMPLETE`/handback message from the current `Stop` transcript
   before deciding whether to re-block, and define what "still incomplete" means in a
   way that is checkable against that parsed output (not merely "re-run the same
   static checklist regardless of what the agent already reported").

## Acceptance Criteria (DRAFT — pending BC-7.03.04x amendment; NOT yet BC-traced)

### AC-001 (BC trace: pending BC-7.03.045/046/047/048 amendment)
- A `pr-manager` dispatch explicitly marked `dispatch_mode: merge-only` (or
  equivalent) is checked against a merge-only-scoped completion checklist, never the
  full 9-step new-PR lifecycle checklist.
- **Test:** `test_BC_7_03_04x_merge_only_mode_scoped_checklist()`

### AC-002 (BC trace: pending BC-7.03.045/046/047/048 amendment)
- A dispatch whose originating instructions explicitly say NOT to merge NEVER results
  in the guard's feedback containing `AUTHORIZE_MERGE=yes` or any equivalent
  authorization-implying language.
- **Test:** `test_BC_7_03_04x_no_fabricated_authorize_merge_regression()`

### AC-003 (BC trace: pending BC-7.03.045/046/047/048 amendment)
- Reproduces GH issue #838's stop-loop as a regression test: given an agent `Stop`
  transcript containing a `STEP_COMPLETE` marker reporting a specific step done, the
  guard's re-block decision reflects that reported state (i.e., does not re-issue an
  identical block demanding a step the agent just reported complete, without at least
  re-verifying that specific claim).
- **Test:** `test_BC_7_03_04x_stop_loop_prior_output_parsed_regression()`

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-001 | Dispatch has no `dispatch_mode` field at all (legacy/未-migrated dispatch) | Amendment must specify a safe default — story-writer flags "default to full-lifecycle, the current behavior, for unmarked dispatches" as the likely-correct default, for PO to confirm |
| EC-002 | Agent's `Stop` transcript contains a `STEP_COMPLETE` marker for the WRONG step (agent error, not guard error) | Guard should still be able to re-block correctly — this story's fix is about the guard READING prior output, not about trusting it uncritically; a malformed/incorrect self-report must not create a NEW bypass |
| EC-003 | `dispatch_mode: create-only` agent's PR is created but the agent's own output claims a merge also happened | Guard must detect this mismatch as a genuine incompleteness/inconsistency (create-only mode does not authorize a merge having occurred) — not silently accept it |
