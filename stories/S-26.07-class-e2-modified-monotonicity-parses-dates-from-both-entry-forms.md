# S-26.07: Class E2 `modified[]` monotonicity parses dates regardless of entry form

**Epic:** E-26 - Post-rc.25 Hook Hardening
**Depends on:** (none)
**Blocks:** (none)
**Priority:** P2
**Closes issue:** none (found in live operation, D-1261)

## Narrative

- **As a** factory operator editing epic, story, BC and VP files whose `modified[]` frontmatter uses version-first entries (`v1.10 2026-10-13: ...`) from the tenth revision onward
- **I want** the Class E2 monotonicity check to read the ISO date out of the entry whichever form it takes, to order same-day entries by numeric version, and to treat an entry it cannot read as a reported non-subject rather than as a string to sort
- **So that** `v1.9` followed by `v1.10` is never reported as a date decrease, a genuine date decrease is still reported in either form, and the E2 arm stops emitting false positives on every epic that has reached a two-digit revision

## Problem Statement (D-1261, reproduced live on E-25)

`run_arm_e2` in `crates/hook-plugins/validate-cross-site-correspondence/src/arm_e.rs` maps each `modified[]` entry through `strip_date_annotation` (everything before the first space or tab) and then compares the resulting strings with `<`.

- Date-first entry `2026-10-13 (v1.16)` strips to `2026-10-13`: lexicographic order equals date order. Correct.
- Version-first entry `v1.10 2026-10-13: ...` strips to `v1.10`; `v1.9 2026-10-13: ...` strips to `v1.9`. Lexicographically `v1.10` < `v1.9` (the character `1` sorts before `9`), so a perfectly ordered sequence is reported as a date decrease: a FALSE non-monotonic. The E-25 epic's `modified[]` (`v1.0` .. `v1.11`) triggers it from the v1.10 entry onward.
- A version-first entry compared with a date-first entry (`v1.4 ...` against `2026-10-13 ...`) is compared as `v1.4` against `2026-10-13`: arbitrary.
- The failure is invisible when the versions happen to sort the same way as the dates, so it surfaces only at the tenth revision of an artifact.

The arm is advisory-only in effect today: the hook is PostToolUse (BC-5.39.010 invariant 2), the write has already landed, and the block signal pollutes telemetry rather than reverting anything. That does not make a false positive acceptable; a gate that cries wolf on E-25 teaches operators to ignore it, and the same defect hides genuine decreases behind noise.

A second, smaller defect sits in the same function: its violation text ("modified[] sequence is non-monotonic - '<curr>' is earlier than preceding '<prev>'") does not conform to the postcondition 22 wording ("modified[] date-decrease at index <i>: ... Update modified[] per POLICY 14 leg 3"). Per the standing rule (the spec wins over the code) the text is brought into line in this story.

## Required BC Amendment (product-owner routing - NOT authored by this story)

BC-5.39.010 precondition 38 reads "strip annotation suffixes (e.g., ` (v1.3)`); compare date strings lexicographically", postcondition 21 / 22 define the relation over "date[i]" after "suffix-strip", and EC-016 / EC-030 / EC-031 and the test-vector table use date-first entries only. ## Acceptance Criteria

> Each AC names a falsifiable Rust test (unit tests in `crates/hook-plugins/validate-cross-site-correspondence/src/arm_e.rs`'s test module, matching the crate's existing `test_BC_5_39_010_class_e2_*` naming) unless it says otherwise. "Entry" means one element of the `modified:` YAML sequence as returned by `extract_frontmatter_sequence`. "Stamp" means the parsed pair (date, optional version tuple).

### AC-001 (the ISO date is extracted from either entry form; traces to BC-5.39.010 precondition 38 (`modified:` extraction; the compared quantity is the date); the version-first form is NOT in the BC - GAP-S2607-001)
A pure function `parse_modified_entry(entry: &str) -> Option<ModifiedStamp>` (hand-rolled byte walk, no `regex` crate, UTF-8 safe slicing per BC-5.39.010 invariant 9) returns the entry's date and optional version for exactly two positional forms, both anchored at character position 0 (the same anchoring discipline as precondition 37):
1. **Date-first:** `YYYY-MM-DD` at position 0, followed by end-of-string, whitespace, or one of `:` `,` `;`; then optionally (after whitespace) a version token, bare (`v1.3`) or parenthesised (`(v1.3)`). Examples: `2026-05-14`, `2026-05-18 (v1.1)`, `2026-05-20 v1.3: Added Class E2`, `2026-07-18 (v1.1): Active [Prior: 2026-07-01 (v1.0) - first]` (only the leading date and version are read; the text after them, including any `[Prior: ...]` chain, is never parsed).
2. **Version-first:** a version token `v<digits>(.<digits>)*` at position 0, one or more spaces or tabs, then `YYYY-MM-DD` followed by end-of-string, whitespace, or `:` `,` `;`. Example: `v1.10 2026-10-13: D-1257 cite propagation (story-writer; ...)`.
The date is valid when the month is `01`-`12` and the day `01`-`31` (a range check, not a calendar check: month lengths and leap years are NOT evaluated, fuel-bounded). The version, when present, is parsed to a `Vec<u64>` of its dot-separated components; a component that overflows `u64` makes the entry's version ABSENT (never a panic, never a wrapped value) while the date is still read. The comparison in AC-002 and the relation in AC-004 use the date, never the raw string.
- **Test:** `test_BC_5_39_010_class_e2_parse_date_first_forms()` (plain date, parenthesised version, bare version with colon, the `[Prior: ...]` chain entry), `..._parse_version_first_form_extracts_date_and_version()`, `..._parse_rejects_calendar_out_of_range_month_and_day()`, `..._parse_reads_only_the_leading_date_never_a_prior_chain_date()` and `..._parse_overflowing_version_component_yields_no_version_but_keeps_the_date()`.

### AC-002 (equal dates are ordered by numeric version; traces to BC-5.39.010 precondition 38 equal-date sentence and postcondition 21 (non-decreasing, equal dates permitted); the tie-break itself is NOT in the BC - GAP-S2607-002)
For two consecutive parseable entries whose dates are EQUAL: if BOTH carry a version, the pair is a violation iff the first entry's version tuple is numerically GREATER than the second's (component-wise, missing trailing components read as 0, so `v1.2` equals `v1.2.0`); equal versions and ascending versions pass. `v1.9` then `v1.10` on one day PASSES (9 < 10); `v1.10` then `v1.9` on one day is a violation. If EITHER entry carries no version the equal-date pair PASSES (preserving EC-030: `["2026-07-30", "2026-07-30 (v1.1)"]` is the BC's own authoring pattern). A pair whose dates DIFFER is decided by the dates alone: the version is never consulted (a lower version on a LATER date is normal, and a higher version on an EARLIER date is a date decrease already caught).
- **Test:** `test_BC_5_39_010_class_e2_equal_dates_v1_9_then_v1_10_passes()`, `..._equal_dates_v1_10_then_v1_9_blocks()`, `..._equal_dates_one_entry_without_version_passes()` (the EC-030 vector), `..._equal_dates_equal_versions_pass()`, `..._version_tuple_compare_pads_missing_components_with_zero()` and `..._differing_dates_ignore_versions()`.

### AC-003 (an entry that yields no date takes the hook's closed non-blocking behavior; traces to BC-5.39.010 precondition 37 last sentence (unparseable format: `host::log_warn` advisory + `HookResult::Continue`, "do NOT block on unparseable format") as the nearest closed behavior in Part E, and precondition 39 (HostError on the primary target stays fail-closed, unchanged); the clause for a `modified[]` entry is NOT in the BC - GAP-S2607-003)
An entry for which `parse_modified_entry` returns `None` (no date at position 0 in either form, an out-of-range date, an empty string, a non-string-shaped item) is NOT a comparison subject: it is skipped, ONE advisory per such entry is emitted through the `Advisory` channel (message names the zero-based index in the ORIGINAL `modified[]` array and the first 40 characters of the entry, escaped, and the form it expected), and the E2 check proceeds over the remaining parseable entries, comparing each parseable entry with the PRECEDING PARSEABLE entry. An unparseable entry therefore neither blocks on its own nor masks a genuine decrease between its parseable neighbours. `run_arm_e2` returns `(Vec<Violation>, Vec<Advisory>)` (the shape `run_arm_e1` already has); the single call-site in `lib.rs` extends the advisories before `emit_advisories`. This is NOT a new fail-closed or fail-open decision invented here: it is the precondition-37 behavior applied to the `modified[]` entry the same way, pending GAP-S2607-003.
- **Test:** `test_BC_5_39_010_class_e2_unparseable_entry_is_skipped_with_one_advisory_naming_its_original_index()`, `..._unparseable_entry_does_not_mask_a_decrease_between_its_neighbours()` (`["2026-10-13 (v1.1)", "garbage", "2026-10-12"]` still blocks), `..._all_entries_unparseable_continues_with_advisories_only()`, `..._advisory_text_is_escaped_and_capped_at_40_characters()` and `..._single_entry_sequence_skips_e2_as_before()` in `src/arm_e.rs`; `test_BC_5_39_010_lib_extends_advisories_from_run_arm_e2()` in the crate's `lib.rs` test module (the sibling-site sweep for the changed return type).

### AC-004 (regression vectors; traces to BC-5.39.010 postconditions 21 and 22, EC-016, EC-030, EC-031)
The four vectors the defect record names, each as its own test, written FIRST and failing against the unchanged function where the defect applies:
1. **v1.9 -> v1.10:** `["v1.8 2026-10-12: a", "v1.9 2026-10-13: b", "v1.10 2026-10-13: c"]` and `["v1.9 2026-10-12: a", "v1.10 2026-10-13: b"]` PASS (today: FALSE block, `v1.10` < `v1.9`).
2. **Mixed forms:** `["2026-10-12 (v1.8)", "v1.9 2026-10-13: x", "2026-10-13 (v1.10)"]` PASSES (a date-first, a version-first and a date-first entry in one sequence; the equal-date pair is ordered by version 9 < 10).
3. **Equal dates:** `["2026-07-30", "2026-07-30 (v1.1)"]` PASSES (EC-030) and `["v1.2 2026-10-13: a", "v1.2 2026-10-13: b"]` PASSES.
4. **Genuinely non-monotonic pair, still blocks, in each form:** `["2026-05-18", "2026-05-14"]` (EC-031 shape), `["v1.10 2026-10-13: a", "v1.11 2026-10-12: b"]` (version-first; the LATER-numbered version carries the EARLIER date) and the mixed `["v1.10 2026-10-13: a", "2026-10-12 (v1.11)"]` each produce exactly one `[Class E2]` violation; the pre-existing `["2026-05-14", "2026-05-18 (v1.1)", "2026-05-15"]` (EC-016) still blocks.

### AC-005 (the first strict decrease reports once, by pair, in the original index space; traces to BC-5.39.010 postcondition 22 ("first pair where date[i] > date[i+1]") and postcondition 23 (combined E1 + E2 enumeration))
