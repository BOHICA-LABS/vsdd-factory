# S-12.14: Cargo Audit Cache — Canonicalize CWD-Relative Producer Path + Validate Consumer Read Location

**Epic:** E-12 — Engine Governance
**Priority:** P2
**Status:** draft (BC authorship required before dispatch)
**Origin:** D-1207 (Drift Item — previously mis-scoped as "harmless"; this story re-scopes
as a defect requiring root-cause investigation and fix)

## Context / Defect History

`plugins/vsdd-factory/hooks/update-cargo-audit-cache.sh` is a bash data provisioner for the
cargo-audit advisory check. Per ADR-021 Option b, the bash script runs `cargo audit --json` and
writes the output to a cache file; a downstream WASM hook reads the cache via
`host::read_file` rather than shelling out directly (fuel-safety).

**The defect (line 7 of the script):**

```bash
OUTPUT_FILE=".factory/hooks/cargo-audit-cache.json"
```

This is a CWD-relative path. The script uses `mkdir -p "$(dirname "$OUTPUT_FILE")"` to create
the parent directory, then writes the file. If the script is invoked from:

- **Repo root (`/repo/`):** Produces `/repo/.factory/hooks/cargo-audit-cache.json` (correct).
- **`.factory/` worktree cwd (`/repo/.factory/`):** Produces
  `/repo/.factory/.factory/hooks/cargo-audit-cache.json` (WRONG — a doubly-nested path that
  does not match the correct location).

The factory runs with a `.factory/` worktree mounted as a separate working directory
(`factory-artifacts` branch). Hooks and provisioner scripts invoked from a `.factory/` cwd
will produce the doubly-nested path. This is the "untracked-files anomaly" logged in D-1207:
an untracked `.factory/.factory/` directory appeared in the repo without anyone understanding
why.

**D-1207 classification was incorrect.** D-1207 logged this as "harmless — just add an ignore
pattern." That classification was made WITHOUT verifying where the WASM hook consumer reads.
If the consumer's `host::read_file` call resolves the cache path relative to the repo root, it
reads from `/repo/.factory/hooks/cargo-audit-cache.json`. If the producer was invoked from a
`.factory/` cwd, the cache landed at `/repo/.factory/.factory/hooks/cargo-audit-cache.json`.
The consumer silently reads STALE DATA (or a missing file) — a silent audit bypass, not a
"harmless" path artifact.

**This is CWE-706 (Use of Incorrectly-Resolved Name or Reference) at minimum, and potentially
CWE-754 (Improper Check for Exceptional Conditions) if a missing cache file is treated as
"no advisories found" by the consumer.**

## Narrative

- **As a** factory operator who depends on `cargo audit` advisory checks running correctly as
  part of the pre-commit hook chain
- **I want** `update-cargo-audit-cache.sh` to resolve the output path relative to the
  repository root unconditionally (regardless of the cwd from which the script is invoked),
  and the WASM consumer hook to read from the same canonical absolute path
- **So that** the audit cache ALWAYS lands where the consumer expects it, the
  `.factory/.factory/` untracked-file anomaly (D-1207) is eliminated at the source rather
  than papered over with an ignore pattern, and the cargo audit advisory gate cannot be
  silently bypassed due to a CWD-dependent path mismatch

### AC-001 (traces to BC-TBD postcondition 1 — producer path resolution)

`update-cargo-audit-cache.sh` resolves `OUTPUT_FILE` to an absolute path anchored at the
repository root, regardless of the cwd from which the script is invoked. The canonical
resolution method uses `git rev-parse --show-toplevel` (or an equivalent portable mechanism)
to determine the repo root, then constructs the absolute path as
`"$(git rev-parse --show-toplevel)/.factory/hooks/cargo-audit-cache.json"`.

Verified by a bats test that:
1. Invokes the script with cwd set to the repo root — confirms the cache file is written to
   the expected absolute path.
2. Invokes the script with cwd set to `.factory/` — confirms the cache file is STILL written
   to the same absolute path (not a doubly-nested `.factory/.factory/` path).
3. After both invocations, confirms no `.factory/.factory/` directory exists in the
   working tree.

### AC-002 (traces to BC-TBD postcondition 2 — consumer read-path verification)

Before any code change is made to the producer script, the implementation MUST first:
1. Read the WASM hook(s) in `hooks-registry.toml` that consume `cargo-audit-cache.json`
   (identified by `host::read_file` calls or equivalent).
2. Determine the exact path those consumers resolve for the cache file (relative to repo
   root, relative to cwd at dispatch time, or absolute).
3. Confirm that after the producer path fix (AC-001), the consumer reads from the same
   absolute path the producer writes to.
4. If the consumer uses a different path resolution, fix BOTH the producer AND the consumer
   in the same PR so they are in sync.

This AC prevents the fix from swapping a CWD-relative producer path for a different
mismatch between producer and consumer. The test vehicle: a bats integration test that
exercises the full provisioner → consumer path by verifying the consumer's resolved read
path matches the producer's resolved write path under both invocation CWDs.

### AC-003 (traces to BC-TBD postcondition 3 — D-1207 anomaly eliminated)

After the fix is merged:
- `git status` in the `.factory/` worktree shows no untracked `.factory/` subdirectory
  (the doubly-nested path anomaly is gone).
- The cargo-audit advisory hook reports the same advisory count when invoked from repo root
  cwd as when invoked from `.factory/` cwd (no data divergence between invocation contexts).
- A CHANGELOG entry documents the fix and references D-1207.
