# S-25.01: Dispatcher INDETERMINATE Outcome Layer 1 — Fail-Loud on Cannot-Complete: Durable Marker + Next-Advance Gate

## Narrative

- **As a** factory pipeline operator whose validators run in fuel-bounded and epoch-bounded WASM
  sandboxes
- **I want** the dispatcher to make "couldn't validate" a FIRST-CLASS, fail-LOUD outcome that
  writes a durable `.factory/unvalidated-mutation.marker` file and blocks the next state-advancing
  Agent dispatch and `git commit`/`git push` Bash dispatch until the affected artifact is
  re-validated or an operator explicitly clears the marker

  `validate-pr-merge-prerequisites` and `validate-wave-gate-prerequisite` once S-21.24 activates

## Acceptance Criteria

### BC-1.18.001 — INDETERMINATE Outcome Classification, plugin.indeterminate Event, Durable Marker

**AC-001** (traces to BC-1.18.001 postcondition 1 — fuel cause)

When a fail-closed plugin's WASM execution traps and `trap.downcast_ref::<Trap>()` yields
`Some(Trap::OutOfFuel)`, the dispatcher classifies the outcome as `DispatchOutcome::Indeterminate`
with `cause = "fuel"`. `get_fuel()` is NOT the authoritative check — only the Trap downcast is.

**AC-002** (traces to BC-1.18.001 postcondition 1 — epoch timeout cause)

When a fail-closed plugin's WASM execution traps and `trap.downcast_ref::<Trap>()` yields
`Some(Trap::Interrupt)`, the dispatcher classifies the outcome as `DispatchOutcome::Indeterminate`
with `cause = "epoch"`.

**AC-003** (traces to BC-1.18.001 postcondition 1 + invariant 1 — OutputTooLarge cause with
per-invocation Store flag reset)

When any host function returns `OutputTooLarge(-3)` to the plugin WASM during execution (setting
`StoreData::host_output_too_large_seen = true`), AND the plugin subsequently completes with
`exit_code = 0`, AND `failure_policy = fail-closed`, the outcome MUST be
`DispatchOutcome::Indeterminate` with `cause = "output-too-large"`. The `host_output_too_large_seen`
flag MUST be reset to `false` immediately before each WASM module invocation (not only at `Store`
creation) — this is a correctness invariant (per-invocation reset, not per-Store creation reset).

**AC-004** (traces to BC-1.18.001 postcondition 2 + postcondition 5 + invariant 2 — outcome trichotomy; non-exhaustive Trap wildcard)

`DispatchOutcome::Indeterminate` is a distinct variant from `DispatchOutcome::Pass` and
`DispatchOutcome::Fail`. PASS requires `exit_code = 0` AND `host_output_too_large_seen = false`.
FAIL requires non-zero `exit_code`. INDETERMINATE covers the remaining gap. Existing PASS/FAIL
semantics for `PluginResult::Ok`, `PluginResult::Crash`, and normal `PluginResult::Timeout`
variants are UNCHANGED (backward-compat anchor). The Trap match arm in `classify_outcome`
MUST include a wildcard arm `_ => { /* not INDETERMINATE; route to existing on_error handling */ }`
— `Trap` is `#[non_exhaustive]`; a future unrecognized Trap variant MUST NOT be silently bucketed
as INDETERMINATE (BC-1.18.001 invariant 2).

**AC-005** (traces to BC-1.18.001 postcondition 4 + invariant 3 + invariant 4 — atomic marker write; single-marker policy; PostToolUse-only)

When `failure_policy = fail-closed` AND hook type is `PostToolUse` AND outcome is `Indeterminate`,
the dispatcher atomically writes `.factory/unvalidated-mutation.marker` via write-to-temp + rename
(`O_CREAT | O_WRONLY | O_TRUNC` then `rename`). The marker file MUST contain all six required
TOML fields: `timestamp` (RFC 3339), `plugin_name` (string), `artifact_path` (string, empty
string when no artifact context — never omit the field), `cause` (one of `"fuel"`, `"epoch"`,
`"output-too-large"`), `trace_id` (string), `expires_at` (RFC 3339 UTC timestamp = `timestamp
+ UNVALIDATED_MUTATION_MARKER_TTL_SECONDS`; written by `write_indeterminate_marker` at creation;
`UNVALIDATED_MUTATION_MARKER_TTL_SECONDS = 86_400`; enables dispatcher-native TTL auto-clear
(`check_and_clear_expired_marker`) per BC-1.18.003 PC4 and dispatcher native block_if_marker TTL
check per BC-1.18.002 PC5/PC6; BC-1.18.001 PC4 v1.2; ADR-048 §Decision 2). Single-marker policy: a second INDETERMINATE event
overwrites (last-writer-wins). The marker write is PostToolUse only.

**AC-006** (traces to BC-1.18.001 postcondition 3; BC-3.08.001 Event 8 — plugin.indeterminate
event)

**Sink-mechanism correction (v1.13 sync to BC-3.08.001 v1.32 / ADR-048 §Decision 4 — human-ratified,
S-25.01 LOCAL adversary pass 3 F-P3-001 MEDIUM resolution — historical provenance, non-load-bearing):**
the dispatcher emits a
`plugin.indeterminate` event via `HostContext::emit_internal` — the SAME dual-sink helper every
other dispatcher-native BC-3.08.001 event uses — for EVERY INDETERMINATE outcome (both fail-closed
and fail-open). `emit_internal` dual-writes: (a) durably, unconditionally, to
`dispatcher-internal-{date}.jsonl` (via `InternalLog`, when `ctx.internal_log` is `Some` — this is
the only sink every default production dispatcher run writes today, independent of
`observability-config.toml`), and (b) onto the `ctx.events` queue, which a future FileSink/Router
(pending S-4.07) or an operator's opt-in `VSDD_SINK_FILE` will drain into an `events-*.jsonl`-shaped
path. This story MUST NOT claim that a literal `events-*.jsonl` file is durably written today — the
`sinks::Router`/`FileSink` apparatus is not yet wired into `main.rs`. The event wire format MUST
include all mandatory fields per BC-3.08.001 Event 8: `type` ("plugin.indeterminate"),
`trace_id`, `session_id`, `plugin_name`, `artifact_path` (empty string when no artifact context),
`cause` (`"fuel"` | `"epoch"` | `"output-too-large"`), `failure_policy` (`"fail-closed"` or
`"fail-open"`), `timestamp`. BC-3.08.001 is the wire-format authority; BC-1.18.001 is the
triggering-condition authority.

### BC-1.18.002 — Next-Advance Gate: Two-Arm Quarantine

**AC-007** (traces to BC-1.18.002 postcondition 1 + invariant 4 — Agent arm block; block message completeness)

When `.factory/unvalidated-mutation.marker` exists AND a `PreToolUse` hook fires for an `^Agent$`
dispatch, the `validate-unvalidated-mutation-marker` WASM plugin returns `exit_code = 2`
(block). The block message MUST contain: the `plugin_name` from the marker, the `artifact_path`
from the marker, the `cause` from the marker, a re-validation instruction (T1 — Edit/Write
re-validate the artifact named in `artifact_path`; the primary, inherently-ungated agent recovery
path per AC-020 — NOT a "re-invoke the named plugin" dispatcher-command phrasing), and the manual
escape hatch instruction (`rm .factory/unvalidated-mutation.marker`, run by the human operator in
their own terminal — T3 per AC-020). The message MUST be machine-parseable (structured fields,
not freeform prose).

**AC-008** (traces to BC-1.18.002 postcondition 2 + invariant 4 — Bash arm block: git commit/push Phase 1/1b/2/3/4 security filter algorithm (v1.3); quoting-in-scope; block message completeness)

When `.factory/unvalidated-mutation.marker` exists AND a `PreToolUse` hook fires for a `^Bash$`
dispatch for which `is_git_commit_or_push(command)` returns `true`, the
`validate-unvalidated-mutation-marker-git` WASM plugin returns `exit_code = 2` (block). The
block message format is identical to AC-007.

`is_git_commit_or_push(command) → bool` is the authoritative production-grade security filter
(BC-1.18.002 PC2 v1.3; ADR-047 §Decision 9). Under-blocking is the dangerous failure mode;
the algorithm is fail-safe on ambiguity:

- **Phase 1 — Compound command splitting.** Split `command` on `&&`, `||`, `;`, `|`, `&`, and
  newline. Trim each segment. Apply Phases 1b–4 to each segment independently; return `true` if
  ANY segment returns `true`.
- **Phase 1b — POSIX quote-aware tokenization.** Before applying Phases 2–4, tokenize each
  segment from Phase 1 using POSIX word-splitting rules via the `shell-words` crate. Quote
  removal and token concatenation occur at this phase — Phases 2–4 operate on the resulting
  token list, not on the raw whitespace-split string. Examples: `git "commit"` → tokens
  `["git", "commit"]`; `git 'push' origin` → tokens `["git", "push", "origin"]`; `g'i't commit`
  → tokens `["git", "commit"]` (POSIX concatenates unquoted `g`, single-quoted `i`, and unquoted
  `t` into the token `git`). Do NOT implement ad-hoc quote-stripping (e.g., `s/["']//g` regex)
  — the `shell-words` crate provides POSIX parser-equivalence, eliminating the parser-differential
  bypass class where ad-hoc stripping could produce different tokenization than the actual shell.
- **Phase 2 — Executable identification by basename.** Strip leading env-var assignment tokens
  (matching `^[A-Za-z_][A-Za-z0-9_]*=`) and the literal `env` token if it is the first token.
  Compute `basename` of the first remaining token (strip all characters up to and including the
  last `/`). If `basename ≠ "git"` (case-sensitive), return `false` for that segment.
- **Phase 3 — Skip global options.** Scan tokens after `git`: `--` ends Phase 3 (next token is
  subcommand); `--flag=value` skips one token; tokens in the **complete recognized arg-taking set**
  (`-C`, `-c`, `--namespace`, `--git-dir`, `--work-tree`, `--super-prefix`, `--config-env`) skip
  that token AND the immediately following token; tokens in the recognized no-arg set are skipped;
  an unrecognized token starting with `-` triggers **fail-safe → return `true` (block)** — arity
  is unknown from the closed recognized set, and under-blocking is the dangerous failure mode.
- **Phase 4 — Subcommand match.** Return `true` iff the candidate subcommand is exactly `commit`
  or `push` (case-sensitive, full-token match). `commit-graph`, `commit-tree`, `push-pack`, and
  any other token that merely contains `commit` or `push` as a substring do NOT match.

The illustrative regex `\bgit\b.*\b(commit|push)\b` approximates this rule but is NOT
authoritative — it false-positives on `git commit-graph write` because the hyphen in `commit-graph`
is a word boundary making `\bcommit\b` match inside a different subcommand token (EC-011); it
cannot detect the gated subcommand in compound commands (EC-015/EC-016); and it does not enforce
basename matching (EC-017/EC-018). The Phase 1/1b/2/3/4 algorithm above is the sole authoritative
specification.

Commands that MUST be blocked (non-exhaustive): `git commit --amend` (EC-006), `git push
--force-with-lease` (EC-007), `git --git-dir .git commit -m "state"` (EC-013), `git --work-tree
/tmp push` (EC-014), `git status && git commit -m "x"` (EC-015), `git diff ; git push` (EC-016),
`/usr/bin/git commit -m "init"` (EC-017), `./git push origin main` (EC-018), `env GIT_DIR=.git
git commit -m "x"` (EC-021), `git --unknown-flag commit` (EC-022, fail-safe), `git --config-env
FOO=BAR commit` (EC-023), `git "commit"` (EC-024, Phase 1b quoting), `git 'push' origin`
(EC-025, Phase 1b quoting), `g'i't commit` (EC-026, Phase 1b POSIX token concatenation).

The following are OUT OF SCOPE by design — blocking these forms is UNDECIDABLE for static string
analysis (Rice's theorem). They are ALLOWED under the fail-open posture; the durable marker
written at PostToolUse time, the `^Agent$` next-advance arm, and GitHub server-side branch
protection provide defense-in-depth. See BC-1.18.002 Threat Model & Scope for the canonical
actor model (cooperating AI agent, NOT adversary-resistant boundary): `$(git commit -m "x")`
(EC-027, command substitution), `echo x | xargs git commit` (EC-028, xargs indirection),
`eval "git push origin main"` (EC-029, dynamic evaluation), and variable/alias/function
indirection forms.

**AC-009** (traces to BC-1.18.002 postcondition 3 — non-advancing not gated; out-of-scope forms documented)

Bash dispatches for which `is_git_commit_or_push(command)` returns `false` are NOT gated even
when the marker exists. Read, Edit, Write, MultiEdit tool dispatches are NOT gated.

The v1.3 algorithm (authoritative per BC-1.18.002 PC2 v1.3; ADR-047 §Decision 9; full
definition in AC-008) is the load-bearing pure filter. Key NOT-gated behaviors:

- **Phase 1 (compound splitting):** A compound command is only NOT gated if ALL segments return
  `false`; if any segment resolves to `commit` or `push`, the function returns `true` (blocked).
- **Phase 1b (POSIX quote-aware tokenization):** The `shell-words` crate tokenizes each segment.
  Quoted forms that resolve to `commit` or `push` after quote removal ARE blocked (e.g.,
  `git "commit"` → BLOCKED per EC-024; `git 'push' origin` → BLOCKED per EC-025; `g'i't commit`
  → BLOCKED per EC-026). This phase is what differentiates v1.3 from v1.2.
- **Phase 2 (basename):** A command is NOT gated if `basename(executable) ≠ "git"` (e.g.,
  `cat gitfile` — `basename("cat") = "cat" ≠ "git"`, returns `false`).
- **Phase 3–4 (option skip + subcommand match):** The recognized arg-taking global-option set
  (`-C`, `-c`, `--namespace`, `--git-dir`, `--work-tree`, `--super-prefix`, `--config-env`) each
  consume the following token as their argument before subcommand identification. Recognized no-arg
  flags are skipped without consuming a following token. An unrecognized `-`-prefixed token
  triggers fail-safe → `true` (blocked). Only exact tokens `commit` or `push` are gated.

The illustrative regex `\bgit\b.*\b(commit|push)\b` is NOT the authoritative rule — see AC-008.

BC-1.18.002 EC-001 through EC-005 MUST pass (non-advancing commands — `git status`, `git log`,
`git diff`, `git fetch`, non-git commands — `is_git_commit_or_push` returns `false`).
Additionally:
- `git commit-graph write` → NOT blocked: Phase 4 full-token match; subcommand is `commit-graph`,
  not `commit` (EC-011).
- `git -C .factory commit -m "state"` → BLOCKED: Phase 3 recognizes `-C` as arg-taking; `.factory`
  consumed as argument; Phase 4 subcommand is `commit` (EC-012).
- `git --git-dir .git commit -m "state"` → BLOCKED: Phase 3 `--git-dir` arg-taking; `.git`
  consumed; Phase 4 subcommand is `commit` (EC-013).
- `git --work-tree /tmp push` → BLOCKED: Phase 3 `--work-tree` arg-taking; `/tmp` consumed;
  Phase 4 subcommand is `push` (EC-014).
- `git status && git commit -m "x"` → BLOCKED: Phase 1 splits on `&&`; segment 2 subcommand is
  `commit`; any-segment `true` → function returns `true` (EC-015).
- `git diff ; git push` → BLOCKED: Phase 1 splits on `;`; segment 2 subcommand is `push` (EC-016).
- `/usr/bin/git commit -m "init"` → BLOCKED: Phase 2 `basename("/usr/bin/git") = "git"`;
  Phase 4 subcommand `commit` (EC-017).
- `./git push origin main` → BLOCKED: Phase 2 `basename("./git") = "git"`; Phase 4 subcommand
  `push` (EC-018).
- `git status && git log --oneline` → NOT blocked: Phase 1 splits; segment 1 subcommand `status`,
  segment 2 subcommand `log`; no segment matches `commit` or `push`; returns `false` (EC-019).
- `env GIT_DIR=.git git commit -m "x"` → BLOCKED: Phase 2 strips `env` + `GIT_DIR=.git`;
  executable is `git`; Phase 4 subcommand `commit` (EC-021).
- `git --unknown-flag commit` → BLOCKED (fail-safe): Phase 3 unrecognized option, no `=`,
  subcommand position uncertain; returns `true` (EC-022).
- `git --config-env FOO=BAR commit` → BLOCKED: Phase 3 `--config-env` arg-taking; `FOO=BAR`
  consumed; Phase 4 subcommand `commit` (EC-023).

**Phase 1b quoting (v1.3 additions — IN SCOPE):**
- `git "commit"` → BLOCKED: Phase 1b POSIX tokenization; `"commit"` → token `commit`; Phase 4
  match (EC-024).
- `git 'push' origin` → BLOCKED: Phase 1b POSIX tokenization; `'push'` → token `push`; Phase 4
  match (EC-025).
- `g'i't commit` → BLOCKED: Phase 1b POSIX token concatenation; `g'i't` → token `git`; Phase 2
  basename `git`; Phase 4 match (EC-026).

**Out-of-scope forms (NOT blocked by design — BC-1.18.002 Threat Model & Scope; defense-in-depth):**
- `$(git commit -m "x")` → NOT blocked: outer command is a command substitution, not a
  statically-literal `git` invocation; undecidable for static analysis; caught by other controls
  (EC-027).
- `echo x | xargs git commit` → NOT blocked: Phase 1 splits on `|`; segment 2 executable is
  `xargs` (basename `xargs` ≠ `git`); `git commit` is a string argument to `xargs`, not the
  top-level executable; returns `false` (EC-028).
- `eval "git push origin main"` → NOT blocked: Phase 2 executable is `eval` (basename `eval` ≠
  `git`); `git push` is a string argument subject to dynamic evaluation; undecidable for static
  analysis; caught by other controls (EC-029).

**AC-010** (traces to BC-1.18.002 postcondition 4 — absent marker: both arms pass)

When `.factory/unvalidated-mutation.marker` is absent, both Arm 1 (`^Agent$`) and Arm 2
(`^Bash$` git commit/push) return `exit_code = 0` (allow).

**AC-011** (traces to BC-1.18.002 precondition 1 + invariant 2 + postcondition 5 + postcondition 6 — gate registers on_error="block_if_marker" (fail-closed-but-recoverable on crash); two-axis model; ADR-048 §Decision 1; D-1135 reversed)

Both `validate-unvalidated-mutation-marker` hook entries in `hooks-registry.toml` MUST have
`on_error = "block_if_marker"` (NOT `"continue"` or `"block"`) AND `failure_policy = "fail-open"`.
`failure_policy = "fail-open"` is UNCHANGED from v1.3 (two-axis model — see below).

**Crash behavior (`block_if_marker`):** When the WASM gate plugin itself cannot complete at the
dispatcher layer (fuel exhaustion, epoch timeout, crash), the dispatcher executes a NATIVE
(non-WASM) marker-presence-and-TTL check — this supersedes the v1.3 `on_error = "continue"`
unconditional-allow-on-crash posture (ADR-048 §Decision 1; D-1135 reversed):
- **BLOCK (exit_code=2):** iff a non-expired `.factory/unvalidated-mutation.marker` exists
  (`expires_at > now UTC`; BC-1.18.002 PC5; story EC-033). Block message includes marker
  fields (`plugin_name`, `artifact_path`, `cause`, `expires_at`) plus three recovery options
  ordered by sanctioned preference (MUST NOT instruct agent to run `rm` — agent-tool rm is
  de-sanctioned per INV6/T4; AC-020): (a) Edit/Write re-validate the artifact named in
  `artifact_path` (T1 — primary agent recovery: inherently ungated, works even during gate
  crash; wait for PostToolUse PASS to clear the marker per BC-1.18.003 PC1); (b) wait for
  TTL expiry — 86400s from `expires_at` timestamp (T2 — passive self-healing); (c) human
  operator runs `rm .factory/unvalidated-mutation.marker` in their own terminal (T3 —
  break-glass; never intercepted by dispatcher; BC-1.18.002 v1.6 PC5).
- **ALLOW (exit_code=0):** if the marker is absent OR TTL-expired (`expires_at ≤ now UTC`) OR
  the crash-handler's own file-read fails (ENOENT → treat as absent; BC-1.18.002 PC6;
  story EC-034). No unconditional self-lock is possible: a crash with no valid quarantine
  signal cannot block indefinitely.

The self-lock hazard (INV2) is avoided by the no-valid-quarantine-signal → Allow branch, NOT
by unconditional allow. Three independent recoverability guarantees (INV6) ensure the system
is never in an irrecoverable quarantine state — see AC-020.

**Two-axis model (ADR-039; ADR-047 §Decision 9; ADR-048 §Decision 1):** Two orthogonal
failure-mode axes govern the gate and MUST NOT be conflated:
- **(i) `block_if_marker` crash policy** (`on_error = "block_if_marker"`): when the WASM plugin
  itself fails at the dispatcher layer — crash, fuel exhaustion, epoch timeout — the dispatcher
  executes the native marker-presence-and-TTL check (Block iff non-expired marker; Allow
  otherwise). This supersedes the v1.3 unconditional-allow-on-crash (`on_error = "continue"`)
  posture. `failure_policy = "fail-open"` governs a separate axis (the INDETERMINATE outcome
  of the gate plugin itself — see BC-1.18.004) and is orthogonal to `on_error`.
- **(ii) Filter-internal fail-SAFE posture** (Phase 3 of `is_git_commit_or_push`): when the
  filter encounters an UNRECOGNIZED git global option, it returns BLOCK (subcommand position is
  uncertain; under-blocking is the dangerous failure mode). This is a conservative within-filter
  design choice, orthogonal to axis (i): the filter's internal posture has no bearing on what the
  dispatcher does when the WASM plugin itself crashes.

### BC-1.18.002 Invariant 6 — Ungated-Escape Invariant

**AC-020** (traces to BC-1.18.002 invariant 6 — ungated-escape invariant; four-tier recovery
model; ADR-048 §Decision 3; VP-107)

The system is NEVER in an irrecoverable quarantine state. Three independent recovery tiers
(T1/T2/T3) guarantee the quarantine is always escapable. A fourth path (T4) is de-sanctioned.
The guaranteed recovery is T1+T2+T3, NOT agent-tool rm (ADR-048 §Decision 3 stable anchor):

- **(T1 — Primary agent recovery) Edit/Write to the artifact (re-validation dispatch):**
  Edit and Write tool dispatches do not match `^Agent$` (Arm 1) OR `^Bash$` (Arm 2). No arm
  fires; the crash-path native `block_if_marker_check` is not invoked for Edit/Write dispatches
  (no matched arm → no crash check). This path is INHERENTLY ungated: invariant to the gate
  plugin's crash behavior, to the marker's presence or expiry state, and to any `on_error` value
  on any arm. Confirmed ungated by construction (BC-1.18.002 PC3/AC-009). VP-107 verifies T1
  explicitly. This is the agent's genuine primary recovery path — re-validate the artifact named
  in `artifact_path` via Edit/Write, then wait for the PostToolUse gate plugin to produce PASS
  and clear the marker (BC-1.18.003 PC1; AC-012 + AC-022).

- **(T2 — Passive recovery) TTL auto-expiry (no dispatch required):**
  After `UNVALIDATED_MUTATION_MARKER_TTL_SECONDS` (86400s) have elapsed since the `expires_at`
  timestamp, any subsequent gate evaluation on the normal path finds `expires_at ≤ now (UTC)` →
  Allow + auto-delete (BC-1.18.003 PC4; AC-021). Any crash-path evaluation also finds marker
  expired → Allow (AC-011 PC6). No operator dispatch is required — passive self-healing.

- **(T3 — Human break-glass) Operator `rm` in own terminal:**
  The PreToolUse hook chain is invoked only when the AI agent calls a tool through the
  dispatcher. A terminal `rm .factory/unvalidated-mutation.marker` executed by the human
  operator in their own shell is NOT a dispatcher-mediated agent tool call and is NEVER
  intercepted by the hook chain. This is the break-glass pattern: the human principal, acting
  outside the mediation boundary, retains unconditional filesystem access.

- **(T4 — Agent-tool `rm`, DE-SANCTIONED) NOT a recovery path the invariant relies upon:**
  On the non-crash path, `is_git_commit_or_push("rm .factory/...")` returns `false`
  (`basename("rm") = "rm" ≠ "git"`) → Arm 2 does NOT gate the dispatch on the normal path.
  However, on the CRASH PATH (`on_error = "block_if_marker"`): when the `^Bash$` gate plugin
  crashes, the dispatcher's native `block_if_marker_check` runs for ALL `^Bash$` dispatches —
  including `rm .factory/unvalidated-mutation.marker` — with no `is_git_commit_or_push` filter.
  If a non-expired marker is present, the native check BLOCKS the `rm` dispatch. This is
  ACCEPTABLE — NOT an INV6 violation — because: (1) T1 (Edit/Write re-validation) is the agent's
  genuine ungated primary recovery; (2) a command-filter to whitelist `rm` in the crash handler
  is UNSOUND per Rice's theorem (same undecidable class as the `is_git_commit_or_push` scope,
  already accepted out-of-scope) and UNNECESSARY given T1; (3) allowing the agent to erase its
  own quarantine constraint in an anomalous crash state would be a CWE-636 regression.

**VP-107 scope:** VP-107 verifies T1 — that Edit/Write tool dispatch does NOT match either gate
arm's tool pattern (`^Agent$`, `^Bash$`); no arm fires; the `block_if_marker` crash-path native
check is never invoked for Edit/Write. VP-107 does NOT verify "agent-tool rm is never gated"
(that claim is de-sanctioned under T4). T3 is verified by architectural argument (human shell
outside dispatcher mediation). T2 is covered by the TTL invariant test.

### BC-1.18.003 — Marker Clear Protocol

**AC-012** (traces to BC-1.18.003 postcondition 1 + invariant 2 — re-validation clear; scoped to named plugin AND artifact path; PostToolUse hook only)

When the plugin whose `plugin_name` matches the marker's `plugin_name` field subsequently
produces `DispatchOutcome::Pass` (i.e., exit_code = 0 AND `host_output_too_large_seen = false`)
**in a PostToolUse hook invocation**, the dispatcher calls `delete_marker_if_pass()` which deletes
`.factory/unvalidated-mutation.marker`. The clear is artifact-scoped: BOTH conditions must hold —
(a) the dispatched plugin's `plugin_name` equals the marker's `plugin_name` field, AND (b) the
current dispatch's artifact path matches the marker's `artifact_path` field (exact string equality
of the normalized absolute path — both resolved to absolute form before comparison). **Empty-path
fallback (BC-1.18.003 EC-009):** if the marker's `artifact_path` is empty (the failing plugin was
a non-artifact-scoped validator — e.g., a wave-gate or path-staging validator — with no single
associated file), the artifact condition is vacuously satisfied and plugin_name equality alone
suffices for clearance. If the same plugin produces PASS on a DIFFERENT non-empty artifact, the
marker is NOT cleared — artifact A's quarantine persists until A is successfully re-validated by
the named plugin (story EC-031; BC-1.18.003 EC-008). A PreToolUse PASS result from the named
plugin MUST NOT clear the marker. Other plugins' PASS results do not clear the marker regardless
of hook type.

**AC-013** (traces to BC-1.18.003 postcondition 2 — idempotent delete)

`delete_marker_if_pass()` is idempotent: if `.factory/unvalidated-mutation.marker` is absent at
delete time, the function returns `Ok(())` (no-op). `io::ErrorKind::NotFound` is silently
swallowed. All other `io::Error` variants are propagated as `Err`.

**AC-014** (traces to BC-1.18.002 invariant 3 + BC-1.18.003 postcondition 3 + BC-1.18.003 invariant 3 — operator rm escape hatch; both arms unblocked simultaneously)

`rm .factory/unvalidated-mutation.marker` is the fully supported operator escape hatch. No
special command is required. After the rm, both Arm 1 and Arm 2 unblock simultaneously (both
check for the marker's presence at runtime; absent marker → pass).

### BC-1.18.003 Postcondition 4 — TTL-Expiry Clear Path

**AC-021** (traces to BC-1.18.003 postcondition 4 + invariant 5 — TTL-expiry clear path;
marker-level deadman; TTL-loudness audited event; ADR-048 §Decision 2 + §Decision 4 —
Emission-Point Correction, introduced by the F-P2-002 finding, human-ratified 2026-08-31 per
ADR-048's own revision history — historical provenance, non-load-bearing)

**Emission-point correction (v1.12 sync to BC-1.18.003 v1.4 / ADR-048 §Decision 4 — human-ratified,
S-25.01 LOCAL adversary pass 2 F-P2-002 HIGH resolution — historical provenance, non-load-bearing):**
TTL detection, auto-delete, and the
audited `marker.cleared` emission are performed ENTIRELY dispatcher-native by
`check_and_clear_expired_marker(factory_root, now, ctx: &HostContext) -> io::Result<Option<MarkerFields>>`
in `crates/factory-dispatcher/src/indeterminate_marker.rs`, called from `executor.rs`'s
tier-execution loop for every registry entry with `on_error == OnError::BlockIfMarker` BEFORE
that entry's Arm 1/Arm 2 WASM gate plugin (`evaluate_gate`) is invoked, on the normal (non-crash)
path. **Signature correction (v1.13 sync to BC-1.18.003 v1.5 / ADR-048 §Decision 4 — human-ratified,
S-25.01 LOCAL adversary pass 3 F-P3-001 MEDIUM resolution — historical provenance, non-load-bearing):**
the function takes `ctx: &HostContext`
(not a bare `log: &InternalLog, session_id: &str` pair) — `base_ctx: &HostContext` is already in
scope at the `executor.rs` call site, so this is a signature-widening refactor, not new plumbing.
`check_and_clear_expired_marker` MUST:
1. Read `.factory/unvalidated-mutation.marker` via `read_all_marker_fields`.
2. If present and `expires_at ≤ now (UTC)` (TTL elapsed): delete the marker file (idempotent;
   `io::ErrorKind::NotFound` swallowed; other IO errors logged but do NOT panic — auto-delete
   failure must not block the Allow return), then immediately call
   `emit_marker_cleared(ctx, &fields, "TTL_EXPIRED", "deadman", None)`, which internally routes the
   `marker.cleared` event through `ctx.emit_internal` (dual-sink: durable
   `dispatcher-internal-{date}.jsonl` write + `ctx.events` queue — NEVER a raw `InternalLog::write`
   call, per ADR-048 §Decision 4 (F-P3-001 correction — historical provenance, non-load-bearing)) with: `clear_mode = "TTL_EXPIRED"`, `actor_type =
   "deadman"`, `trace_id` from marker TOML `trace_id` field, `plugin_name` from marker TOML,
   `artifact_path` from marker TOML, `reason = null`, `timestamp` = time of the clear event, and
   return `Some(fields)` — signaling the caller (`executor.rs`) to treat the dispatch as Allow
   (`exit_code = 0`) without invoking the WASM gate plugin at all for this determination.
3. Otherwise (marker absent, or present and non-expired) return `None` without deleting.

By the time `evaluate_gate` subsequently runs (only reached when `check_and_clear_expired_marker`
returned `None`), the marker is guaranteed either absent or non-expired: `evaluate_gate` performs
NO `expires_at` parsing, deletion, or emission of its own — it is a PURE marker-presence check
(Block if present, Allow if absent). **TTL-loudness (ADR-048 §Decision 4):** the previously silent
auto-delete is now audited; emission is via `emit_marker_cleared(ctx, ...)`, called from
`check_and_clear_expired_marker` immediately after the native `std::fs::remove_file` succeeds,
routing through `ctx.emit_internal` (never a raw `InternalLog::write`; v1.13/ADR-048 §Decision 4,
F-P3-001 correction — historical provenance, non-load-bearing) —
and never from inside the WASM gate plugin via the `emit_event` host ABI, because the ABI's
RESERVED_FIELDS enrichment makes it structurally impossible for a WASM plugin to emit an event
carrying the marker's own (foreign) `trace_id`/`plugin_name` rather than its own dispatch identity
(BC-1.18.003 v1.5 PC4). The Allow+auto-delete decision is verified by VP-106; the
`marker.cleared(TTL_EXPIRED)` emission itself is verified by VP-108.

`UNVALIDATED_MUTATION_MARKER_TTL_SECONDS = 86_400` (24-hour deadman constant defined in
`crates/factory-dispatcher/src/indeterminate_marker.rs`). `expires_at` is the RFC 3339 UTC
timestamp written by `write_indeterminate_marker` at marker creation as `timestamp + 86400s`
(BC-1.18.001 PC4 v1.2; ADR-048 §Decision 2). Both Arm 1 (Agent) and Arm 2 (git commit/push)
are immediately unblocked by TTL expiry — same as marker absence.

**Crash-path TTL-allow does NOT emit `marker.cleared`:** the dispatcher's NATIVE crash-path TTL
check (AC-011 PC6 — crash + expired marker → Allow, `block_if_marker_check`) does NOT emit
`marker.cleared(TTL_EXPIRED)`. Only the dispatcher-native normal-path pre-check
(`check_and_clear_expired_marker`) emits it — `block_if_marker_check` (Decision 1) and
`check_and_clear_expired_marker` (this AC) are two distinct dispatcher-native functions; a crash
means the normal-path pre-check either did not run or was interrupted before completing. The
marker remains until the next normal-path pre-check clears it with the audited event
(BC-1.18.003 EC-014).

**Backward compatibility — legacy markers (missing `expires_at`):** Markers written before
ADR-048 implementation lack the `expires_at` field. `check_and_clear_expired_marker` MUST treat a
missing `expires_at` field as NON-EXPIRED (conservative; no silent auto-clear of old markers),
returning `None` and leaving the marker in place — the subsequent `evaluate_gate` then sees a
still-present marker and Blocks unconditionally, with no `expires_at` awareness required. Such
markers remain in effect until explicitly cleared via `rm` (PC3/AC-014) or successful
re-validation (PC1/AC-012).

**TTL is marker-level (INV5):** TTL expiry operates solely on the `expires_at` timestamp; it
does NOT check `plugin_name` or `artifact_path`. This is orthogonal to the artifact-scoped
re-validation clear (PC1/AC-012), which requires (a) plugin_name match AND (b) artifact_path
match. Story EC-035 covers this path.

- `clear_mode = "OPERATOR_OVERRIDE"`
- `actor_type = "operator"`
- `trace_id` = trace_id from the unmatched `marker.written` event (v1.14 — previously sourced from

- `reason = "RAW_DELETE_DETECTED: marker absent without prior marker.cleared event; inferred operator out-of-band clear"` (MUST be non-null for OPERATOR_OVERRIDE)
- `timestamp` = current evaluation time (deletion time is unobservable; operator shell is outside dispatcher mediation)
- `plugin_name` and `artifact_path` = likewise read from the unmatched `marker.written` event's own fields

historical provenance, non-load-bearing):** a fail-closed INDETERMINATE that
NEVER wrote a marker — either a PreToolUse dispatch (no write is ever attempted, BC-1.18.001

(story EC-008) — produces no `marker.written` event, so `reconcile_raw_delete` finds no unmatched

`marker.cleared(OPERATOR_OVERRIDE)` events for it — no fabricated NIST AU-3/AU-10 audit record.
This is the direct regression test for F-P6-001 (BC-1.18.003 v1.6 EC-017; BC-3.08.001 Event 10;
VP-108 postcondition 7). See story EC-036 for the canonical scenario.

**Bounded scan (production-grade requirement, ADR-048 §Decision 4 — MANDATORY, not
optional; requirement has held since its introduction and through subsequent §Decision 4
corrections, historical provenance non-load-bearing):** because `reconcile_raw_delete` runs on
the common marker-absent path before EVERY
Arm 1 (`^Agent$`) and Arm 2 (`^Bash$` git commit/push) dispatch, the scan MUST be bounded to avoid
unbounded I/O growth on the hot dispatch path: implementations MUST cap the scan to the CURRENT

total bytes/records read (a fixed-size tail read of the current day's file, not a full-file scan).
An unbounded scan on every Agent/git-commit dispatch would reintroduce the same class of
large-artifact resource cost that S-25.01 exists to eliminate (F1-delta-analysis §3). The exact
byte/record cap and any memoization strategy (e.g., a lightweight on-disk checkpoint to avoid
re-scanning already-reconciled ranges across dispatcher process invocations) are implementation
details, not fixed by the ADR or this AC — the implementer MUST choose and document a concrete
bound (e.g., last N KB or last N lines of the current day's file) satisfying the two MUST
constraints above.

This reconciliation step never gates the dispatch decision (BC-3.08.001 Invariant 3) — it MAY run
either synchronously before the Allow result is returned or as a best-effort step after, at
implementer's discretion.

**Best-effort:** if `ctx.internal_log` is `None` (the `dispatcher-internal-{date}.jsonl` log is
unavailable) or the unmatched record cannot be found, the annotation is omitted with no hard
failure. An unreconciled gap is observable by monitoring for `marker.written` events without
subsequent `marker.cleared` (v1.14 — previously `plugin.indeterminate`). VP-108 postcondition 3
covers this path's positive reconciliation (clear-path emission correctness); VP-108 postcondition
7 covers the non-fabrication negative control above; VP-106 does not cover either — VP-106 is
scoped to the clear-DECISION (Some/None + auto-delete file-state) property exercised by
`check_and_clear_expired_marker`, not to the emission-correctness of any `clear_mode`.

**AC-024** (traces to BC-1.18.001 v1.5 invariant 3 SUPERSEDED corollary + postcondition 4 v1.5

Mirroring AC-022/AC-023's structure, this AC covers the FOURTH audited clear path: a cross-pair
marker overwrite under BC-1.18.001 invariant 3's single-marker, last-writer-wins policy. When a

cleared) and a NEW INDETERMINATE fail-closed event fires for a DIFFERENT pair B `(plugin_b,
artifact_b)`, `write_indeterminate_marker`'s caller (`executor.rs`, at BOTH
`write_indeterminate_marker` call sites — the same sites that also call AC-025's
`emit_marker_written`) MUST:
1. Read the EXISTING marker's fields (`trace_id`, `plugin_name`, `artifact_path`) via
   `read_all_marker_fields` BEFORE the temp+rename overwrite — this read is unavoidable and
   UNCHANGED from v1.13, since the write itself overwrites the file the fields are read from; the
   read result is held, not emitted, until the write's outcome is known.
2. Call `write_indeterminate_marker(&new_fields, &marker_path)`.
3. **Emission-point correction (this burst — ADR-048 §Decision 4 (F-P9-001 correction — historical provenance, non-load-bearing)):** ONLY on the `Ok(())`
   arm (the write actually, durably succeeded), compare the pre-overwrite marker's
   `(plugin_name, artifact_path)` against pair B's:
   - If DIFFERENT (cross-pair), call `emit_marker_cleared(ctx, &existing_fields, "SUPERSEDED",
     "system", Some(reason))` — which routes through `ctx.emit_internal` (dual-sink: durable
     `dispatcher-internal-{date}.jsonl` write + `ctx.events` queue) — carrying pair A's OWN
     `trace_id`/`plugin_name`/`artifact_path` (never B's), with `reason = "SUPERSEDED: marker
     overwritten by a new plugin.indeterminate event for a different (plugin_name, artifact_path)
     pair before being cleared; last-writer-wins (BC-1.18.001 INV3)"` (non-null — `SUPERSEDED`
     joins `OPERATOR_OVERRIDE` as a `reason`-mandatory `clear_mode`), `timestamp` = time of the
     clear event. This call fires FIRST, immediately BEFORE AC-025's `emit_marker_written` call,
     in the SAME `Ok(())` arm (SUPERSEDED first, then `marker.written` — matching BC-1.18.001 v1.5
     postcondition 4's "write-success arm now emits BOTH write-tied events together" clause).
   - If the SAME pair (same-pair re-INDETERMINATE — continuous quarantine of the same target),
     emit NOTHING — unchanged from v1.13; already fully covered by the marker's own `trace_id`
     update at overwrite (BC-1.18.001 invariant 3 corollary).
4. **Write-failure non-fabrication (NEW this burst — ADR-048 §Decision 4 (F-P9-001 correction — historical provenance, non-load-bearing)):** on `Err(_)`

   unconditionally at the pre-overwrite READ, BEFORE `write_indeterminate_marker` was even called

   claimed it was overwritten). This is the direct fix for BC-1.18.003 v1.7 EC-018 (the F-P9-001
   regression test).

This closes a false-attribution audit-integrity gap (NIST AU-3/AU-10): without step 3,
`reconcile_raw_delete` (AC-023) would later find pair A's `marker.written` unmatched (if pair B's
marker is subsequently raw-deleted out-of-band) and mis-attribute A's silent supersession to a
human `OPERATOR_OVERRIDE` that never happened. No change to `reconcile_raw_delete`'s matching
logic is required — its scan already treats ANY `type == "marker.cleared"` record (regardless of
`clear_mode`) as closing the `(plugin_name, artifact_path)` key, so a `SUPERSEDED` record for A
closes A's key the moment B's write succeeds.

Wire format (BC-3.08.001 v1.34 Event 9): `clear_mode = "SUPERSEDED"`, `actor_type = "system"`,
`reason` mandatory non-null — UNCHANGED by this correction; only the emission POINT (WHEN) moved,
not the WHAT. VP-108 postcondition 5 verifies the (now write-then-emit-ordered) positive emission;
VP-108 postcondition 8 (NEW) is the direct negative-control regression test for F-P9-001 — a
cross-pair overwrite where `write_indeterminate_marker` returns `Err(_)` MUST yield ZERO
`marker.cleared(SUPERSEDED)` events AND ZERO `marker.written` events.
