# S-25.06: Append-Log Artifact Class — Sanctioned Backfill-Split Executor + ShardRegistry Enrollment + Cap-Triggered Rotation

## Narrative

- **As a** factory pipeline operator who depends on the four cycle append-log files
  (`decision-log.md`, `burst-log.md`, `lessons.md`, `session-checkpoints.md`) being compactable
  without requiring a manual shell write that the Claude Code auto-mode permission classifier
  correctly blocks as a POL-3 / TD-FACTORY-HOOK-BYPASS-001 P0 bypass
- **I want** a sanctioned, hook-validated, NATIVE (non-WASM, fuel-safe) CLI executor that:
  (a) performs the BC-1.18.008-specced one-time backfill-split against each of the four
  currently-oversized files, wiring the already-implemented `run_mechanism_a_backfill_split`
  function to an actual invocation path; and
  (b) enrolls those files in the ShardRegistry so ongoing cap-triggered rotation fires
  automatically per the BC-1.18.005 size-trigger mechanism — eliminating the class of manual
  compaction operations that have no sanctioned executor today
- **So that** no agent or human operator ever needs a bare `cp`/shell write to compact a cycle
  append-log file again, the WASM fuel-budget exhaustion and hook-block anti-patterns documented
  in CLAUDE.md §WASM plugin fuel budgets are permanently eliminated for the append-log class,
  and the BC-1.18.008 mandatory one-time backfill mandate is actually discharged rather than
  remaining a spec obligation without an execution path

## Context / Feature Summary

**Origin:** This story captures a mechanistic-coverage gap discovered at S-25.02 cluster-3
post-merge review. BC-1.18.008 specced "a mandatory, one-time backfill-split operation, executed
once at F4 activation" for `decision-log.md`, `burst-log.md`, `lessons.md`, and
`session-checkpoints.md`. S-25.02 cluster-3 (PR #831) shipped the ALGORITHM — specifically
`run_mechanism_a_backfill_split` in `crates/factory-dispatcher/src/shard_manager.rs` —
implementing all postconditions, idempotency, crash-atomicity, Backfill Recovery Manifest, and
independent census. But this function has exactly ZERO production call sites. The four files are
NOT enrolled in any ShardRegistry config; no CLI subcommand invokes the function for them.

### The Two Layers of the Gap

**Layer 1 — One-time backfill execution (BC-1.18.008 obligation unpaid):**
`run_mechanism_a_backfill_split` requires: (a) a `ShardEntry` with the artifact's metadata, (b)
the canonical file path, (c) `record_boundary_offsets` computed from the BC-1.18.008 marker
regexes for that artifact, and (d) `retention_count`. Today there is no code path that supplies
these four arguments for the real live files. The function can be called in unit tests with
synthetic fixtures; it cannot be called against `/repo/.factory/cycles/*/decision-log.md` without
a new CLI entry point.

As of 2026-09-12, the files are materially oversized:
- `v1.0-brownfield-backfill/decision-log.md`: ~1,233 KB / ~10,445 lines
- `v1.0-brownfield-backfill/session-checkpoints.md`: ~1,228 KB
- `v1.0-brownfield-backfill/burst-log.md`: ~953 KB
- `v1.0-brownfield-backfill/lessons.md`: ~291 KB
- `v1.0-feature-engine-discipline-pass-1/decision-log.md`: ~251 KB / ~564 lines
- `v1.0-feature-engine-discipline-pass-1/burst-log.md`: ~629 KB
- `v1.0-feature-engine-discipline-pass-1/lessons.md`: ~155 KB
Every one of these is at or beyond the WASM-fuel-safe budget documented in ADR-042 / ADR-051.

**Layer 2 — No ongoing cap-triggered rotation (BC-1.18.005/BC-1.18.006 not wired for this class):**
Even after the one-time backfill runs, the four files will continue to grow. The BC-1.18.005
size-trigger + BC-1.18.006 roll mechanism fires only for artifacts enrolled in the ShardRegistry.
Without enrollment, every future write to `burst-log.md` or `decision-log.md` bypasses the
cap check, and the files will re-inflate without any automatic compaction.

### The Constraint: No Manual Shell Writes

The correct fix is NOT a human-authorized shell `cp` or a one-off agent `python -c`. Those paths
are the exact anti-patterns POL-3 / TD-FACTORY-HOOK-BYPASS-001 P0 exist to prevent. **RESOLVED
2026-09-25 per ADR-052 §Decision 9** (see Architecture Compliance Rule 7 below): the
production-grade fix is NOT an Edit/Write-tool-mediated write either — it is a sanctioned,
one-time, human-approved `Bash`-tool execution of a native `factory-dispatcher
backfill-append-logs` binary under a closed argument grammar (ADR-052 §Decision 3), an
armed-activation manifest (§Decision 4), and a native admission gate (§Decision 5a) — so the
compaction is auditable (stdout census report + durable txn record, §Decision 6/7), crash-safe,
and structurally distinct from an unvalidated `cp`/`python -c` bypass without requiring the
Edit/Write tool surface to mediate the four files' content directly (which BC-1.18.013's
Postconditions establish is unnecessary: the binary's own admission gate and armed-activation
manifest are the sanctioning mechanism, not the Edit/Write tool call itself).

### What the `last-amended-migrate` CLI Cannot Do

`last-amended-migrate`'s `TARGET_FILES` const is hard-coded to 5 files (STATE.md, BC-INDEX.md,
STORY-INDEX.md, ARCH-INDEX.md, VP-INDEX.md). It handles frontmatter `changelog:`/`last_amended`
fields only (BC-10.13.001 scope). It cannot apply the content-body record-boundary split required
by BC-1.18.008. **RESOLVED 2026-09-25 per ADR-052 §Decision 2:** the missing entry point is a NEW
`backfill-append-logs` subcommand added to the `factory-dispatcher` binary (co-located with
`shard_manager.rs`), NOT an extension of `last-amended-migrate`. BC-10.13.001's 5-file scope is
unaffected.

### AC-001 (traces to BC-1.18.013 Precondition 3, Postcondition 6, Invariant 5, EC-008)
The `backfill-append-logs` subcommand of the `factory-dispatcher` binary accepts EXACTLY two
invocation forms — `backfill-append-logs` and `backfill-append-logs --census` — and no others.
It takes NO path argument, NO cycle-directory argument, and NO auto-discovery mode. The four
target files are the FIXED set named in ADR-052 §Decision 8's allowlist:
`.factory/cycles/v1.0-brownfield-backfill/{decision-log.md,burst-log.md,lessons.md,session-checkpoints.md}`.
Any invocation outside the two accepted forms (a path argument, a `--cycle` flag, an extra flag,
a shell metacharacter, or a compound command) is REJECTED by the pre-shell classifier
(ADR-052 §Decision 5c) before the binary is even invoked, and rejected again by the binary itself
with a non-zero exit if somehow bypassed.

### AC-002 (traces to BC-1.18.013 Postcondition 1)
For EACH of the four target files independently, content-preservation is verified via
BC-1.18.008 Postcondition 6(a)'s existing byte-for-byte record-boundary-safe partition check
(concatenation of all resulting shards plus the final current file reproduces the original
monolithic file byte-for-byte). This BC introduces no new per-file content-preservation
mechanism; the check is performed at ADR-052 §Decision 7c step 3b, per file, before the
`CURRENT-backfill-append-logs.json` pointer swap.

### AC-003 (traces to BC-1.18.013 Postcondition 2)
For EACH of the four target files independently, the independent census is verified via
BC-1.18.008 Postcondition 6(b)'s existing record-integrity check (every structural record present
in the original file appears in EXACTLY ONE resulting shard). There is no cross-file ID oracle;
each file's own record set is closed and self-contained. Verified at ADR-052 §Decision 7c step
3b, per file, before the pointer swap.

### AC-004 (traces to BC-1.18.013 Postcondition 3, Invariant 3)
The migration's atomic unit is the four SEPARATE files sharing ONE txn record, ONE generation,
and ONE `CURRENT-backfill-append-logs.json` pointer swap (per-migration pointer, ADR-052 §Decision 7e; v1.5 sibling sweep of the BC-1.18.013 v1.4 rename). If content-preservation (AC-002) or census (AC-003) fails
for ANY ONE of the four files, the ENTIRE migration aborts: none of the four canonical files is
touched, not merely the failing one. Each atomic file replacement (`rename(2)`), once past the
pointer swap, is followed by the platform-appropriate durability barrier (Linux:
`fsync(file_fd)` + `fsync(parent_dir_fd)`; macOS/APFS: `fcntl(F_FULLFSYNC)` + best-effort
`fsync(dir_fd)`) per ADR-052 §Decision 7d.

### AC-005 (traces to BC-1.18.013 Postcondition 3a)
Immediately before the `CURRENT-backfill-append-logs.json` pointer swap (and exactly once, never per-file), the
migration binary re-reads all four target files' current content, computes a single SHA-256 over
their concatenated bytes in fixed order (`decision-log.md`, `burst-log.md`, `lessons.md`,
`session-checkpoints.md`), and compares it against `source_sha256` in the txn record. Any
divergence aborts with `FINGERPRINT_MISMATCH_ABORT` (exit 2); all four canonical files are left
untouched; re-activation is required.

### AC-006 (traces to BC-1.18.013 Postcondition 4, EC-001)
Rollback on verification failure is whole-migration, not per-file: if content-preservation
(AC-002) or census (AC-003) fails for any of the four files, ALL FOUR files' original content is
left completely untouched (fail-loud, not partial-and-silent) — including files that themselves
staged cleanly. No subset of the four files is ever migrated while the others are left pending.

### AC-007 (traces to BC-1.18.013 Postcondition 5, Postcondition 5a, EC-004)
Idempotency has two layers. The governed migration's OWN idempotency signal is
`completed-backfill-append-logs.json`'s presence (`ALREADY_MIGRATED`, exit 0; v1.5 per BC-1.18.013
v1.4: checked BEFORE any MIGRATION lock is acquired — the sole lock operation permitted is the
non-blocking `exclusive.lock` probe of Postcondition 5a — and subject to Postcondition 5a's
txn-record reconciliation, which runs before the early return; the unconditional "no lock / zero
mutation" reading is superseded except in the clean steady state, EC-004) — authoritative for
"has this governed migration already run." Independently, each of the four files' OWN
`mechanism_a_backfill_already_migrated` / Backfill Recovery Manifest presence check

assuming none have a pre-existing manifest.

### AC-019 (D2; traces to BC-1.18.013 Precondition 6(c) "How DRAINING waits" + "Timeout", Invariant 6(d), EC-011; VP-143 D2 black-box; VP-146 a4)
The coordinator (`run_backfill_append_logs`) executes, in order and BEFORE any source snapshot, STAGING
work or staging generation: (1) stale-reservation TTL GC; (2) acquire `exclusive.lock`; (3) durable
`gate_state = DRAINING` flip under `LOCK_EX` on `gate-state.json`; (3a) initial txn record
`state=STAGING`, `generation_id=null`, `source_sha256=null` strictly AFTER the DRAINING flip; (4) poll
`reservations/` until empty; (5) only after quiescence compute `source_sha256`, flip `LOCKED`, fill the
txn record. A reservation never removed ⇒ `DRAIN_TIMEOUT_ABORT` (exit 2; drain timeout default 30 s,
injectable — tests inject ~200 ms): txn `ABORTED`, `gate_state` -> OPEN (under `LOCK_EX`), `exclusive.lock`
released, no staging generation, all four canonical files byte-identical, `source_sha256` never recorded;
a retry after the writer completes succeeds. A reservation removed (simulated PostToolUse) mid-poll before
the timeout lets the drain proceed with `source_sha256` computed only after the file vanished. Every
other abort path (census, content-preservation, fingerprint, expiry) also flips the gate to OPEN.

### AC-020 (D2; traces to BC-1.18.013 Precondition 6(c) "Stale reservations from dead writers", EC-012, EC-019)
Stale-reservation reclamation at drain step 1 is TTL-ONLY, never PID liveness: a reservation with

under TTL 3,600 s ⇒ stale; absent `created_at` + mtime 4,000 s ago ⇒ stale). TTL and drain timeout are
injectable parameters of the drain function.

## Architecture Compliance Rules

These rules are extracted from the architecture section files and ADRs that govern this story.
The implementer MUST NOT violate any of these; violations are bugs, not style preferences.

1. **No WASM-sandboxed executor for append-log migration (ADR-051 §Decision 7 / CLAUDE.md §WASM
   plugin fuel budgets):** The executor MUST run as a native binary (not inside a WASM plugin,
   not from within a hook plugin). WASM fuel budgets are insufficient for files in the 1 MB
   range. A WASM executor for this task is a bug, not a design choice.

2. **Single-commit-per-burst (TD-VSDD-053):** The activation-step execution (T-10, POST-MERGE per the
   2026-10-06 human decision) produces
   four modified cycle files. These MUST land in a single `.factory/` commit (state-manager
   disciplines). Never split the four-file compaction across two commits.

3. **Shard-manager is the single mutation authority (ADR-051 §Scope Note):** Do NOT add a
   second implementation of the backfill-split algorithm. The ONLY correct path is calling
   `run_mechanism_a_backfill_split` from `shard_manager.rs`. Any reimplementation is a POLICY
   violation.

4. **Enrollment is per-cycle-directory (ADR-051 §canonical-filename convention):** The
   ShardRegistry entry for `decision-log.md` must use the full path under a specific cycle
   directory (e.g. `.factory/cycles/v1.0-brownfield-backfill/decision-log.md`), not a glob
   or wildcard. Each cycle's files are enrolled independently with that cycle's configured cap.

5. **`last-amended-migrate`'s TARGET_FILES is unaffected (BC-10.13.001; RESOLVED 2026-09-25):**
   ADR-052 §Decision 2 places the `backfill-append-logs` subcommand in `factory-dispatcher`, NOT
   `last-amended-migrate`. BC-10.13.001's 5-file TARGET_FILES scope is therefore neither extended
   nor amended by this story — no BC-10.13.001 amendment is needed. (Previously this rule flagged
   a conditional BC-10.13.001 amendment pending the T-1 binary decision; that condition did not
   materialize.)

6. **`run_mechanism_a_backfill_split` signature is stable (BC-1.18.008 anchor):** Do not modify
   the existing function signature. If the new CLI path needs a slightly different invocation
   shape, add a wrapper. Do not modify the existing function, which is already anchored by
   BC-1.18.008 and covered by `bc_1_18_008_backfill_split_test.rs` (73+ passing tests).

7. **POL-3 no-bypass discipline (TD-FACTORY-HOOK-BYPASS-001 P0) — RESOLVED per ADR-052 §Decision 9
   (2026-09-25; FINDING HIGH-2 CLOSED).** This rule's original text asserted an impossible
   combination of constraints (a "native CLI" that must ALSO be logged as an Edit/Write tool
   call — a native binary performing filesystem writes cannot simultaneously be an Edit/Write
   tool call). Per ADR-052 §Decision 9, the architect withdrew that original text and replaced it
   verbatim with:

   > "The activation step is executed via the `Bash` tool with one-time interactive human
   > approval at F4 activation (no standing settings.json allowlist). The migration binary is
   > invoked at its absolute trusted path:
   > `{project-root}/target/release/factory-dispatcher backfill-append-logs`. The invocation is
   > NOT an Edit/Write tool call. It is a Bash execution of the native migration binary under
   > ADR-052 §Decision 3's closed argument grammar, activated under ADR-052 §Decision 4's
   > armed-activation manifest, producing a census report captured per ADR-052 §Decision 6."

   **Resolution addressed:** (a) Agent tool surface for T-10 is the `Bash` tool, invoking the
   native binary at its absolute trusted path — never Edit/Write, never a raw `cp`/`python -c`
   bypass. (b) POL-3/TD-FACTORY-HOOK-BYPASS-001 is satisfied because the invocation goes through
   the closed-argument-grammar pre-shell classifier (ADR-052 §Decision 5c) and the native
