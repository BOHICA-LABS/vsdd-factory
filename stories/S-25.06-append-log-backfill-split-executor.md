# S-25.06: Append-Log Artifact Class — Sanctioned Backfill-Split Executor + ShardRegistry Enrollment + Cap-Triggered Rotation

## Narrative

- **As a** factory pipeline operator who depends on the four cycle append-log files
  (`decision-log.md`, `burst-log.md`, `lessons.md`, `session-checkpoints.md`) being compactable
  without requiring a manual shell write that the Claude Code auto-mode permission classifier
  correctly blocks as a POL-3 / TD-FACTORY-HOOK-BYPASS-001 P0 bypass
- **I want** a sanctioned, hook-validated, NATIVE (non-WASM, fuel-safe) CLI executor that:
  (a) performs the BC-1.18.008-specced one-time backfill-split against each of the four
  currently-oversized files, wiring the already-implemented `run_mechanism_a_backfill_split`
  function to an actual invocation path; and
  (b) enrolls those files in the ShardRegistry so ongoing cap-triggered rotation fires
  automatically per the BC-1.18.005 size-trigger mechanism — eliminating the class of manual
  compaction operations that have no sanctioned executor today
- **So that** no agent or human operator ever needs a bare `cp`/shell write to compact a cycle
  append-log file again, the WASM fuel-budget exhaustion and hook-block anti-patterns documented
  in CLAUDE.md §WASM plugin fuel budgets are permanently eliminated for the append-log class,
  and the BC-1.18.008 mandatory one-time backfill mandate is actually discharged rather than
  remaining a spec obligation without an execution path

## Context / Feature Summary

**Origin:** This story captures a mechanistic-coverage gap discovered at S-25.02 cluster-3
post-merge review. BC-1.18.008 specced "a mandatory, one-time backfill-split operation, executed
once at F4 activation" for `decision-log.md`, `burst-log.md`, `lessons.md`, and
`session-checkpoints.md`. S-25.02 cluster-3 (PR #831) shipped the ALGORITHM — specifically
`run_mechanism_a_backfill_split` in `crates/factory-dispatcher/src/shard_manager.rs` —
implementing all postconditions, idempotency, crash-atomicity, Backfill Recovery Manifest, and
independent census. But this function has exactly ZERO production call sites. The four files are
NOT enrolled in any ShardRegistry config; no CLI subcommand invokes the function for them.

### The Two Layers of the Gap

**Layer 1 — One-time backfill execution (BC-1.18.008 obligation unpaid):**
`run_mechanism_a_backfill_split` requires: (a) a `ShardEntry` with the artifact's metadata, (b)
the canonical file path, (c) `record_boundary_offsets` computed from the BC-1.18.008 marker
regexes for that artifact, and (d) `retention_count`. Today there is no code path that supplies
these four arguments for the real live files. The function can be called in unit tests with
synthetic fixtures; it cannot be called against `/repo/.factory/cycles/*/decision-log.md` without
a new CLI entry point.

As of 2026-09-12, the files are materially oversized:
- `v1.0-brownfield-backfill/decision-log.md`: ~1,233 KB / ~10,445 lines
- `v1.0-brownfield-backfill/session-checkpoints.md`: ~1,228 KB
- `v1.0-brownfield-backfill/burst-log.md`: ~953 KB
- `v1.0-brownfield-backfill/lessons.md`: ~291 KB
- `v1.0-feature-engine-discipline-pass-1/decision-log.md`: ~251 KB / ~564 lines
- `v1.0-feature-engine-discipline-pass-1/burst-log.md`: ~629 KB
- `v1.0-feature-engine-discipline-pass-1/lessons.md`: ~155 KB
Every one of these is at or beyond the WASM-fuel-safe budget documented in ADR-042 / ADR-051.

**Layer 2 — No ongoing cap-triggered rotation (BC-1.18.005/BC-1.18.006 not wired for this class):**
Even after the one-time backfill runs, the four files will continue to grow. The BC-1.18.005
size-trigger + BC-1.18.006 roll mechanism fires only for artifacts enrolled in the ShardRegistry.
Without enrollment, every future write to `burst-log.md` or `decision-log.md` bypasses the
cap check, and the files will re-inflate without any automatic compaction.

### The Constraint: No Manual Shell Writes

The correct fix is NOT a human-authorized shell `cp` or a one-off agent `python -c`. Those paths
are the exact anti-patterns POL-3 / TD-FACTORY-HOOK-BYPASS-001 P0 exist to prevent. The
production-grade fix is a sanctioned CLI executor that goes through the same Edit/Write tool
surface that hooks validate — so the compaction is auditable, hook-validated, and crash-safe.

### What the `last-amended-migrate` CLI Cannot Do

`last-amended-migrate`'s `TARGET_FILES` const is hard-coded to 5 files (STATE.md, BC-INDEX.md,
STORY-INDEX.md, ARCH-INDEX.md, VP-INDEX.md). It handles frontmatter `changelog:`/`last_amended`
fields only (BC-10.13.001 scope). It cannot apply the content-body record-boundary split required
by BC-1.18.008. This story extends `last-amended-migrate` OR adds a new subcommand to the
`factory-dispatcher` binary to provide the missing entry point — the exact module/binary decision
is an architecture decision for the implementing burst (architect should weigh this during
activation).

## Provisional Acceptance Criteria

> **IMPORTANT:** These ACs are PROVISIONAL and will be superseded by ACs derived from the new
> product-owner-authored BC (likely BC-1.18.013 or higher) once that BC is authored and anchored.
> Do NOT trace these provisional ACs to BC IDs — the BCs do not yet exist. The ACs below capture
> the intended behavior for product-owner reference during BC authorship.

### AC-001 (provisional)
A new CLI subcommand (`backfill-append-logs` or an equivalent name agreed at activation) exists in
either `last-amended-migrate` or `factory-dispatcher`. The command accepts: (a) one or more
append-log file paths, or (b) a cycle directory and auto-discovers the four canonical files within
it. The command returns exit code 0 when all targeted files are successfully split or already
migrated; non-zero on any error.

### AC-002 (provisional)
For each targeted file that is NOT already migrated (idempotency short-circuit per BC-1.18.008
Invariant 3), the executor calls `run_mechanism_a_backfill_split` with correctly computed
`record_boundary_offsets` derived from BC-1.18.008's marker-table regexes for that specific
artifact stem (`decision-log`, `burst-log`, `lessons`, `session-checkpoints`). The
marker-computation logic is unit-tested against known fixtures drawn from the real files.

### AC-003 (provisional)
Content-preservation: after a successful backfill-split, a post-split census verifies that every
record from the original file appears in exactly one shard, and the record counts (per BC-1.18.008
Postcondition 6) match the pre-split census. Any mismatch is a hard failure: the executor emits
`E-SHD-003` (or the applicable taxonomy code) and does NOT publish the split result.

### AC-004 (provisional)
Crash-atomicity and rollback: if the executor process terminates between shard-write and
canonical-truncate, a re-run detects the partial state via the Backfill Recovery Manifest and
completes (self-heals) rather than duplicating records. If verification fails after a complete
run, already-written shards are removed (rollback), leaving the canonical file unmodified.

### AC-005 (provisional)
ShardRegistry enrollment: a TOML configuration entry (or equivalent source-of-truth update) is
added for each of the four append-log files in each active cycle directory. After enrollment, the
existing BC-1.18.005 size-trigger fires automatically during future dispatcher hook operations
when a file exceeds its configured cap, triggering a BC-1.18.006 roll without operator
intervention.

### AC-006 (provisional)
The new executor runs within the `last-amended-migrate` or `factory-dispatcher` binary without
any WASM sandbox, fuel budget, or async executor constraint. A single invocation of the command
for the largest currently-oversized file (`~1,233 KB decision-log.md`) completes in under 10
seconds on the developer workstation. No WASM plugin or hook intercepts the invocation itself.

### AC-007 (provisional)
Verbatim shard sidecars with pointer integrity: after the backfill, each shard file is a
byte-for-byte slice of the original content (no reencoding, no whitespace normalization), and
the shard index entries record `original_sha256` and `bytes_at_seal` consistent with
`run_mechanism_a_backfill_split`'s existing Postcondition 5 write-once seal.

### AC-008 (provisional)
A CHANGELOG entry is added to `CHANGELOG.md` under `[Unreleased] > Added` describing the new
CLI subcommand and enrollment behavior before the PR is opened.

## Edge Cases

| ID | Description | Expected Behavior |
|----|-------------|-------------------|
| EC-001 | Targeted file is already migrated (Backfill Recovery Manifest present) | `mechanism_a_backfill_already_migrated` returns true; executor short-circuits to idempotency path per BC-1.18.008 Invariant 3 |
| EC-002 | Targeted file was partially migrated (shards written, canonical not yet truncated) | Self-heal path (heal_or_confirm_already_migrated) completes the truncation; no duplicate records |
| EC-003 | Targeted file is a single oversized record exceeding BC-1.18.008 EC-002 single-record exception threshold | Executor emits a warning and proceeds with the BC-1.18.008 EC-002 exception path; does not fail hard |
| EC-004 | Targeted file does not exist or is unreadable | Executor exits non-zero with a clear error; no partial state written |
| EC-005 | Targeted file's cycle directory does not match any enrolled ShardRegistry entry | Executor operates in one-time-backfill-only mode; enrollment is a separate precondition |
| EC-006 | `record_boundary_offsets` computed from the marker regex yields zero boundaries for a non-empty file | Hard failure; `record_boundary_offsets_are_well_formed` guard prevents empty-oracle partition |
| EC-007 | Content-preservation census mismatch after split | Hard failure with `E-SHD-003`; shards are removed (rollback); canonical file unmodified |
| EC-008 | File is between two cycle directories with different enrolled caps | Enrollment is per-cycle-directory; each cycle's files use that cycle's configured cap independently |

## Architecture Compliance Rules

These rules are extracted from the architecture section files and ADRs that govern this story.
The implementer MUST NOT violate any of these; violations are bugs, not style preferences.

1. **No WASM-sandboxed executor for append-log migration (ADR-051 §Decision 7 / CLAUDE.md §WASM
   plugin fuel budgets):** The executor MUST run as a native binary (not inside a WASM plugin,
   not from within a hook plugin). WASM fuel budgets are insufficient for files in the 1 MB
   range. A WASM executor for this task is a bug, not a design choice.

2. **Single-commit-per-burst (TD-VSDD-053):** The activation-step execution (T-10) produces
   four modified cycle files. These MUST land in a single `.factory/` commit (state-manager
   disciplines). Never split the four-file compaction across two commits.

3. **Shard-manager is the single mutation authority (ADR-051 §Scope Note):** Do NOT add a
   second implementation of the backfill-split algorithm. The ONLY correct path is calling
   `run_mechanism_a_backfill_split` from `shard_manager.rs`. Any reimplementation is a POLICY
   violation.

4. **Enrollment is per-cycle-directory (ADR-051 §canonical-filename convention):** The
   ShardRegistry entry for `decision-log.md` must use the full path under a specific cycle
   directory (e.g. `.factory/cycles/v1.0-brownfield-backfill/decision-log.md`), not a glob
   or wildcard. Each cycle's files are enrolled independently with that cycle's configured cap.

5. **TARGET_FILES in `last-amended-migrate` must not grow without a BC-10.13.001 amendment:**
   BC-10.13.001 governs exactly which files `last-amended-migrate` mutates. If the new
   subcommand lives in this binary, it MUST be additive (new subcommand, not expanding
   TARGET_FILES) and the BC must be amended to reflect the new subcommand scope. Architect to
   adjudicate.

6. **`run_mechanism_a_backfill_split` signature is stable (BC-1.18.008 anchor):** Do not modify
   the existing function signature. If the new CLI path needs a slightly different invocation
   shape, add a wrapper. Do not modify the existing function, which is already anchored by
   BC-1.18.008 and covered by `bc_1_18_008_backfill_split_test.rs` (73+ passing tests).

7. **POL-3 no-bypass discipline (TD-FACTORY-HOOK-BYPASS-001 P0) — CONTRADICTION IDENTIFIED
   (FINDING HIGH-2 — OPEN activation gate, architect resolution required):**
   This rule as originally stated asserts an IMPOSSIBLE combination of constraints:
   - AC-006 (lines ~185-188) requires a "native CLI" where "No WASM plugin or hook intercepts
     the invocation itself."
   - This rule (Rule 7, original text) required the activation step "to be an agent-executed
     CLI invocation logged as an Edit/Write tool call, not a raw Bash `cp` or Python `open()`."
   - A native CLI that performs filesystem writes is NOT an Edit/Write tool call. Claude's
     Edit/Write tools are the agent-tool-surface that runs through hook validation. A native
     binary (e.g., `./factory-dispatcher backfill-append-logs ...`) writes directly to the
     filesystem outside the Edit/Write surface. These two requirements cannot both hold: a
     native-binary invocation cannot simultaneously be an Edit/Write tool call.

   **Current status: OPEN activation gate.** Before this story can transition to `status: ready`,
   the architect must specify a REAL sanctioned invocation mechanism + permission policy that
   can actually execute under the operator's auto-mode permission classifier. The specific
   tension to resolve:
   - Agent shell-writes to `.factory/` are POL-3-blocked (TD-FACTORY-HOOK-BYPASS-001 P0).
   - A native CLI sidesteps the Edit/Write hook-validation surface.
   - The `Bash` tool (shell execution) under auto-mode requires a permission grant that must
     be explicitly authorized for the target path pattern.
   - The activation step (T-10) must have a clearly specified, actually executable invocation
     path — not a prohibition of all execution paths simultaneously.

   **Resolution must address:** (a) Which agent tool surface is used for T-10 (Edit/Write with
   content piped through the tool, Bash with an explicit permission grant, or another sanctioned
   path)? (b) How does this interact with POL-3? (c) Does the invocation produce an audit trail
   that hook validators can inspect? The resolution happens at cluster-5 F1 activation (architect
   + product-owner burst). This rule is recorded here to document the open gate accurately — not
   to resolve it. Do NOT mark this story `status: ready` until the architect provides the answer.
