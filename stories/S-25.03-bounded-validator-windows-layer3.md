# S-25.03: Bounded Validator Windows Layer 3 — Validators Read from Shards via Bounded Lookups

## Narrative

- **As a** factory pipeline operator who has Layer 2 (artifact sharding) deployed
- **I want** all validators to read BOUNDED WINDOWS from individual shards rather than scanning
  whole files, with trusted-boundary-checkpoints carrying cross-shard invariants (changelog
  monotonicity, trajectory-tail) across shard boundaries, and the regression-gate's own
  state file bounded and rotated under the same shard rules
- **So that** fuel-exhaustion INDETERMINATE events from the read path are eliminated by
  construction — each validator invocation reads at most one bounded shard, completing within
  the fuel budget even as the corpus grows indefinitely

## Context / Feature Summary

**Registered at:** F3 story-decomposition burst, validation-integrity-layer1 cycle,
2026-08-30 (story-writer). Source: ADR-047 §Decision 8b (Ratified Future Phase Layer 3).

**Why Layer 3 follows Layer 2 (not concurrent):**
Layer 3 requires the sharding infrastructure from Layer 2 to exist (shard files, shard index,
bounded shard sizes). Validators cannot read from shards until shards exist and their format is
finalized. The bounded-window query API (how validators navigate from a shard index to a specific
shard, and how checkpoint records are structured) is a Layer-2 output that Layer-3 consumes.

**Two categories of bounded-window validators (from ADR-047 §D8b):**

*Window-local validators (safe — no cross-shard state needed):*
- `validate-closes-completeness` → current burst shard only (Closes blocks are local to a burst)
- `validate-factory-path-staging` → tool params (already bounded at Layer 1 Cohort A)

*Whole-corpus validators requiring trusted-boundary-checkpoint carry-forward:*
Cross-shard invariants (e.g., changelog monotonicity — sequence numbers must increase across
shard boundaries; trajectory tail — the STATE.md banner must match the prior shard's last entry)
require a trusted-boundary-checkpoint carried forward from the prior SEALED shard. Each sealed
shard's checkpoint record contains: `(last_validated_seq, last_shard_id, last_shard_digest, summary)`.
The validator for shard N reads the checkpoint from shard N-1 (sealed) and validates the seam.
This follows RFC 9162 (Certificate Transparency checkpoint-carry-forward) and the RocksDB
two-layer model: per-file local check + separate global manifest check.

**Retroactive edits (our cycle-specific requirement):**
Our cycle performs retroactive remediations. If a remediation edits a SEALED shard, that shard
must be re-validated and its checkpoint recomputed; downstream shard seam validations also re-run.
This MUST be explicit in the Layer 3 implementation — a "sealed shard" is NOT immutable in our
cycle, and the validator design must handle re-sealing.

**regression-gate state-file reform:**
The regression-gate plugin failed to persist its own state file 22 times due to OutputTooLarge
(from the F1 forensics). Layer 3 reforms the regression-gate to write its state file to a
bounded-rotated file under the same shard rules. After this reform, regression-gate can be flipped
to fail-closed (if not already done in Layer 2) with its STATE-FILE WRITE also guaranteed to
succeed within the OutputTooLarge envelope.

## Acceptance Criteria

> **PRELIMINARY — Requires product-owner BC authorship at activation.**
> ACs below are PROVISIONAL based on ADR-047 §Decision 8b ratified content. Product-owner
> MUST author formal BCs with canonical PC numbering before this story advances to ready.

### AC-001: Window-local validators read only the current shard (traces to ADR-047 §D8b — BC-TBD)

`validate-closes-completeness` and `validate-factory-path-staging` MUST read only the current
shard file (or tool params respectively). Neither validator MUST scan the full shard history.
Each invocation MUST complete within the single-shard fuel budget established by Layer 2.

### AC-002: Whole-corpus validators use checkpoint carry-forward (traces to ADR-047 §D8b — BC-TBD)

Validators for cross-shard invariants (changelog monotonicity, trajectory-tail) MUST read:
(a) the current shard's data, AND (b) the boundary checkpoint from the prior sealed shard.
The checkpoint record MUST contain: `last_validated_seq`, `last_shard_id`, `last_shard_digest`,
`summary`. The seam between shard N-1 and shard N MUST be validated using this checkpoint.

### AC-003: Re-sealing of retroactively edited shards (traces to ADR-047 §D8b retroactive-edits — BC-TBD)

When a remediation edits a sealed shard, the shard MUST be re-validated and its checkpoint
recomputed. Downstream shard seam validations (shard N+1, N+2, ...) MUST also re-run to
propagate the new checkpoint values. The shard manager MUST NOT treat sealed shards as immutable.

### AC-004: regression-gate state-file bounded and rotated (traces to ADR-047 §D8b, F1 §10 — BC-TBD)

The regression-gate plugin MUST write its state file to a bounded-rotated file (under the same
shard rules as the cycle artifacts). The state file MUST NOT exceed the single-shard fuel budget.
After this reform, regression-gate MUST successfully persist its state file (the 22× OutputTooLarge
failure mode is eliminated by construction).

### AC-005: OutputTooLarge read-path elimination (traces to ADR-047 §D8b, ADR-047 §D6 — BC-TBD)

After Layer 3, `host_fn_returned_output_too_large` events from the read path (read_file,
read_prefix host functions) MUST drop to zero on normal pipeline writes to sharded artifacts.
The INDETERMINATE outcome from OutputTooLarge (introduced in Layer 1 for fail-closed plugins)
SHOULD become a dead code path for the sharded read-path. (The Store-flag mechanism remains for
defense-in-depth; the root-cause elimination is confirmed by monitoring plugin.indeterminate
events with cause=output-too-large in production after Layer 3.)

### AC-006: Full regression suite stays green (traces to ADR-047 §D7 — BC-TBD)

`cargo test --workspace --all-targets` and `plugins/vsdd-factory/tests/run-all.sh` MUST stay
green after Layer 3 lands.

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-001 | First shard in a series (no prior sealed shard; no checkpoint) | Validator validates the first shard as a complete corpus; writes initial checkpoint for shard 0 |
| EC-002 | Retroactive edit of a sealed shard N | Re-validate shard N; recompute checkpoint N; re-validate seam N→N+1; cascade to all downstream seams |
| EC-003 | Checkpoint file for shard N-1 is absent or corrupt | Fail-loud; block dispatch until operator restores checkpoint (analogous to missing marker in Layer 1) |
| EC-004 | regression-gate state-file write exceeds shard cap | Roll to new state-file rotation BEFORE writing (same roll-before-write rule as artifact shards; AC-004 reform) |
| EC-005 | Validator reads two shards (current + prior checkpoint) but both are at cap | Each shard read is independently bounded; combined fuel = 2 × single-shard fuel; must remain within fuel budget. Architecture must account for this in cap derivation |
