# S-26.02: `validate-factory-path-staging` False-Positives on Raw Command String / Branch Name

## Narrative
- **As an** agent staging changes on a `develop`-based branch
- **I want to** `validate-factory-path-staging` to gate on what is ACTUALLY staged
  under `.factory/`, not on whether my command's raw text happens to mention a
  `.factory/` path token
- **So that** I am never blocked from legitimate git operations (including a
  `gh issue create` whose BODY text merely references a path) when zero factory paths
  are staged

## Problem Statement (GH issue #840, P1, AXIS-2 current-source defect)

`validate-factory-path-staging` (`crates/hook-plugins/validate-factory-path-staging/`,
`PreToolUse`; BC-4.16.001; registered per ADR-031 §Decision 3, story S-21.01) exists to
enforce that `.factory/`-tree paths are staged only via the correct factory-artifacts
worktree/branch discipline (CAP-034). The guard was observed raising
`FactoryPathOnProductBranch` in two false-positive shapes:

1. Blocking a git-staging operation on a `develop`-based branch when the actual staged
   diff (`git diff --cached --name-only`) contains **zero** `.factory/`-tree paths —
   the guard decided from the raw command STRING (a path token appearing anywhere in
   the invoked command text) and the branch name alone, not from what was actually
   staged.
2. Blocking a `gh issue create` call whose issue BODY text merely mentioned a
   `.factory/` path as a string literal (describing this very defect, in fact) — the
   guard's raw-string scan fired on prose, not on any git-staging action at all.

## Required BC Amendment (product-owner routing — NOT authored by this story)

BC-4.16.001 needs its gate predicate corrected from "raw command string contains a
`.factory/` path token AND branch is `develop`-based" to "the ACTUAL currently-staged
path set (`git diff --cached --name-only`, or the tool-call's own destination path for
non-git tool calls) contains at least one path under `.factory/`." Product-owner must
also decide, in consultation with architect, whether non-git tool calls (e.g.
`gh issue create`) should be exempted from this guard entirely (they never stage
anything) or should have their own narrower, correctly-scoped check — the story-writer
flags this ambiguity for PO/architect adjudication rather than resolving it here.

## Acceptance Criteria (DRAFT — pending BC-4.16.001 amendment; NOT yet BC-traced)

### AC-001 (BC trace: pending BC-4.16.001 amendment)
- On a `develop`-based branch, a git-staging command whose `git diff --cached
  --name-only` output contains zero paths under `.factory/` is NEVER blocked with
  `FactoryPathOnProductBranch`, regardless of what path tokens appear in the raw
  command string.
- **Test:** `test_BC_4_16_001_zero_staged_factory_paths_not_blocked()`

### AC-002 (BC trace: pending BC-4.16.001 amendment)
- Reproduces GH issue #840's exact `gh issue create` false-positive as a regression
  test: a non-staging tool call whose text body mentions a `.factory/` path string is
  NOT blocked.
- **Test:** `test_BC_4_16_001_gh_issue_create_mention_not_blocked_regression()`

### AC-003 (BC trace: pending BC-4.16.001 amendment)
- A git-staging command whose `git diff --cached --name-only` output DOES contain at
  least one path under `.factory/`, on a `develop`-based branch, is still correctly
  blocked (no regression on the guard's true-positive case; CAP-034 enforcement
  intact).
- **Test:** `test_BC_4_16_001_true_positive_staged_factory_path_still_blocked()`

### AC-004 (traces to BC-4.16.001 Invariant 7, Invariant 3 (amended), Postcondition 1 (amended), Postcondition 3, EC-015, EC-016, EC-017, EC-018, T-10, T-11, T-12, T-13; [D-1254-HOOK-FP-003], GH #840 family)
The branch that PC1, PC3 and the block message are evaluated against is the branch of the git TARGET directory T of the `git add` / `git stage` invocation (the work tree the command stages in), NEVER the branch of the hook
process's working directory (the dispatcher's session project root). T is resolved from the payload in this order and the FIRST rule that applies wins: (1) the value of the explicit `-C <path>` global option of the (first)
`git add`/`git stage` invocation, ANY path and not only a `.factory`-class one (successive `-C` options compose as git does, each relative to the previous); (2) otherwise the value of `--work-tree <path>` /
`--work-tree=<path>` or of `-c core.worktree=<path>`; (3) otherwise the directory named by the last `cd <dir>` / `pushd <dir>` that precedes the git invocation in the same payload; (4) otherwise the working directory of
the guarded Bash call itself when the hook input carries it; (5) only when none of (1)-(4) is available, the hook process's own working directory (the pre-v1.10 behavior, retained solely as the last-resort fallback).
Branch detection is `git -C <T> branch --show-current` through `host::exec_subprocess`, EXACTLY ONE invocation per payload (T is taken from the first `git add`/`git stage` invocation; a second target in a chained payload
is under-matched exactly as the Invariant 6 accepted residual 2 states). If detection on the resolved T fails (T is not a git work tree, does not exist, git exits non-zero, empty output / detached HEAD, git unavailable) the
plugin FAILS OPEN with an advisory warning per Invariant 3 and MUST NOT fall back to the hook-process branch. The branch named in the PC1 block message is the branch of T. What AC-004 does NOT change: the Precondition 2
detection contract; the Invariant 4 conservative path, bulk-flag (`-A`, `--all`, `-u`, `.`, glob) and `.factory/`-argument forms and their EC-004 / EC-008 / EC-010 verdicts (the staged-path predicate that would relax them is
the separate amendment owed to AC-001..AC-003); PC2-PC4; a `.factory/` path staged on a product-branch T is blocked exactly as before; a T on `factory-artifacts` passes unconditionally (PC3).
Required behaviors (the BC vectors): (a) a feature-branch worktree reached by `git -C W add crates/...`, `cd W && git add crates/...` or a Bash call whose working directory is `W` is PASSED (PC2) and is never judged on a
`develop`-rooted session (EC-015, T-10); the same three forms with `.factory/STATE.md` are BLOCKED by PC1 and the message names `product branch 'feature/S-25.09'`, NOT `develop` (EC-015, T-11); (b) a `factory-artifacts`
worktree staged through a non-`.factory`-class path (`cd /repo/.factory && git add -A`, a Bash working directory on that worktree, `git -C /repo/.factory-wt add STATE.md`) is PASSED by PC3 (EC-016, T-12); (c) genuine
`develop` staging of `.factory/` paths (no `-C`, no `cd`, target = project root on `develop`, `git -C /repo add ...`, `cd /repo && git add ...`, and `release/v1.0.0-rc.26`) is still BLOCKED naming the TARGET's branch
(EC-017, T-13; the true-positive case is intact); (d) fail-open and single-invocation: `git -C /nonexistent add .factory/STATE.md`, `git -C /tmp/not-a-repo add ...` and a detached-HEAD T are PASSED with an advisory warning and
no session-branch fallback; a chained `git -C W1 add a.rs && git -C W2 add .factory/x.md` performs ONE detection on W1; composed `-C` values (`git -C /repo -C .worktrees/S-25.09 add .factory/STATE.md`) resolve to
`/repo/.worktrees/S-25.09` and are BLOCKED with `product branch 'feature/S-25.09'` (EC-018).
- **Test:** `test_BC_4_16_001_EC015_feature_worktree_target_is_judged_on_its_own_branch_not_the_session_branch()` (T-10, T-11: the three forms x `crates/` path and `.factory/STATE.md` path),
  `test_BC_4_16_001_EC016_factory_artifacts_worktree_target_passes_pc3_via_cd_and_working_directory()` (T-12), `test_BC_4_16_001_EC017_genuine_develop_staging_of_factory_paths_still_blocked_naming_the_target_branch()` (T-13)
  and `test_BC_4_16_001_EC018_unresolvable_target_fails_open_single_detection_and_composed_c_values()`; names are PROPOSED and the test-writer finalizes them in `crates/hook-plugins/validate-factory-path-staging/tests/`.
  A pure resolver unit table (`resolve_staging_target(payload_command, hook_input_cwd) -> TargetDir`) covers rules 1-5 and their precedence without a subprocess.
