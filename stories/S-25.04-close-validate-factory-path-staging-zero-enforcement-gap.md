# S-25.04: Close validate-factory-path-staging Zero-Enforcement Gap — Real Layer-1 Production Trigger

## Narrative

- **As a** factory pipeline operator who was told (S-25.01) that `validate-factory-path-staging`'s
  fail-closed assignment closes the CWE-754 "cannot-complete-treated-as-PASS" hole for the
  `.factory/` **git-staging exclusivity guard** (INV-E21-001, CAP-034 — `validate-factory-path-staging`
  blocks `git add`/`git stage` of `.factory/` paths on product branches; it has no role in validating
  the *content* of a `.factory/` artifact write)
- **I want** that fail-closed assignment to have an ACTUAL production enforcement effect — a real
  trigger path that reaches `write_indeterminate_marker` and the next-advance gate when a
  fail-closed validator's WASM execution cannot complete (fuel exhaustion, epoch timeout, or
  OutputTooLarge)
- **So that** the gap identified in ADR-047 v1.4 / BC-1.18.004 v1.2 (the assignment is safely SET
  but currently ENFORCES NOTHING — identical runtime effect to `failure_policy = "fail-open"`) is
  genuinely closed, not just correctly documented — via a new **post-hoc git-staging detective
  mirror** validator (`validate-factory-path-staged`, BC-4.16.002) that inspects the actual git
  index/branch state after a Bash command completes, giving the existing marker/gate mechanism
  (S-25.01) its first structurally-reachable PostToolUse trigger

## Context / Feature Summary

**Follow-up to S-25.01 (Layer 1), anchored per ADR-047 v1.4 §Decision 8a "Known Gap" note
(20bf81dd) and BC-1.18.004 v1.2 postcondition 4 (df3219ea) — both human-directed factual
corrections, routed from pr-reviewer's fresh-eyes MAJOR finding on PR #807, NOT a POLICY 22
design/security-model change. Activated at F1/F2 (2026-09-04); BCs anchored; status promoted to
`ready` in this same burst.**

**The gap, precisely stated:** `validate-factory-path-staging` (BC-4.16.001) is registered in
`hooks-registry.toml` as `failure_policy = "fail-closed"`, PreToolUse `^Bash$`. The Layer-1
durable-marker write path (`write_indeterminate_marker`, invoked from the dispatcher's PostToolUse
handling per BC-1.18.001 invariant 4) fires **ONLY on a PostToolUse dispatch**. Because this
validator is registered PreToolUse, it structurally can never reach that write path — no matter
how many times its WASM execution fuel-exhausts, epoch-times-out, or trips OutputTooLarge, no
marker is ever written and no gate is ever triggered. Combined with `on_error = "continue"`
(which never blocks the *current* dispatch either, present or future) and this validator's
absence from the ADR-039 §Decision 2 exhaustion-leg roadmap prior to this story, an INDETERMINATE
outcome on this validator degrades to the identical advisory-only `plugin.indeterminate` event a
`failure_policy = "fail-open"` plugin would produce. The fail-closed config bit is real and
correctly set; it currently enforces nothing.

**PREMISE CORRECTION (F1, 2026-09-04 — supersedes v1.0's provisional framing):** the original
v1.0 authoring of this story described option (a)'s companion validator as mirroring
`validate-factory-path-staging`'s check "on the artifact-write side," and provisionally guessed a
new BC would live at `BC-1.18.005`/SS-01. Ground-truthing `validate-factory-path-staging` against
its own authoritative behavioral contract (**BC-4.16.001**, SS-04) showed this framing was
imprecise in a way that mattered for BC authorship: `validate-factory-path-staging` does **not**
validate the *content* of a `.factory/` artifact write. It is a narrow **git-staging exclusivity
guard** (INV-E21-001, CAP-034, issue #342): a `PreToolUse ^Bash$` plugin that inspects a Bash
payload for a `git add`/`git stage` command and, if any argument resolves to a `.factory/`-rooted
path **and** the current branch is a product branch (not `factory-artifacts`), blocks the command
before it runs. There is no "artifact write" for a companion validator to validate — the thing
being protected is exclusive git-tracking of `.factory/` content between the `factory-artifacts`
orphan branch and product branches. The companion validator that actually closes the enforcement
gap is therefore **not** a generic Edit/Write/MultiEdit `.factory/`-write validator; it is the
natural **post-hoc detective mirror** of the same git-staging-exclusivity concern: a
`PostToolUse ^Bash$` plugin that, after a Bash command completes, inspects the *actual* git
index/branch state (`git diff --cached --name-only` + `git branch --show-current`, the same
`host::exec_subprocess` pattern `validate-factory-path-staging` itself already uses) to detect
whether a `.factory/` path ended up staged on a product branch. This closes the residual-risk
class BC-4.16.001's own text-based command-parsing heuristics cannot see — staging via git
plumbing, aliases, wrapper scripts, or any invocation whose completed command text never contains
a recognizable `git add`/`git stage` substring (BC-4.16.001 Invariant 6 Accepted Residuals) —
because the check runs against actual index state, not payload text. This correction relocated
the new BC's home from the guessed `BC-1.18.005`/SS-01 to the correct **BC-4.16.002**/SS-04 (new
sibling of BC-4.16.001, same capability CAP-034) — the SS-01 BCs (BC-1.18.001/BC-1.18.004) needed
only narrow, non-mechanism-changing amendments, since they define the *generic* INDETERMINATE/
marker mechanism that already applies automatically to any qualifying PostToolUse fail-closed
plugin, including this new one. See `.factory/cycles/v1.0-brownfield-backfill/
S-25.04-f1-delta-analysis.md` §0 for the full correction record and `.factory/cycles/
v1.0-brownfield-backfill/S-25.04-f2-architecture-decisions.md` §4 for the ADR-047 §D8a
erratum-class clarification note (ready for a subsequent architect/state-manager commit; not
applied by this story file).

**Why this matters:** `validate-factory-path-staging` was the ONE Cohort A validator originally
advertised (S-25.01 v1.1–v1.20, ADR-047 v1.0–v1.3) as immediately, unconditionally effective — no
S-21.24 calibration dependency, unlike the two `^Agent$` Cohort A-deferred validators. Discovering
that it, too, currently delivers zero enforcement meant Layer 1's fail-LOUD guarantee had **no
live production trigger at all** as of S-25.01 merge — both effective-enforcement paths (this one
structurally inert, the other two S-21.24-gated) were dormant. This story delivers the first one.

**Confirmed closure design (F1 §2 + F2, architect/product-owner, 2026-09-04):**

- **New PostToolUse companion validator: `validate-factory-path-staged`** (SS-04, BC-4.16.002) —
  the git-staging-exclusivity **detective mirror** of BC-4.16.001. Reuses S-25.01's marker/gate
  machinery (`write_indeterminate_marker`, `should_write_marker`, `classify_outcome`,
  `validate-unvalidated-mutation-marker` both gate arms) verbatim — no new marker mechanism, no
  new WASM-tier-loop branching. Only a new WASM plugin crate + one new `hooks-registry.toml` entry
  are needed. Crate: `crates/hook-plugins/validate-factory-path-staged/`. Registration:
  `event = "PostToolUse"`, `tool = "^Bash$"`, `priority = 161`, `failure_policy = "fail-closed"`,
  `on_error = "continue"`, `timeout_ms = 5000`, native-WASM fuel-axis-only calibration
  (`fuel_cap = max(observed_max × 1.5, 50_000_000)`).
- **Trigger scope: BROAD — unconditional, no command-text pre-filter (human-ratified 2026-09-04,
  FINAL, not provisional).** The companion's internal `git diff --cached --name-only` /
  `git branch --show-current` check runs on **every** completed `PostToolUse ^Bash$` dispatch,
  regardless of whether the triggering command's text looked git-related. The architect
  recommended BROAD over a narrower text-gated alternative because a text-gated internal filter
  would make the detective mirror a near-tautological confirmation of BC-4.16.001's own successes
  and functionally blind to BC-4.16.001's own documented failure modes (Invariant 6 Accepted
  Residuals) — the check being performed is against actual index state, not payload text, so any
  internal text-based pre-filter reintroduces the same under-match risk class the mirror exists to
  close. Cost is bounded: both `exec_subprocess` calls read only git's index metadata and current-
  branch pointer, governed by staged-path cardinality and repository ref state — not by
  `.factory/` cycle-artifact size or triggering payload size, the same "bounded input"
  classification `validate-factory-path-staging` itself received for Cohort A-immediate treatment.
- **ADR-039 §Decision 2 roadmap extension confirmed** — `validate-factory-path-staged` is the
  seventh member, placed in the native-WASM sub-list (alongside `validate-cross-site-
  correspondence`), fuel-axis-only calibration; a validator-specific calibration corpus (synthetic
  ≥500-simultaneously-staged-paths fixture, not the six-member large-`.factory/`-artifact corpus)
  is directed for the eventual formal-verifier/test-writer calibration pass. This registration act
  does NOT require S-21.24 to have merged (S-21.24 governs the separate ADR-039 Phase-4
  CURRENT-DISPATCH-blocking executor wiring for the full seven-validator set).
- **Option (b) (changing `validate-factory-path-staging`'s own `on_error` from `"continue"` to a
  blocking variant) remains REJECTED as primary** — F1 found no infeasibility in option (a), so no
  escalation to option (b) is warranted. `validate-factory-path-staging`'s own registration is
  byte-identical/unchanged by this story (AC-003).

## Acceptance Criteria

### AC-001: `validate-factory-path-staged` reaches the existing marker-write path (traces to BC-4.16.002 Postcondition 3 — INDETERMINATE trigger/AC-001 closure criterion; and BC-1.18.001 Postcondition 4 — durable marker write, generic mechanism invoked)

The new PostToolUse WASM validator `validate-factory-path-staged` MUST be registered in
`hooks-registry.toml` as `event = "PostToolUse"`, `tool = "^Bash$"`, `priority = 161`,
`failure_policy = "fail-closed"`. When this plugin's own WASM execution cannot complete during
either of its `exec_subprocess` calls (fuel exhaustion, epoch timeout, or OutputTooLarge), the
dispatcher MUST classify the outcome as `DispatchOutcome::Indeterminate` (BC-1.18.001 Postcondition
1) and MUST reach `write_indeterminate_marker` (BC-1.18.001 Postcondition 4) — this is the first
Layer-1 validator whose fail-closed assignment has a structurally-reachable PostToolUse trigger
(BC-4.16.002 Postcondition 3).

### AC-002: Existing marker + gate mechanism is reused, not re-implemented (traces to BC-4.16.002 Invariant 5 — reuse-not-reimplementation of S-25.01 marker/gate machinery; and BC-1.18.001 Postcondition 4 / Invariant 4 — generic mechanism, REUSE-UNCHANGED)

`validate-factory-path-staged` MUST NOT introduce a second marker file, a second gate mechanism, or
duplicate `classify_outcome` / `should_write_marker` logic, and MUST NOT introduce any
plugin-specific branching in the tier-execution loop. It reuses `.factory/unvalidated-mutation.marker`,
`write_indeterminate_marker`, `validate-unvalidated-mutation-marker` (both existing gate arms), and
the existing pure-core classification functions from S-25.01 verbatim.

### AC-003: No behavioral change to `validate-factory-path-staging` itself (traces to BC-4.16.002 Invariant 1 — second enforcement instantiation, additive not replacement; and Edge Case EC-003 — sibling's own PreToolUse registration unaffected)

`validate-factory-path-staging`'s own registration (PreToolUse `^Bash$`, `on_error = "continue"`,
`failure_policy = "fail-closed"`, BC-4.16.001) is UNCHANGED by this story. This story adds a
companion validator (`validate-factory-path-staged`); it does not modify or replace the existing
one. Option (b) (changing `on_error`) remains explicitly OUT OF SCOPE for this delivery (see
Context §Confirmed closure design).

### AC-004: ADR-039 §Decision 2 roadmap extension (traces to BC-4.16.002 Traceability — ADR-039 §Decision 2 seventh-member roadmap entry, native-WASM/fuel-axis-only sub-list; architect-owned ADR content per F1 §6 / F2 §3, no independent BC postcondition for the ADR document edit itself)

ADR-039 §Decision 2's exhaustion-leg roadmap MUST be extended to name `validate-factory-path-staged`
(from AC-001) as a seventh member, in the native-WASM sub-list (alongside
`validate-cross-site-correspondence`), fuel-axis-only calibration (`fuel_cap =
max(observed_max × 1.5, 50_000_000)`; calibration corpus: synthetic ≥500-simultaneously-staged-paths
fixture per architect F2 §3.2, not the six-member large-`.factory/`-artifact corpus). This
registration act does NOT require S-21.24 to have merged; it is independent of the ADR-039 Phase 4
CURRENT-DISPATCH-blocking executor wiring that S-21.24 delivers for the full seven-validator set.
The exact ADR-039 §Decision 2 text is finalized in F2 §3.1 and is routed to architect/state-manager
to apply verbatim (not this story's implementer to edit directly).

### AC-005: Layer-1 effective fail-closed count increases from ZERO (traces to BC-1.18.004 Postcondition 4 — companion "Layer-1 effective fail-closed count at S-25.04 merge: N≥1" statement)

After this story merges, BC-1.18.004 Postcondition 4's new companion statement — "Layer-1 effective
fail-closed count at S-25.04 merge: N ≥ 1," attributable to `validate-factory-path-staged`'s live

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-001 | `validate-factory-path-staged` itself fuel-exhausts during its `exec_subprocess` calls for a completed Bash dispatch | Dispatcher classifies INDETERMINATE per `classify_outcome` (S-25.01, unchanged); `write_indeterminate_marker` fires because this validator IS registered PostToolUse (unlike `validate-factory-path-staging`) — this is the exact behavior AC-001 requires (BC-4.16.002 PC3 / EC-001). |
| EC-002 | A Bash command stages/writes files entirely outside `.factory/` | The unconditional BROAD-scope check still runs (`git diff --cached --name-only`, `git branch --show-current`); finds no `.factory/` path staged → passes (BC-4.16.002 PC2 / EC-002). |
| EC-003 | `validate-factory-path-staging` (PreToolUse, BC-4.16.001) still fuel-exhausts independently | Unchanged S-25.01 behavior: no marker written via THIS validator (PreToolUse-only per BC-1.18.001 invariant 4, AC-003); `validate-factory-path-staged` (PostToolUse, this story) is the one that can reach the marker for the corresponding completed write (BC-4.16.002 EC-003). |
| EC-004 | Both `validate-factory-path-staging` (PreToolUse, blocks a `git add` on one dispatch) and `validate-factory-path-staged` (PostToolUse, INDETERMINATE fail-closed on a later dispatch) are involved | Two `plugin.indeterminate` events emitted at most (one per plugin, per BC-3.08.001 Event 8 semantics — unchanged); `(plugin_name, artifact_path)` pairs distinguish the two validators' own INDETERMINATE events by construction; single-marker last-writer-wins policy (BC-1.18.001 invariant 3) applies exactly as it would for any two distinct fail-closed plugins (BC-4.16.002 EC-004). |
| EC-005 | Branch detection fails (`git branch --show-current` non-zero exit, empty output, detached HEAD) during the post-hoc check | Fail-open (BC-4.16.002 PC4 / Invariant 3): exit code 0, advisory warning only — mirrors BC-4.16.001 Invariant 3 exactly; an uncertain branch state is not, on its own, evidence of a violation. |
| EC-006 | `.factory/` path appears staged and current branch is `factory-artifacts` (legitimate state-manager commit) | Passes unconditionally (BC-4.16.002 PC2 / EC-006), mirroring BC-4.16.001 PC3. |
| EC-007 | Triggering Bash command was not git-related at all (e.g. `npm test`) | The check still executes unconditionally per BROAD scope (Precondition 2) — NOT a text-based fast-pass skip; resolves via PC2 because `git diff --cached --name-only` returns nothing relevant. An EARLIER git-plumbing/script/alias action that already staged a `.factory/` path before this non-git command ran would still be caught — the exact residual-risk class BROAD scope exists to close (BC-4.16.002 EC-007). |
| EC-008 | `validate-factory-path-staged` crashes for a non-resource-exhaustion reason (`Trap::UnreachableCodeReached`, host-ABI mismatch) | `on_error = "continue"` applies: advisory only, no block, no marker (BC-4.16.002 PC5 / EC-008). |
