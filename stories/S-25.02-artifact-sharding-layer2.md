# S-25.02: Artifact Sharding Layer 2 — Size-Triggered Shard Rotation for Cycle Artifacts

## Narrative

- **As a** factory pipeline operator who has Layer 1 (INDETERMINATE markers, BC-1.18.001-004) deployed
- **I want** the append-only cycle artifacts (decision-log.md, burst-log.md, lessons.md,
  session-checkpoints.md) AND `BC-INDEX.md`'s two independent size drivers (its frontmatter
  `changelog:` array and its per-subsystem body tables) to be automatically split into capped
  shards when they approach the validator-completion fuel envelope, with a deterministic,
  native-dispatcher size/item-count rule enforced by a PreToolUse gate rather than LLM-side
  awareness
- **So that** no shard ever exceeds the size at which fuel-exhaustion INDETERMINATE events fire,
  eliminating the root cause of Layer-1 marker writes BY CONSTRUCTION (for both mechanism-A
  append-logs and BC-INDEX's own size drivers — BC-INDEX alone produced 45.2% of the first 708
  observed `plugin.indeterminate` events) and making the Cohort B validators
  (`validate-burst-log`'s Edit/Write/MultiEdit arm, `regression-gate`, `convergence-tracker`) safe
  to flip to `failure_policy = "fail-closed"`

## Context / Feature Summary

**Registered at:** F3 story-decomposition burst, validation-integrity-layer1 cycle, 2026-08-30
(story-writer). **Populated at:** F3 incremental-stories burst, 2026-09-06 (story-writer), from
the F2-converged, human-ratified spec. Source: ADR-047 §Decision 8b (originally: Ratified Future
Phase Layer 2) elaborated into ADR-051 (accepted v1.8, D-1167) — Two-Mechanism Size-Triggered
Shard Rotation for Cycle Append-Logs and BC-INDEX Sharding.

**Why Layer 2 follows Layer 1 (not concurrent):** Layer 1 instruments the INDETERMINATE failure
mode (detects and surfaces it). Layer 2 attacks the root cause (large artifacts). Layer-1
`plugin.indeterminate` production forensics (available after S-25.01 merged) confirmed
`BC-INDEX.md` alone accounts for 45.2% of the first 708 observed events, directly shaping ADR-051's
decision to widen scope beyond the original mechanism-A-only draft to also cover BC-INDEX's two
independent size drivers (D-1166, human widest-scope decision).

**Two mechanisms, three artifact shapes, one native gate (ADR-051 §Decision 1):**

1. **Mechanism A — byte-size-denominated shard rotation for the four append-only cycle logs**
   (`decision-log.md`, `burst-log.md`, `lessons.md`, `session-checkpoints.md`). A `stat()`-only
   size check (BC-1.18.005) triggers a roll-before-write (BC-1.18.006: publish the current
   content as a NEW sealed file via copy, then atomically replace the canonical file's content
   with empty in place — never a rename-away) plus retention/compaction (BC-1.18.007) plus a
   mandatory one-time backfill-split of the four pre-existing oversized files (BC-1.18.008).
2. **Mechanism B1 — item-count-denominated rotation of `BC-INDEX.md`'s frontmatter `changelog:`
   array** (BC-INDEX's dominant size driver, 177,305 of 539,713 bytes measured 2026-09-05), reusing
   the already-shipped `rotate_changelog` primitive (ADR-049 §Decision 6, CAP-042) via a
   single-actor block-and-retry contract (BC-1.18.009) plus a governed one-time cold-start backfill
   migration (BC-1.18.012, ~1,997 unrotated items).
3. **Mechanism B2 — per-subsystem body-table sharding of `BC-INDEX.md`'s ten `### SS-NN` sections**
   into individually-addressable shard files, with zero-lookup first-level addressing (via the
   already-authoritative ARCH-INDEX BC-S-prefix→SS-NN mapping, POLICY 6) and manifest-based
   second-level sub-sharding for the two subsystems (SS-05, SS-06) already over cap on section size
   alone (BC-1.18.010), plus a governed one-time migration (BC-1.18.011).

**Shard cap formula (production-grade; ADR-051 §Decision 2, BC-1.18.005 Postcondition 4/6):**
```
shard_cap_bytes <= (PRACTICAL_FUEL_CEILING / WORST_CASE_FUEL_PER_BYTE) - MAX_SINGLE_RECORD_BYTES - SAFETY_MARGIN
```
Constants are PROVISIONAL until the F4 synthetic calibration harness runs (owned by
performance-engineer, co-run with implementer per BC-1.18.005 Postcondition 7); the formula SHAPE
is locked now (illustrative worked value: 49,152 bytes / 48 KiB), the numbers are not. Effective
per-artifact cap is the MINIMUM across every Cohort B validator that reads that artifact
(Cross-Validator Minimum Rule, BC-1.18.005 Postcondition 5).

**Three governed one-time migrations are MANDATORY companions, not follow-ups** (BC-1.18.008 for
mechanism A, BC-1.18.011 for B2, BC-1.18.012 for B1) — per CLAUDE.md's production-grade default, a
gate that only prevents FUTURE overflow without retroactively shrinking the artifacts already
producing the majority of observed INDETERMINATE events is an incomplete delivery of this story's
own stated purpose.

**Cohort B flip is the capstone (BC-7.08.001):** once BC-1.18.005/006's gate is F4-locked AND
BC-1.18.008's backfill-split has COMPLETED (hard sequencing gate — flipping fail-closed before the
pre-existing oversized files are split would immediately re-trigger the exact INDETERMINATE loop
this story exists to eliminate), `hooks-registry.toml` assigns `failure_policy = "fail-closed"` to
exactly three registry entries: `validate-burst-log`'s `^(Edit|Write|MultiEdit)$` arm ONLY (its
sibling `^Bash$` git-commit chain-detection arm is exec-free, unrelated, and explicitly out of
scope), `regression-gate`, and `convergence-tracker`.

**SS-04 touchpoint (ADR-051 §Decision 6, adjudicated 2026-09-06):** the retention/compaction
policy's validator enumeration directly audits four SS-04-owned WASM crates
(`validate-dispatch-advance`, `validate-state-structure`, `validate-closes-completeness`,
`validate-cross-site-correspondence`) for archival-scheme correctness, and imposes a new
archive-inclusive-glob obligation on POLICY-1's (`append_only_numbering`) SS-04-adjacent
enforcement path (`consistency-validator`/adversary-prompt agent level, `lint_hook: null`) — the

## Acceptance Criteria

### AC-001: Native `stat()`-only deterministic size-trigger, zero-cost bypass, match-first blast-radius scoping (traces to BC-1.18.005 postcondition 1, postcondition 2, invariant 3, edge cases EC-018, EC-019)

A native (non-WASM) dispatcher function, invoked from the PreToolUse handling path before the
registry-driven plugin loop, checks the tool call's target path against a `[[shard]]` config
table. An unmatched path returns `Continue` immediately with zero `stat()` calls (zero-cost bypass
for the ~99% of `Edit`/`Write`/`MultiEdit` calls Layer 2 does not touch). A matched path reads
ONLY the current shard's byte size via filesystem metadata — never file content, never a WASM
sandbox, never a fuel budget — so the check itself is structurally incapable of producing a
`plugin.timeout`/`plugin.indeterminate` event.

**Match-first blast-radius scoping (added BC-1.18.005 v1.12, S-25.02 Phase F4 LOCAL adversary
cluster-1 pass-6 finding F-C1-P6-001, LOW pending-intent, product-owner adjudication).**
`ShardRegistry::load()` performs STRUCTURAL TOML deserialization only; the new `validate_entry(&
ShardEntry)` function carries all semantic checks (EC-009/EC-011/EC-012/EC-013/EC-015/EC-016/
EC-017) and runs AFTER `find_matching_entry` resolves the current dispatch's target path, and ONLY
against the MATCHED entry. An unmatched target returns `Continue` — and a target matching a
DIFFERENT, well-formed entry proceeds under normal gate logic — even if a SIBLING `[[shard]]`
entry is semantically malformed: a sibling's config typo no longer blocks unrelated dispatches
(EC-018). The one residual exception is whole-file STRUCTURAL TOML parse failure — invalid TOML
syntax, or any entry omitting a non-`Option`-typed field required for `toml::from_str` to succeed
(`artifact_stem`, `shard_cap_bytes`, or any of the four `cap_formula_inputs` fields) — which STILL
fails loud (`HookResult::Error`) for every `Edit`/`Write`/`MultiEdit` dispatch while the config
file exists, matched or not, because `find_matching_entry` cannot run at all without a
successfully deserialized registry (EC-019). This narrows the ENTRY-SCOPE of every existing
fail-loud check cited elsewhere in this story (AC-005, AC-023) from "every entry in the file,
every dispatch" to "the entry matched against the current dispatch's target path, evaluated at
entry-match time" — it does NOT change any cited check's substantive fail-loud outcome, numeric
threshold, or "before any write against that artifact" timing guarantee (BC-1.18.005 postcondition
1 "Blast-radius scoping" sub-paragraph, invariant 3 extension).

### AC-002: Per-tool-semantics projected-size formula (traces to BC-1.18.005 postcondition 3, edge case EC-005)

`projected_size` is computed per-tool: for `Write`, `projected_size = len(content)` alone
(`current_shard_bytes` is NOT added — `content` is the complete post-apply file). For
`Edit`/`MultiEdit`, `projected_size = current_shard_bytes + net_delta_bytes` (the net length delta,
summed across all edit blocks for `MultiEdit`, which may be negative). `projected_size <=
shard_cap_bytes` (inclusive boundary) returns `Continue`; `> shard_cap_bytes` triggers the roll
sequence.

**Documentary note (non-AC, no code obligation — BC-1.18.005 v1.11 Postcondition 3 "Known formula
gap").** The `Edit`/`MultiEdit` net-delta formula above computes a SINGLE-occurrence
`len(new_string) - len(old_string)` delta and does not account for `replace_all: true`'s occurrence
multiplicity (actual on-disk delta is `occurrence_count(old_string, current_file_content) x
(len(new_string) - len(old_string))`), which can under-count `projected_size` for a bulk
`replace_all` edit. Product-owner has explicitly adjudicated this gap DEFERRED to BC-1.18.006
(cluster 2) — not a cluster-1/S-25.02 obligation — because closing it requires a full-content read
that departs from Postcondition 2's stat()-only guarantee and because this cluster's trigger is
non-blocking today (a fired trigger only `tracing::warn!`s and returns `Continue`; the roll/block
outcome does not exist until BC-1.18.006 lands). No AC or code change follows here; see
BC-1.18.005 Postcondition 3's "Known formula gap" sub-paragraph and Related BCs for the explicit
deferral anchor.

### AC-003: Cross-Validator Minimum Rule (traces to BC-1.18.005 postcondition 5)

An artifact's effective `shard_cap_bytes` is the MINIMUM across every Cohort B validator that reads
it (e.g., `burst-log.md`'s cap is `MIN(cap_for(validate-burst-log), cap_for(regression-gate),
cap_for(convergence-tracker))`; `decision-log.md`/`lessons.md`/`session-checkpoints.md`'s cap
excludes `validate-burst-log`'s per-plugin cap, since that validator does not read them). A single
global cap across all four mechanism-A artifacts MUST NOT be used.

### AC-004: Cap-formula constants are config, not hardcoded — F4 calibration harness (traces to BC-1.18.005 postcondition 6, postcondition 7)

`PRACTICAL_FUEL_CEILING`, `WORST_CASE_FUEL_PER_BYTE`, `MAX_SINGLE_RECORD_BYTES`, and
`SAFETY_MARGIN` are read from the `[[shard]]` config, never embedded as Rust constants in
`shard_manager.rs`. A synthetic calibration harness (performance-engineer, co-run with
implementer) locks the final numeric values before this BC's postconditions are treated as final,
re-run whenever `DEFAULT_FUEL_CAP` changes at the operator level; if a Cohort B plugin's fuel/byte
relationship is superlinear, `WORST_CASE_FUEL_PER_BYTE` uses the LOCAL marginal rate at the largest
tested size, never the global average slope.

### AC-005: Item-count trigger for the `"frontmatter-changelog-array"` shape, with `low_water_mark` config (traces to BC-1.18.005 postcondition 1, postcondition 8, edge cases EC-008, EC-010, EC-011, EC-012, EC-014, EC-016, EC-020, EC-021, EC-022)

The SAME native gate dispatches to an item-count trigger (`current_item_count + 1 > N`) when the
`[[shard]]` config entry declares `shape = "frontmatter-changelog-array"`, distinguished from the
`"flat"` byte-size shape by that field alone (never content-sniffed). A sibling `low_water_mark`
config value (default `floor(N/2)` when omitted) declares the rotation TARGET — never `N` itself
and never a hardcoded `N-1`. Fail-loud (`HookResult::Error`) on `low_water_mark >= N` (the `== N`
boundary included) or negative; any legal value in `(floor(N/2), N)` up to and including `N-1`
loads normally but emits a non-fatal `tracing::warn!` amortization advisory.

**Missing-file / first-write create path (added S-25.02 Phase F4 LOCAL adversary cluster-1 pass-3
finding F-C1-P3-001, product-owner adjudication, BC-1.18.005 v1.9).** When the
`"frontmatter-changelog-array"`-shaped target artifact does not yet exist on disk — a legitimate
first-ever `Write` that CREATES the artifact — `read_changelog_item_count` MUST map
`io::ErrorKind::NotFound` to `Ok(0)`, treating the not-yet-existing artifact as holding 0 existing
changelog items, mirroring EC-004's flat-shape missing-file-is-zero precedent (BC-1.18.005
postcondition 8's missing-file/first-write sub-bullet). The item-count trigger then evaluates

### AC-006: Staged, crash-recoverable roll-before-write sequence — copy-then-atomic-truncate, never rename-away, byte-level I/O, write-once (non-empty-destination) sealed shards with a bounded 0-byte-destination reclaim, empty-canonical short-circuit, and self-heal zero-byte-seal guard (traces to BC-1.18.006 postcondition 1, postcondition 2, postcondition 8, invariant 2, invariant 3, invariant 9, edge cases EC-021, EC-022, EC-024, EC-025)

When a roll is triggered, the gate performs, in order, before returning any `HookResult`: (a) read
the canonical file's current content (once, roll-only); (b) publish the sealed shard as a brand-NEW
file at `<stem>.<seq:04>.md` via `publish_sealed_shard`'s exclusive-create primitive, `write_exclusive`
— **CORRECTED (BC-1.18.006 v1.8→v1.9, cluster-2 LOCAL adversary pass-8 finding F-C2-P8-001, MEDIUM):
step (b) is `write_exclusive` (a `std::fs::hard_link`-based no-clobber create onto a not-yet-existing
destination, failing atomically with `ErrorKind::AlreadyExists` on collision), NEVER `write_atomic`'s
rename-based create — a plain `rename()` unconditionally overwrites an existing destination and
structurally cannot express step (b)'s write-once, refuse-if-exists contract (Postcondition 8 below).**
(c) atomically REPLACE the canonical file's content with empty via the SAME `write_atomic`
temp-file-then-rename primitive (never a delete-then-create, never a rename of the canonical path away
— the canonical path resolves to SOME valid file at every observable instant); (d) atomically publish
the updated shard-index TOML. Steps (a)-(b) failure returns `HookResult::Error` (`E-SHD-001`) with the
canonical file untouched; step (c) failure after (b) succeeded self-heals via resume-from-truncate on
the next dispatch (`E-SHD-006`); step (d) failure after (c) succeeded self-heals via index
reconciliation on the next dispatch (`E-SHD-007`). Steps (c) and (d) remain exactly as before — this
correction is scoped to step (b) alone.

**Empty-canonical short-circuit — no roll when there is no history to preserve, already shipped
(NEW, BC-1.18.006 v1.6→v1.7, cluster-2 LOCAL adversary pass-3 finding F-C2-P3-001, MAJOR, edge case
EC-021).** The four-step sequence above applies ONLY when the canonical file's content is non-empty
at the moment step (a) would read it. When BC-1.18.005's size-trigger fires but the canonical file
is already exactly 0 bytes at that moment — the incoming call's own payload alone exceeds
`shard_cap_bytes` against an already-empty shard, with no pre-existing history to preserve —
`execute_roll` performs NONE of steps (b)-(d) and returns `Ok(None)` rather than executing a
zero-content roll: no shard file is published, the canonical file is left untouched at 0 bytes, and
no `[[shard]]` index entry is appended. This is a deliberate, correct short-circuit, not an
omission: publishing a sealed shard here would permanently consume a `seq` slot for zero
informational content and append a `[[shard]]` entry with `bytes_at_seal = 0` — banned
unconditionally by Invariant 9 below. The trigger-fire branch still returns `HookResult::Block`
(Invariant 1 is unaffected — the oversized call is never applied), but via the distinct
empty-canonical template AC-007 specifies below, not the unified rotate-and-retry template, because
there is no history to "rotate." **This AC extension documents already-shipped behavior** —
`execute_roll`'s `Ok(None)` short-circuit is already implemented; no code or test change follows
from this AC extension.

**Self-heal MUST refuse a 0-byte sealed-shard candidate, never index it — NEW pending Red Gate
obligation (BC-1.18.006 v1.6→v1.7, cluster-2 LOCAL adversary pass-3 finding F-C2-P3-002, MINOR,
invariant 9, edge case EC-022).** No `[[shard]]` index entry may ever have `bytes_at_seal = 0`, and
this binds ALL paths that append `[[shard]]` entries, not only `execute_roll` — `execute_roll`
already satisfies this structurally (the empty-canonical short-circuit above and Postcondition 3's
unconditional per-shard cap guarantee together ensure every prospectively- or retroactively-sealed
shard copies real, non-empty content). The gap is in the two self-heal reconciliation paths —
`self_heal_reconcile_missing_index_entries` (the `E-SHD-007` recovery, this AC's own
step-(d)-failure self-heal above) and `self_heal_resume_from_truncate` (the `E-SHD-006` recovery,
this AC's own step-(c)-failure self-heal above) — which append `[[shard]]` entries by inspecting
whatever sealed-shard-shaped file (`<stem>.<seq:04>.md`) is already on disk, with no equivalent
non-empty guard. Both self-heal paths MUST refuse to append a `[[shard]]` entry for a candidate
sealed-shard file whose on-disk size is exactly 0 bytes: SKIP that candidate (append no entry for
it, continue reconciling any other genuinely-orphaned entries in the same pass), and emit a
`tracing::warn!` diagnostic — never a `HookResult::Error`, since a stale externally-created 0-byte

**Write-once sealed shards for NON-EMPTY destinations, with a bounded 0-byte-destination reclaim —
`publish_sealed_shard` MUST refuse to overwrite non-empty content, NEW pending Red Gate obligation
(BC-1.18.006 v1.7→v1.8, cluster-2 LOCAL adversary pass-4 finding F-C2-P4-002, MINOR, postcondition 8,
edge case EC-024, defense-in-depth; SCOPING + 0-byte reclaim added v1.8→v1.9, cluster-2 LOCAL adversary
pass-8 findings F-C2-P8-001/F-C2-P8-002, MEDIUM/MEDIUM, edge case EC-025).** A sealed shard, once
published, is immutable content — step (b)'s seal-publish attempts `write_exclusive`'s atomic
exclusive-create (`std::fs::hard_link` onto a not-yet-existing destination; **CORRECTED, F-C2-P8-001:
never `write_atomic`'s rename, which cannot itself express a refuse-if-exists contract**). If the
`AlreadyExists` collision is against a destination that is NON-EMPTY, the gate MUST NOT overwrite it —
it returns `HookResult::Error` (NEW `E-SHD-009`, "sealed-shard immutability violation: refusing to
overwrite an existing seal at `<path>`") and applies NEITHER the seal NOR any of the roll's other steps
for this attempt (no truncate, no index publish); the pre-existing destination file is left completely
untouched, byte-identical. This guard applies to step (b) in BOTH its prospective invocation (this
AC's own Postcondition 1 sequence) and its retroactive invocations (AC-024/AC-025's catch points (i)
and (ii), which reuse this exact step). **Why this is defense-in-depth, not the primary fix:** the
primary, root-cause fix is AC-024's corrected self-heal-first sequencing (below) — under that fix, a
well-formed dispatch should never attempt to publish at a colliding `seq`. This write-once guard is
the SECOND, independent layer, converting any residual seq-collision (a self-heal reconciliation bug,
an external actor placing a same-named file on disk, or a future code path not yet anticipated) into
a loud, actionable, fail-safe error rather than a silent overwrite of durably-sealed history.

**0-byte-destination reclaim exception (NEW, BC-1.18.006 v1.8→v1.9, cluster-2 LOCAL adversary pass-8
finding F-C2-P8-002, MEDIUM, edge case EC-025) — resolving the Invariant-9 interaction.** A 0-byte file
at the destination `seq` path is, by Invariant 9's own reasoning, structurally NEVER a genuine orphan
of this BC's own write paths (`execute_roll`'s prospective and retroactive rolls alike only ever seal
non-empty content) — it can only be an external anomaly (a human `touch`, a botched manual recovery, a
corrupted transfer) with no durable sealed history to protect. Left un-addressed, this interacts with
Invariant 9's self-heal skip-and-warn guard (above) to produce a PERMANENT DEADLOCK: self-heal never
indexes the 0-byte file, so `next_seal_seq` never advances past it, and every future roll attempt
recollides with the SAME 0-byte file forever. **REQUIRED resolution — the write-once refusal above
applies ONLY to a NON-EMPTY pre-existing destination; a 0-byte pre-existing destination is safe to
replace, and `publish_sealed_shard` MUST reclaim it rather than refuse:** if `write_exclusive`'s
exclusive-create fails with `AlreadyExists`, `publish_sealed_shard` `stat()`s the pre-existing
destination exactly once; if its size is exactly 0 bytes, it unlinks the 0-byte file and retries
`write_exclusive` exactly ONCE (never in a loop — bounded to a single reclaim attempt, so a racing
concurrent writer cannot induce unbounded retries). If that single retry ALSO fails with
`AlreadyExists` (a genuine race: a concurrent writer placed real content at the path between the
`stat()` and the retry), OR if the pre-existing destination's size was non-zero to begin with, the gate
fails loud with `E-SHD-009` exactly as specified above — the 0-byte exception never weakens the
non-empty case's write-once guarantee. A successful 0-byte reclaim emits a `tracing::warn!` diagnostic
naming the reclaimed path but does NOT block or fail the current dispatch. **This AC extension is a
NEW, unimplemented Red Gate obligation** — TDD'd from scratch under this story's `tdd_mode: strict`:
(i) a fixture that pre-creates a NON-EMPTY file at the destination `seq` path before a roll
(prospective or retroactive) attempts to publish at that same `seq`, asserting `HookResult::Error`/
`E-SHD-009` is returned, the pre-existing file's content is byte-identical after the attempt (never
overwritten), and no truncate or index-publish occurs (EC-024); (ii) a fixture that pre-creates a
0-BYTE file at the destination `seq` path, asserting the roll SUCCEEDS (the 0-byte file is reclaimed,
the new seal content is durably published at that exact path, no `E-SHD-009`); and (iii) a fixture
where a concurrent writer places real content at the path between the probe and the retry, asserting
the race case still fails loud with `E-SHD-009` (EC-025) — all three landing under T-4 (see Tasks).

current/latest shard, and the whole-corpus glob `<stem>*.md` sorts sealed shards before the current
file with zero special-casing.

### AC-013: Mandatory one-time backfill-split of the four pre-existing oversized append-logs (traces to BC-1.18.008 postcondition 1, postcondition 2, postcondition 3)

Executed exactly once, at F4 activation (never as an ongoing mechanism), the backfill-split
partitions each of the four pre-existing monolithic files into sealed shards plus a fresh current
file via a deterministic, greedy, boundary-preserving packing procedure: whole records (per the
artifact's Record-Boundary Marker Table) are accumulated into the current shard, in original-file
order, until appending the next whole record would push the shard's byte size past
`shard_cap_bytes`; at that point the shard is sealed AS-IS — even with slack remaining below the
cap, since no partial record may ever be appended to close that slack — and a new shard begins.
This is the ONLY split-point rule; splitting occurs ONLY at structural record boundaries native to
the artifact's own format (never mid-record, and never keyed on heading level alone).

**`ceil()` is a lower bound, not the exact target (BC-1.18.008 v1.3).**
`ceil(current_bytes / shard_cap_bytes)` is a deterministic LOWER BOUND on the resulting shard count
(`actual_count >= ceil(current_bytes / shard_cap_bytes)`, with equality holding only when every
shard's greedy-packed content leaves less than one additional whole record's worth of slack under
the cap) — useful for sizing estimates and progress-reporting denominators, but MUST NOT be
asserted, in code, tests, or documentation, as the exact resulting shard count. The exact count is
whatever the greedy boundary-preserving packer actually produces against the artifact's real
record-size distribution at F4 execution time.

The full shard index is published for the complete pre-existing history in the same operation,
composing immediately with AC-010's retention policy if the ACTUAL packed shard count — never the
`ceil()` estimate — already exceeds `retention_count`.

**Backfill Recovery Manifest is an additive `ShardIndex` struct field, never a side-channel table
(BC-1.18.008 v1.9, F-C3-P9-004, BLOCKING).** The `[backfill_manifest]` data AC-014's
Recovery-Confirmation Rule relies on is `backfill_manifest: Option<BackfillManifest>`, an ORDINARY
ADDITIVE FIELD of the shared `ShardIndex` struct itself (`#[serde(default,
skip_serializing_if = "Option::is_none")]`) — never a hand-appended side-channel TOML table read
and written by dedicated helper functions (`read_backfill_manifest`/`write_shard_index_for_backfill`)
entirely outside that struct, which was v1.6's original (now-superseded) design. Because every
function that loads a `ShardIndex`, mutates it, and writes it back — AC-006's ongoing per-write roll
(`publish_shard_index_update`) and both self-heal reconciliation paths
(`self_heal_resume_from_truncate`, `self_heal_reconcile_missing_index_entries`) — already
re-serializes the WHOLE `ShardIndex` struct, the Manifest field now round-trips through all of them
automatically, as an ordinary consequence of Rust struct-field serialization — no special-case
preservation code is required, or permitted, at any of those sites. The side-channel
`BackfillManifestWrapper`/`BackfillManifestDocument` serialization helpers and
`read_backfill_manifest`'s standalone re-parse are RETIRED by this amendment; `load_shard_index`
alone is sufficient to read the Manifest.

**Composability with a pre-existing shard set from an ordinary AC-006 roll (BC-1.18.008 v1.9,
F-C3-P9-004, BLOCKING).** When the backfill-split runs against an artifact whose shard-index already
exists with a non-empty `[[shard]]` array but `backfill_manifest: None` — the expected
roll-before-backfill ordering in practice, since these four artifacts are exactly the ones most
likely to trip AC-001's cap gate and receive an ordinary roll BEFORE the F4 mandatory backfill ever
runs for them — this state is neither "already migrated" nor corrupted/ambiguous: the mandatory
one-time migration for this artifact has simply never run yet. The backfill-split proceeds as a
genuine first-ever run, with two adjustments: (1) `original_bytes`/`original_sha256` are always
computed from the canonical file's CURRENT on-disk content at the moment this invocation begins —
never from a reconstructed notion of "the full historical monolithic file" — since content a prior
roll already sealed is durably preserved in ITS OWN pre-existing `[[shard]]` entries, entirely
outside this Manifest's scope; (2) the backfill's own newly-sealed shard entries are APPENDED to the
pre-existing `[[shard]]` array, with `seq` numbering continuing from `existing_max_seq + 1` — never
renumbering, duplicating, or otherwise disturbing the pre-existing rolled entries, which remain
exactly as AC-006's roll mechanism published them (append-only, POLICY-1 consistent).

**Leading-preamble handling (BC-1.18.008 v1.4, F-C3-P3-001).** Every one of the four artifacts
begins with a leading preamble (the YAML frontmatter block, any title/intro prose, and — for
`decision-log.md` only — the table header plus its `|---|...|` separator row preceding the first
`| D-NNN |` record). The preamble is a single atomic, indivisible packing unit, resolved once
BEFORE record-based greedy packing begins: **normal case**
(`preamble_bytes + first_record_bytes <= shard_cap_bytes`) — the preamble rides in the same shard
as the first record, unchanged from today's behavior; **overflow case**
(`preamble_bytes + first_record_bytes > shard_cap_bytes`) — the preamble seals as its own
zero-record shard (`seq=1`, `is_preamble_shard: true`) BEFORE record packing starts fresh at the
first record; **degenerate case** (the preamble ALONE exceeds `shard_cap_bytes` — not reachable for
any of the four mandatory artifacts at current measured preamble sizes, but specified for
completeness) — the preamble seals as its own oversized shard under the SAME `oversized_record:
true` exception AC-014 already establishes for an oversized single record, not a fail-loud abort. A
preamble shard receives a `[[shard]]` index entry exactly like a record-bearing shard
(`records: 0`, plus `is_preamble_shard: true` and, in the degenerate case, `oversized_record: true`)
and is NOT exempt from this AC's own retention-composition clause above — being always `seq=1`, it
is typically the FIRST candidate archived once the artifact accumulates more than
`retention_count` shards.

### AC-014: Backfill-split content-preservation verification, per-shard-cap enforcement, crash-atomicity, idempotency (traces to BC-1.18.008 postcondition 5, postcondition 6, invariant 3, invariant 4, invariant 5)

Before the original monolithic file's role is retired, the backfill-split verifies: (a) the
concatenation of all resulting shards in order reproduces the original file byte-for-byte; (b)
every record appears in exactly one resulting shard (never zero, never two); and (c)
**(BC-1.18.008 v1.4, F-C3-P3-001)** every sealed shard's `bytes_at_seal` is `<= shard_cap_bytes`,
EXCEPT a shard explicitly flagged `oversized_record: true` in the shard index (the oversized-single-
record exception, or AC-013's degenerate oversized-preamble case) — this per-shard-cap check MUST
be executed explicitly against the actual bytes written to each sealed shard file, never merely
assumed to hold because the packing procedure ran.

**Post-hoc disk read-back required, not an in-memory-only length check (BC-1.18.008 v1.6,
F-C3-P6-002 ruling).** "The actual bytes written to disk," in clause (c) above and in checks (a)/
(b), means a FRESH READ-BACK of each sealed shard file from disk, performed AFTER that shard's
write completes, compared against the in-memory partition buffer that was intended to be written —
checking only the in-memory buffer's length BEFORE issuing the write does NOT satisfy any of (a),
(b), or (c). Staging sequence: stage each partition in memory → write it to its staged/temp path →
READ BACK the just-written file from disk → verify the read-back bytes' length (and, for (a)/(b),
full byte-for-byte content and record accounting) against the in-memory partition that was intended
→ only THEN proceed to the atomic index-publish and canonical-truncate sequence below. An
in-memory-only check cannot detect a write that silently truncated, partially flushed, or otherwise
landed corrupted bytes on disk — precisely the failure this gate exists to catch before the
original monolithic file's content becomes unrecoverable except via git history.

Each of (a), (b), (c) is a hard gate — failure aborts the operation with the original file left
untouched (`E-SHD-003`, fail-loud, never partial-and-silent).

**Idempotency is keyed on Manifest presence, never bare shard-index existence (BC-1.18.008 v1.9,
F-C3-P9-004, BLOCKING, supersedes the prior file-existence-only reading).** Bare shard-index-FILE
existence, or a non-empty `[[shard]]` array by itself, is NEVER sufficient evidence of a completed
or in-progress backfill-split — an index may exist, with real sealed shards, purely because AC-006's
ordinary per-write roll mechanism sealed it before the mandatory one-time backfill-split ever ran for
that artifact (the roll-before-backfill ordering AC-013's Composability clause covers). The
already-migrated check MUST load the shard-index (not merely `stat()` the file) and test
`index.backfill_manifest.is_some()`. A `false` result (index present, Manifest absent) routes to
AC-013's Composability clause as a genuine first-ever backfill run — NEVER to the idempotency
disposition list below and NEVER to a fail-loud `E-SHD-011`/`E-SHD-012` disposition. Only a `true`
result (Manifest confirmed present) proceeds to the Recovery-Confirmation Rule below.

**Recovery-Confirmation Rule: exact whole-file `(length, SHA-256)` against the Backfill Recovery
Manifest, never a structural byte-prefix heuristic (BC-1.18.008 v1.6, F-C3-P6-001).** The staged,
validated results become durable via TWO SEQUENTIAL writes: (i) the shard-index — every `[[shard]]`
entry AND the Backfill Recovery Manifest (now an ordinary `backfill_manifest` field of the
`ShardIndex` struct per AC-013's Schema-location correction) recording `original_bytes`/
`original_sha256` (the pre-split monolithic file's exact byte length + SHA-256) and `final_bytes`/
`final_sha256` (the intended final partition's exact byte length + SHA-256), both computed once at
split time from the same in-memory `original_content` buffer — is published first, atomically; (ii)
the canonical file is then truncated-in-place to hold only that final partition's bytes. On any
later invocation against an artifact whose shard-index's `backfill_manifest` field is CONFIRMED
present (per the idempotency check above), the operation reads the canonical file's CURRENT on-disk
bytes exactly once, computes their exact `(length, SHA-256)`, and resolves to exactly one of three
dispositions by comparing against the Backfill Recovery Manifest's two recorded pairs — NEVER by
comparing the canonical bytes against a re-concatenation of already-sealed shards, which
false-positives whenever a sealed shard's content legitimately recurs as a genuine prefix of the
final partition's own content: (1) **SAFE** — matches `(final_bytes, final_sha256)`: step (ii)
already completed; no write is issued; the artifact is reported already migrated. (2)
**DANGEROUS**, unambiguously confirmed — matches `(original_bytes, original_sha256)`: step (ii)
never ran (or crashed before writing); recovery completes it via the **Manifest-Authoritative
Slice-and-Verify Rule** below. (3) **AMBIGUOUS** — matches NEITHER recorded pair: the on-disk state
has been modified by something other than this migration's own two-phase publish sequence, or is
corrupted. This MUST fail loud (`E-SHD-011`) and MUST NOT write anything to the canonical file;
recovery halts for operator investigation, never silently defaulting to either the SAFE or
DANGEROUS disposition.

**Residual `MissingBackfillManifest` disposition (BC-1.18.008 v1.9, F-C3-P9-004) — what `E-SHD-011`
form (b) legitimately covers going forward.** Once idempotency is redefined above to require
CONFIRMED Manifest presence before this Recovery-Confirmation Rule ever runs, the ordinary
roll-before-backfill case (index present, Manifest absent) is no longer routed to a heal/
recovery-confirmation check at all — it is a fresh backfill run (AC-013's Composability clause), not
an error. `MechanismABackfillError::MissingBackfillManifest` (`E-SHD-011` form (b)) therefore now
fires ONLY in the genuinely residual case: the upfront already-migrated check confirms
`backfill_manifest.is_some()`, routing execution into the heal-or-confirm path, but THAT path's own
independent re-read of the same index file then finds `backfill_manifest` absent — a genuine TOCTOU
race (the index file was concurrently rewritten by a manifest-dropping operation between the two
reads; structurally foreclosed going forward by AC-013's Schema-location correction for every
in-tree write path, but not for an out-of-band hand edit or a legacy pre-amendment artifact) or
on-disk corruption of the `backfill_manifest` table specifically. This is the ONLY remaining
legitimate citation for `E-SHD-011` form (b) — never the ordinary roll-before-backfill case, which
now correctly routes to a fresh backfill run instead.

**Manifest-Authoritative Slice-and-Verify Rule: the manifest is a VERIFIER of the healed content,
never a STORE of it (BC-1.18.008 v1.7, F-C3-P7-001).** `final_bytes`/`final_sha256` are a LENGTH
and a HASH — the manifest records no content of its own, so the confirmed DANGEROUS window's
healed content is ALWAYS obtained by slicing the canonical file's own current bytes, never by
"writing the manifest's own recorded `final_bytes` content" as if it were stored (the v1.6 wording
this rule corrects). The heal proceeds through three ordered gates: (1) derive
`offset = original_bytes - final_bytes`, both operands read from the Manifest itself — NEVER by
summing the shard-index's per-shard `bytes_at_seal` fields, an independently-corruptible source
distinct from the Manifest — and take `sliced = canonical_bytes[offset..]`; (2) verify BOTH
`sliced.len() == final_bytes` AND `sha256(sliced) == final_sha256` BEFORE writing anything; (3) on
success, atomically write the verified slice via `write_atomic`; on ANY mismatch, write nothing and
fail loud with **NEW `E-SHD-012`** — distinguished from the top-level AMBIGUOUS `E-SHD-011` by
firing one level deeper, after the `(length, hash)` check has already confirmed the DANGEROUS
window, during this mandatory pre-write slice verification. A prior implementation pass derived the
offset by summing shard-index `bytes_at_seal` entries and wrote the resulting slice WITHOUT
verifying it against `final_bytes`/`final_sha256` at all — a corrupted or stale `bytes_at_seal`
value therefore yielded a silent mis-heal (record duplication or truncation) with no check; this
rule closes that gap by making the offset Manifest-derived and the write conditional on
independent verification, regardless of how the offset was derived.

The operation is safely re-runnable from scratch after a pre-staging interruption, and idempotent
against an already-migrated artifact solely via the SAFE disposition above — never via a
structural byte-prefix comparison against sealed-shard content.

**Heal-write disk read-back (BC-1.18.008 v1.7, F-C3-P7-001, extending the F-C3-P6-002 ruling to
the DANGEROUS-window heal).** The heal's own destructive write receives the SAME post-hoc disk
read-back discipline this AC's earlier paragraph requires for sealed-shard writes: after the
verified slice is written via `write_atomic`, the heal MUST perform a FRESH read-back of the
canonical file from disk and confirm its `(length, SHA-256)` equals `(final_bytes, final_sha256)`
before reporting the heal complete. Trusting `write_atomic`'s own return value with no subsequent
read does NOT satisfy this requirement — it cannot detect a write that silently truncated,
partially flushed, or otherwise landed corrupted bytes on disk at the exact moment (post-heal) when
the pre-heal content is irretrievably gone. A read-back mismatch fails loud with `E-SHD-012` — the
heal's own destructive write already happened at that point, so this final check exists to surface
the corruption immediately (for operator remediation from git history/backup) rather than let a
silently-corrupted canonical file pass as healed.

**Happy-path canonical-write disk read-back — the SAME discipline extended to the THIRD destructive
write site (BC-1.18.008 v1.8, F-C3-P8-002).** The Recovery-Confirmation Rule's step (ii) — the
ORDINARY, first-time/uninterrupted completion of the canonical-truncate write, not only its
crash-recovery heal counterpart above — receives this identical post-hoc read-back requirement.
After step (ii)'s `write_atomic` call returns, the backfill-split MUST perform a FRESH read-back of
the canonical file from disk and confirm its `(length, SHA-256)` equals the Backfill Recovery
Manifest's `(final_bytes, final_sha256)` — already durably published in step (i) of the SAME
two-phase publish sequence, so no new value needs computing — BEFORE the migration reports success
for that artifact. If the read-back does NOT match, the backfill-split MUST fail loud with **NEW
`E-SHD-013`** and halt for operator investigation: the destructive write has already happened at
that point (the original monolithic content is gone from the canonical file, recoverable only from
git history), so this check exists to surface the corruption immediately rather than let a
silently-corrupted canonical file pass as successfully migrated.

**Invariant 5: no destructive write of this BC's one-time migration is ever trusted on its own
return value alone (BC-1.18.008 v1.8).** This generalizes, as one explicit principle, what this AC
already states separately for each of the THREE destructive, one-time, source-overwriting write
sites it specifies: a sealed-shard write is verified against the in-memory partition buffer that
was intended to be written (clause (c) above); the DANGEROUS-window heal write is verified against
the Backfill Recovery Manifest's `(final_bytes, final_sha256)`; and the happy-path
canonical-truncate write (immediately above) is verified against that SAME Manifest pair. Each is
independently confirmed via a fresh post-hoc disk read-back before the migration — or its
interrupted-migration recovery — is allowed to report success, because an in-memory-only success
signal cannot detect a silent truncation, partial flush, or other on-disk corruption before the
source content it discards becomes unrecoverable except via git history.

### AC-023: Load-time fail-loud enforcement of cap-vs-formula inequality (traces to BC-1.18.005 postcondition 9, edge cases EC-013, EC-015, EC-017)

For EVERY `[[shard]]` config entry — regardless of `shape` (Postcondition 8 already establishes that

`shard_cap_bytes`. If the declared `shard_cap_bytes` is GREATER than the computed ceiling, `load()`
returns `HookResult::Error` — the misconfigured entry is REJECTED; it is NEVER silently accepted and
NEVER silently clamped down to the computed ceiling. A declared `shard_cap_bytes` exactly EQUAL to the
computed ceiling (boundary case) loads normally (`Ok`) — the comparison is inclusive of the boundary,
mirroring EC-002's inclusive-boundary precedent for the per-write trigger. This is a load-time
misconfiguration guard over a `[[shard]]` entry's own internal consistency between its declared cap and
its own declared four inputs; it does not require or perform any re-derivation of the F4 harness's

**Divisor-door closure — `worst_case_fuel_per_byte` finiteness/positivity guard (added S-25.02

silently accept a saturated ceiling and MUST NEVER silently substitute a fallback ceiling. Together
with the EC-015 divisor-legality guard, this closes the divisor-door completely (EC-017).
