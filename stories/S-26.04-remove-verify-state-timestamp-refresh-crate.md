# S-26.04: Remove Dormant `verify-state-timestamp-refresh` Crate (ADR-046 §Decision 5 Stage 2)

## Narrative
- **As a** maintainer of the vsdd-factory Cargo workspace
- **I want to** delete the `verify-state-timestamp-refresh` crate — deregistered from
  `hooks-registry.toml` since ADR-046 §Decision 5 Stage 1, its enforcement function
  fully subsumed by `stamp-state-timestamp` — from the workspace and from disk
- **So that** the codebase does not carry a dead crate whose deletion ADR-046 §Decision
  5 explicitly anticipated as a "follow-up crate-deletion story" that was never
  created, closing that open loop

## Problem Statement (ADR-046 §Decision 5 follow-up — no GH issue; human-directed fold-in)

ADR-046 §Decision 5 ("Retire `verify-state-timestamp-refresh` in full, not merely
'relax' it") already executed **Stage 1**: it deregistered the guard's
`hooks-registry.toml` entry, migrated its behavioral-contract content
(`STATE_MD_MAX_BYTES` cap → relocated to `factory-lock-parse`; the byte-cap
Precondition/Invariant/EC-010 → migrated to BC-4.17.001) and retained the crate
in-tree, dormant-but-not-deleted, per POLICY 1 append-only numbering discipline. The
Decision's own reconciliation table explicitly anticipates a **Stage 2**
"follow-up crate-deletion story" for the actual removal — that story was never
created. This story is that follow-up.

**Scope, exactly as ADR-046 §Decision 5's reconciliation table directs — no more, no
less:**

1. Remove `verify-state-timestamp-refresh` from the Cargo workspace member list
   (root `Cargo.toml`).
2. `git rm -r crates/hook-plugins/verify-state-timestamp-refresh/`.
3. Sweep the 2 stale doc-comment references this deletion leaves behind — in
   `factory-lock-parse` (the crate `verify-state-timestamp-refresh` depended on for
   `extract_frontmatter`/`parse_factory_lock`/`STATE_MD_MAX_BYTES`) and in
   `verify-factory-lock`'s own Cargo.toml/doc comments (confirm exact call sites at
   implementation time — this story does not presume their precise line numbers per
   TD-VSDD-091 anti-volatile-pin).
4. Confirm no WASM bundling references the crate (registry, resolvers-registry.toml,
   release bundle manifest) — it was already deregistered from `hooks-registry.toml`
   at Stage 1, so this is a confirmation check, not new deregistration work.
5. Retire BC-5.40.001's VP rows T-001..T-007 (S-19.08 unit/integration tests scoped
   to the `verify-state-timestamp-refresh` crate) as **historical**, annotated as
   describing now-deleted (not merely dormant) coverage — per ADR-046 §Decision 5's
   reconciliation table, these rows are NOT deleted outright (POLICY 1 append-only),
   only re-annotated.

## Required BC Reconciliation (product-owner routing — NOT authored by this story)

BC-5.40.001's VP rows T-001..T-007 currently read "RETAIN AS HISTORICAL... annotated
as describing dormant (deregistered-but-not-deleted) coverage." Once this story
actually deletes the crate, "dormant (deregistered-but-not-deleted)" becomes
factually false — the crate no longer exists on disk at all. Product-owner must
re-annotate these rows to "describing coverage of a now-deleted crate (ADR-046
§Decision 5 Stage 2, S-26.04)," per the SAME reconciliation table's own instruction
that this re-annotation happens "in the follow-up crate-deletion story this Decision
already anticipates" — i.e., THIS story, not a further-deferred one.
