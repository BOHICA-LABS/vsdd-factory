## Narrative

- **As a** security-reviewer and architect jointly responsible for the `unvalidated-mutation.marker`
  quarantine gate's threat model
- **I want to** formally re-evaluate whether BC-1.18.002's fail-OPEN posture on a non-NotFound
  marker-read I/O error (Invariant 2 / EC-030) remains the correct tradeoff, or whether a
  design exists that fails CLOSED on that error class without reintroducing the unclearable
  self-lock INV2 exists to prevent
- **So that** the gate's CWE-703/CWE-636 tension (fail-open-on-error security exposure vs.
  fail-closed-creates-unrecoverable-lock availability exposure) is resolved by a deliberate,
  documented engineering decision rather than left as a recurring point of adversarial
  disagreement that gets silently re-litigated by future implementers (as happened in PR #842)

## Background (for future implementers — read before starting)

During S-25.02 cluster-5 (PR #842, merged into `develop`; commit is documented in
`STORY-INDEX.md` / `burst-log.md` cluster-5 entries — **do not trust a literal SHA cited in
this story's own prose without re-verifying it against `git log` first, per TD-VSDD-091**), a
well-intentioned implementer change made `indeterminate_marker::block_if_marker_check`
(`crates/factory-dispatcher/src/indeterminate_marker.rs`) fail-CLOSED on a non-`NotFound` I/O
error encountered while reading the quarantine marker file. The change was **reverted**
because it violated BC-1.18.002 v1.8's deliberate invariant — the code today (confirmed by
reading `crates/factory-dispatcher/src/indeterminate_marker.rs:404` and
`crates/hook-plugins/validate-unvalidated-mutation-marker/src/lib.rs:118-137`) still
fail-opens on both the dispatcher-native crash-path check (`block_if_marker_check`) and the
WASM gate's own normal-path read (`guard_logic::evaluate_gate`).

BC-1.18.002 EC-030 / Invariant 2 currently **require** fail-OPEN on a marker-read I/O error,
with an explicit documented rationale (BC-1.18.002 v1.8, Invariant 2 paragraph 2 and EC-030
row):

> "an unreadable marker is a cannot-complete infrastructure fault... the operator `rm` escape
> hatch may also fail under the same permission fault, creating an unclearable self-lock —
> the exact failure class INV2 prohibits."

The gate's own Threat Model & Scope section states the canonical claim language (BC-1.18.002
v1.8, verbatim, to be used in all derived artifacts):

> "A fast, fail-open, accidental-misuse interlock for a cooperating agent — NOT an
> adversary-resistant authorization boundary."

ADR-048's fail-closed tightening (`block_if_marker`, §Decision 1) deliberately applied ONLY
to the crash-path + valid-non-expired-marker sub-case (BC-1.18.002 PC5/PC6, EC-031/EC-032) —
it explicitly did NOT extend to the marker-read-I/O-error-during-normal-execution sub-case
(EC-030), which is a distinct case from the crash case (BC-1.18.002 Invariant 2 explicitly
distinguishes: "(a) a successfully-read but malformed marker (EC-008 → BLOCK); (b)
dispatcher-detected plugin crash (EC-031, handled by `block_if_marker`; PC5/PC6)" vs. (c) the
in-scope EC-030 case, unreadable-during-normal-execution → ALLOW).

**The tension to resolve:** a quarantine gate that fails OPEN on an I/O error is a CWE-703
(Improper Check for Unusual or Exceptional Conditions) / CWE-636 (Not Failing Securely)
concern from a security-reviewer's lens — an attacker or a misconfigured filesystem
(permissions drift, disk pressure, a corrupted mount) could induce exactly this I/O error
class to silently disable the quarantine gate. Weighed against that: BC-1.18.002's own
argument is availability — failing closed here could create an unclearable self-lock,
because the SAME permission fault that made the marker unreadable to the gate plugin could
also make it un-`rm`-able by the operator's break-glass escape hatch (T3), defeating INV6's
"never irrecoverable" guarantee. The current spec chose availability (fail-open) with an
explicit, reasoned rationale — this is NOT an oversight or a defect; it is a considered
tradeoff that deserves a fresh, dedicated look rather than being re-litigated ad hoc inside
an unrelated implementation PR (as happened in PR #842).

**Why this is a legitimate deferral (not a defer-pattern violation):** the human explicitly
directed "revert + follow-up story" when PR #842's implementer surfaced the fail-closed
change. Per CLAUDE.md Canonical Principle Rule 3, this qualifies as a legitimate
human-directed deferral because ALL THREE conditions are met: (1) explicit human direction to
defer (the revert-and-follow-up-story instruction), (2) a concrete reason the deferral is
necessary (this is a genuine cross-cutting security-vs-availability tradeoff requiring joint
product-owner + architect + security-reviewer adjudication — not a mechanical fix answerable
by a single specialist in the original PR's scope), and (3) attachment to this specific story
(S-25.07) rather than an untracked "later."

## Acceptance Criteria

### AC-001 (traces to BC-1.18.002 invariant 2)
A joint review session — product-owner, architect, and security-reviewer, all three
participating — produces a written decision memo (persisted under
`.factory/specs/architecture/decisions/` as an ADR amendment to ADR-047/ADR-048, OR as a
standalone decision record if no existing ADR is the correct host — architect's call, not
this story's) that explicitly re-evaluates whether BC-1.18.002 Invariant 2's fail-open
posture on non-NotFound marker-read I/O errors remains correct, and states one of two
outcomes: (a) fail-open is RE-AFFIRMED as correct, with the CWE-703/CWE-636 exposure
explicitly acknowledged and accepted (not silently ignored) in the decision record, or (b) a
specific alternative design is ADOPTED that fails closed on this error class without
reintroducing an unclearable self-lock.
- **Test:** `test_BC_1_18_002_INV2_review_decision_record_exists()` (a documentation-presence
  / structure check, not a runtime behavioral test — verifies the decision record exists,
  cites BC-1.18.002 Invariant 2 and EC-030 by ID, and states one of the two outcomes above)

### AC-002 (traces to BC-1.18.002 EC-030)
IF outcome (b) is adopted (design change), the security-reviewer's independent verification
confirms the new design does NOT create a scenario where BOTH (i) the gate plugin cannot read
the marker AND (ii) the operator's `rm` escape hatch (T3) is simultaneously unusable under the
same fault class — i.e., INV6's "never irrecoverable" guarantee is preserved under the new
design. A candidate design direction (non-binding, for the joint review to evaluate, not a
prescribed solution): a SEPARATE always-clearable escape path independent of the marker
file's own permission state (e.g., a sentinel/override file at a DIFFERENT filesystem path
with independent permissions, or an explicit dispatcher CLI flag/env-var override that does
not require reading or writing the marker file at all) — such that a permission fault
affecting the marker file does not simultaneously disable its own escape hatch.
- **Test:** `test_BC_1_18_002_INV2_alternative_design_preserves_INV6_ungated_escape()`
  (only applicable/written if outcome (b) is chosen; N/A test-writer note required in the PR
  if outcome (a) is chosen instead)

### AC-003 (traces to BC-1.18.002 postcondition 5, postcondition 6)
IF outcome (b) is adopted, `guard_logic::evaluate_gate`
(`crates/hook-plugins/validate-unvalidated-mutation-marker/src/lib.rs`) and
`block_if_marker_check` (`crates/factory-dispatcher/src/indeterminate_marker.rs`) are BOTH
updated consistently — the two call sites must not diverge in their I/O-error handling
posture (this exact divergence risk is why PR #842 changed only one of the two sites and
triggered the revert). All 5 existing `block_if_marker_check` unit tests in
`indeterminate_marker.rs` (lines ~1114-1225, including
`test_BC_1_18_002_block_if_marker_check_io_error_allows`) and the corresponding
`guard_logic::evaluate_gate` EC-030 unit test in
`validate-unvalidated-mutation-marker/src/lib.rs` (lines ~1335-1380) are updated or
superseded to match the new, jointly-decided posture — no stale test asserting the OLD
posture is left in the suite.
- **Test:** `test_BC_1_18_002_evaluate_gate_and_block_if_marker_check_io_error_posture_consistent()`

### AC-004 (traces to BC-1.18.002 invariant 4)
