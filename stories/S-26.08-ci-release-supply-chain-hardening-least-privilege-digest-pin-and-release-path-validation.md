## Narrative

- **As a** maintainer who publishes the factory plugin and its cross-compiled dispatcher binaries from `release.yml`
- **I want** the release workflow to hold only the token permissions each job needs, the semgrep container to be pinned to an immutable digest, the semgrep workflow to hold no write scope it does not use, and the release path to have a validation strategy that does not depend on cutting a real tag
- **So that** a compromised or mistaken step in the build and validation jobs cannot push to `main`, move a tag or publish a Release, a re-tagged image cannot change what the SAST gate runs, and a permission change to the one workflow PR CI cannot execute is proven before it ships rather than discovered during a release

## Problem Statement

**SEC-006-C (`release.yml`).** The workflow declares one top-level block, `permissions: contents: write`, so EVERY job (`validate`, `build-binaries` — which compiles and runs the whole dependency tree — `commit-binaries`, `release`, `bump-marketplace`, `sync-develop`) holds a write token. Only `commit-binaries` (pushes the bundling commit to `main` and force-moves the tag), `release` (creates the GitHub Release) and `sync-develop` (already declares its own `contents: write` and `pull-requests: write`) need write scope.
**SEC-006-D (`semgrep.yml`).** The SAST job runs in `container: image: returntocorp/semgrep:1.61.0` — a mutable tag. A re-pushed or compromised tag changes the code that scans every PR with no diff in this repository.
**SEC-006-E (`semgrep.yml`).** The top level grants `pull-requests: write` on a workflow triggered by `pull_request`. `semgrep ci --config=auto` without an app token has no PR-comment step; the scope is unused. (For fork pull requests GitHub downgrades the token to read-only regardless, so the declaration also misdescribes the workflow's real behavior.)
**Release-path validation.** `release.yml` triggers only on a `v*` tag push (`on: push: tags`), so PR CI never executes it. A permission narrowing that is wrong — a job that needed a scope the new matrix omitted — fails only during a real release, after the tag exists and (for `commit-binaries`) possibly after a partial push. The story therefore needs a validation strategy, not only a YAML diff.

**Claim Boundary (stated honestly).** No static check proves that a job's steps do not need a scope; only running the job with the narrowed token does. This story provides three layers — a static permission-matrix and pin test in PR CI (catches drift and accidental widening), a fork rehearsal of the UNMODIFIED tag-triggered file under a read-only default token (catches a missing grant), and a verification task on the first real release (the production proof, with a revert plan). It does not claim the first two layers substitute for the third. A `workflow_dispatch` dry-run mode was evaluated and NOT adopted: the `if:` guards that skip the push / tag / release steps would be new release logic that PR CI also cannot exercise, so the rehearsal on a fork, which runs the real file, is the stronger evidence.

## Acceptance Criteria

> No AC traces to a behavioral contract: this is a CI / release-process story (frontmatter BC status N/A). Each AC names a falsifiable check. "Workflow files" means `.github/workflows/release.yml` and `.github/workflows/semgrep.yml` as they stand AFTER PR #848 merges.

### AC-001 (SEC-006-C; `release.yml` per-job least privilege)
The top-level block of `release.yml` is `permissions: contents: read` (its comment block is rewritten to say that write scope is granted per job and why). Each job declares its own `permissions`: `validate` — `contents: read`; `build-binaries` — `contents: read`; `commit-binaries` — `contents: write` (the bundling commit push to `main` and the tag force-move; the comment keeps the existing note that `GITHUB_TOKEN` pushes do not re-trigger workflows); `release` — `contents: write` (create the GitHub Release); `bump-marketplace` — `contents: read` (it authenticates to the marketplace repository with the `CLAUDE_MP_PAT` secret, not the job token, and self-skips when the secret is absent); `sync-develop` — its existing `contents: write` and `pull-requests: write`, unchanged. A job that T-1 finds to need any further scope (for example `actions: read` for an artifact download, `id-token`, `attestations`) is granted exactly that scope on that job and the scope and the step that needs it are named in a comment; T-1 records the per-step token-use review, step by step, in the story's Adversarial Review section so the matrix is derived from the steps and not from this story's expectation. No job inherits a write scope from the top level.
- **Check:** the AC-004 permission-matrix test; the AC-005 rehearsal (every job green under a repository default token of read-only).

### AC-002 (SEC-006-D; the semgrep container image is digest-pinned)
`semgrep.yml`'s `container.image` is `semgrep/semgrep@sha256:<digest> # <version>`. (a) The repository is the maintained `semgrep/semgrep`; the deprecated `returntocorp/semgrep` namespace (the current `returntocorp/semgrep:1.61.0`, a mutable tag) is removed from the file. (b) The reference is pinned by digest, where `<digest>` is the index (multi-arch manifest list) digest resolved from the registry AT IMPLEMENTATION TIME (never copied from this story, from training data or from a log), and the human-readable version sits in a trailing `# <version>` comment (for example `# 1.61.0`; the tag is dropped from the reference itself, so no tag can be silently re-pointed under the digest) alongside the resolution date and the update procedure (re-resolve, review the semgrep release notes, change digest and `# <version>` comment together in one PR). (c) The digest is VERIFIED to resolve to the intended version before it is committed: `docker buildx imagetools inspect semgrep/semgrep:<version>` (or the Docker Hub registry API `GET https://hub.docker.com/v2/repositories/semgrep/semgrep/tags/<version>`) is run, the index digest it prints is the digest pinned, and the command with its full output is recorded in the story PR; the implementer ALSO runs `docker buildx imagetools inspect semgrep/semgrep@sha256:<digest>` and records that it resolves. (d) T-1 confirms `<version>` still resolves in `semgrep/semgrep` (a pre-check at authoring on 2026-10-14 found `semgrep/semgrep:1.61.0` resolving as a manifest list, evidence only; the digest is NOT recorded here and is re-resolved at implementation); if it does not resolve, the story picks the version with registry evidence and records why. (e) Regression gate: a CI-run test asserts that NO `container:` or `image:` reference in ANY file under `.github/workflows/` (including `services:` and `container.image` forms, and job-level and step-level `image:`) uses a bare tag (no `@sha256:<64-hex>` digest) or the `returntocorp` namespace; local-build references and `docker://`-less action `uses:` lines are out of its scope (covered by AC-004(d)). Source: PR #848 round-3 review CR-R2-008 (code-reviewer). T-1 also determines whether Dependabot (or the repository's dependency-update tooling) can update a `container:` image in a workflow file and records the answer: if it cannot, the update procedure in the comment is the only mechanism and AC-004's test asserts the pin is present, not that it is current.
- **Check:** the AC-004 digest-pin assertion; the AC-002(e) regression gate; the semgrep job runs green on a real PR with the pinned image.
- **Test:** `every_workflow_container_image_is_digest_pinned_and_not_returntocorp` (name illustrative; follows the host suite's convention). Written FIRST: it fails against the unchanged `semgrep.yml` (bare tag `returntocorp/semgrep:1.61.0`) and passes only after the digest pin and the move to `semgrep/semgrep`. It enumerates every `container:` / `image:` value across all workflow files (no allowlist of files, so a future workflow cannot escape it) and asserts each matches `@sha256:[0-9a-f]{64}` and none contains `returntocorp/`.

### AC-003 (SEC-006-E; `semgrep.yml` holds no unused write scope)
The top-level block of `semgrep.yml` is `permissions: contents: read` only. T-1 runs the semgrep job on a pull request with `pull-requests: write` removed and records the result (the job passes and findings still surface in the job log / SARIF as before); if and only if a step demonstrably needs to write to the pull request, the scope is granted on the JOB, not the top level, and the job is guarded `if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository` so a fork pull request never reaches a write-scoped job, with the step named in a comment. The workflow's triggers, schedule and rule packs are unchanged.
- **Check:** the AC-004 permission-matrix test; the PR run recorded in T-1.

### AC-004 (release-path validation, layer 1; a static policy test runs in PR CI)
A test in the repository's existing PR-CI suite (the bats suite under `plugins/vsdd-factory/tests` or a cargo test, whichever can parse YAML with a tool the CI image ALREADY provides; T-1 inventories the available parsers and installs nothing new without architect approval) loads every workflow under `.github/workflows` and asserts: (a) every workflow has a top-level `permissions` block and none grants `write` at the top level except where the test's explicit allowlist (`sync`-style workflows, none today) says so; (b) `release.yml` equals the AC-001 matrix exactly, job by job (a new job with no `permissions` block fails the test, so a future job cannot silently inherit); (c) `semgrep.yml` has no `write` scope at top level and a digest-pinned `container.image` matching `@sha256:[0-9a-f]{64}`; (d) every `uses:` in every workflow is pinned to a full 40-hex commit SHA (the PR #848 pinning; local `./` actions excepted), with the version in a trailing comment; (e) `actionlint` passes over all workflows, the tool itself pinned by commit SHA / digest under the same rule and its version chosen from its release page at implementation. The test is written FIRST and fails against the unchanged files for (b) and (c).
- **Test:** `release_workflow_permissions_match_matrix`, `semgrep_workflow_has_no_write_scope_and_pinned_image`, `every_workflow_action_is_pinned_to_a_full_sha`, `every_workflow_has_top_level_permissions`, plus the `actionlint` CI step (names illustrative; they follow the host suite's convention).

### AC-005 (release-path validation, layer 2; a documented fork rehearsal of the real file)
`RELEASING.md` gains a section "Rehearsing release.yml" with an exact, repeatable procedure: (1) a scratch fork (or a private copy) of the repository with its Actions setting "Workflow permissions" at the READ-ONLY default; (2) the branch containing the change to `release.yml` pushed to the fork's default branch; (3) a prerelease tag of the form `v<next>-rehearsal.<n>` pushed to the fork, which triggers the real tag-triggered file unmodified; (4) what to expect (`bump-marketplace` self-skips for want of the secret; `commit-binaries` pushes the bundling commit to the FORK's default branch, which the procedure says to allow via the fork's branch protection or to expect and record as the one permitted failure with its exact error); (5) what to capture (run URL, per-job conclusions, the permission block shown in each job's "Set up job" log, which prints the token permissions); (6) cleanup. The story's PR attaches the rehearsal evidence for THIS change: every job green under read-only defaults, each job's logged token permissions equal to the AC-001 matrix. A write grant that is missing fails its job in the rehearsal, which is the point.
- **Check:** the section exists and its steps are executable verbatim (T-5 executes them); the evidence is attached to the PR.

### AC-006 (release-path validation, layer 3; the first real release under the new file is verified and revertible)
The story's final task is owned by whoever cuts the next real release after this story merges (S-26.05 for rc.26 if it follows, otherwise the next cut): after the tag run, verify that every job concluded success, the bundling commit and the retag happened, the GitHub Release exists, and the marketplace bump either ran or self-skipped as before; record the run URL in the decision log through the state-manager. The revert plan is written in the story PR description: a single `git revert` of the story's `release.yml` commit restores the previous permission block, and `release.yml` changes are never combined with other release-process edits in the same PR so the revert is clean. A failed first release under the new file is a stop-and-revert event, not a debugging session on a live tag.
- **Check:** the decision-log entry citing the run URL; the PR description's revert plan.
