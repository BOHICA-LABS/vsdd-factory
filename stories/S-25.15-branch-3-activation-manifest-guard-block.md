# S-25.15: Branch 3 Guard Block - Armed-Activation Manifest Validation at the PreToolUse Layer (ADR-052 §Decision 5c Branch 3)

## Narrative

- **As a** factory operator whose agents may attempt to launch the sanctioned `migrate-bc-index` / `backfill-append-logs` command
- **I want** the PreToolUse guard to refuse a NEW activation whose armed-activation manifest is invalid, with the same code and reason token the binary would give
- **So that** an unauthorized or malformed activation is stopped before the process is even spawned, consistently with the binary (one validation, two hosts), and never leaks the offending manifest value

### AC-001 (was S-25.13 AC-019) (the Branch 3 guard block; traces to BC-1.18.011 Precondition 5 ("the guard layer (Branch 3 REJECT) carries the same code and reason token as a block, not an `E-MAINTENANCE-001/002` verdict"), EC-087, EC-090; GAP-13)

A `Bash` PreToolUse of the sanctioned `migrate-bc-index` / `backfill-append-logs` command for a Branch 3 (new activation) with an invalid manifest is BLOCKED by the guard with a `HookResult` block whose reason names `ACTIVATION_MANIFEST_INVALID` and the reason token and never the offending value (each hostile value asserted absent from the block reason); the same five reasons (`activation_id_unsafe_component`, `activation_id_not_uuid`, `migration_id_mismatch`, `unparseable`, `absent`) with the S-25.13 precedence; the guard evaluates the SAME pure validation as the binary (one implementation, two hosts; a parity test feeds identical manifest bytes to both and asserts identical tokens); a valid manifest is not blocked by this branch; a STAGING resume or COMMITTING recovery is NOT a Branch 3 and is never blocked on manifest grounds here. No story delivers the §5c Branch 1-4 classifier host (S-12.16 leaves Branches 1-4 to ADR-052 §Decision 5c) and a hook plugin MUST NOT depend on `shard_manager`; the placement of the host and of the shared validator is GAP-13. This AC is written behaviorally so it survives the placement ruling.

## Architecture Compliance Rules

1. **One implementation, two hosts:** the guard and the binary share the validator; a parity test enforces identical tokens for identical bytes; no second decode.
2. **Closed reason set:** exactly the five S-25.13 tokens; no sixth.
3. **Never echo:** no manifest byte or value in the block reason.
4. **No hook-plugin dependency on `shard_manager` / `factory-dispatcher`.**
5. **Error codes: ONLY existing taxonomy entries** (`ACTIVATION_MANIFEST_INVALID`); not an `E-MAINTENANCE-001/002` verdict (BC-1.18.011 Precondition 5).
6. **No WASM fuel exhaustion risk:** the guard validation is bounded (size-capped manifest read) so a hook-plugin host stays within the fuel budget (CLAUDE.md WASM plugin fuel budgets).
7. **POLICY 21 / POL-3 / POLICY 19:** no new `.sh`; no `.factory/` shell bypass; ADR-052 cited by section, never by version.

### Forbidden Dependencies (build-time enforcement)

- No hook-plugin crate (`crates/hook-plugins/*`) MAY depend on `shard_manager` or `factory-dispatcher`; if one does the build MUST fail.
- The shared validator host MUST NOT depend on `internal_log`, `executor`, `main` or any hook-plugin crate; if it does the build MUST fail.
- `last-amended-migrate` MUST NOT depend on `factory-dispatcher`; if it gains that dependency the build MUST fail.
- No new external crates (a new leaf workspace crate for the validator is an architect-approved GAP-13 outcome, not a new external dependency).
