# S-25.10: Hardened Intent-Log Format, Shared Module and Durable Writer (ADR-054 Decisions 1 and 4; slice 1 of 3)

## Narrative

- **As a** factory pipeline operator who will one day run the governed one-time migrations (`migrate-bc-index`, then `backfill-append-logs`) against the
  live `.factory/` tree, and who must be able to verify a half-finished or crashed migration with `sed` and `shasum` alone
- **I want** ONE shared, byte-exact, fail-closed intent-log implementation: the hardened format, a checksum over the exact on-disk bytes, a byte-level reader that
  tolerates a torn tail but never corruption in the middle, tail repair before append, strict durability, and value rules that reject what the reader cannot parse
- **So that** a torn write can never silently discard a valid record (A-1/A-2), the writer can never produce a record its own reader rejects (A-3), the checksum
  is reproducible with `sed` + `shasum` (A-4), a record is durable to media before the WAL boundary counts as reached (A-5), and the two migrations can never drift
  into two private copies of the format again (A-6)

## Context / Feature Summary

**What the code does today (verified in `.worktrees/S-25.09`, branch `feature/S-25.09`, 2026-10-08, function-name anchors per TD-VSDD-091).** The B2 originals
`append_intent_log_record`, `intent_log_checksum_input`, `read_intent_log`, `parse_intent_log_block` and `decide_intent_log_recovery` (with the
`IntentLogRecoveryDecision` enum) live in `crates/factory-dispatcher/src/shard_manager.rs`; the `Fs` trait's `append` (plain `fsync`, no directory sync) lives in
`shard_manager/migration_fs.rs` (with a second `Fs` implementation in `shard_manager/obl1_kani_proofs.rs`). `INTENT_LOG_RECORD_V1` / `END_INTENT_LOG_RECORD` appear in `shard_manager.rs` and the runbook.
S-25.06's `feature/S-25.06` branch holds a drifted second copy (`write_append_log_intent_record`, `parse_append_log_intent_log_block`, `read_append_log_intent_log`,
`append_log_intent_log_checksum_input`, `AppendLogIntentLogRecoveryDecision`, `decide_append_log_recovery`).

**The defects this story closes (ADR-054 §Context).** A-1 (HIGH) valid record + non-record garbage + a later append is discarded; A-2 (HIGH) one invalid UTF-8 byte makes the
whole log unreadable; A-3 the writer accepts values the reader cannot parse (LF, CR) and silently rewrites non-UTF-8 paths lossily; A-4 the checksum covers
`|`-joined parsed values, not the on-disk bytes; A-5 the append uses plain `fsync` (not durable to media on macOS) and no directory sync on creation; A-6 the
format is shared by copy and the copies have drifted. (B-1/B-2/B-3 are S-25.11's.)

## Architecture Compliance Rules

The implementer MUST NOT violate any of these; violations are bugs, not style preferences.

1. **One module, no copies (ADR-054 Decision 4):** the intent-log format, reader and writer live ONLY in `shard_manager/intent_log.rs`; `INTENT_LOG_RECORD_V1` / `END_INTENT_LOG_RECORD` appear nowhere else in `crates/` except the module's tests; the four B2 format originals are deleted, not wrapped.
2. **Byte-level, never string-level (Decision 1.7):** the reader consumes `&[u8]` and never decodes the file as one UTF-8 string; a record is returned only if all 11 lines parsed, the checksum matched and the END line is present; a torn tail is absent; corruption followed by a valid record FAILS CLOSED.
3. **Checksum over the exact on-disk bytes (Decision 1.4):** SHA-256 of the first nine lines as written; nothing is reconstructed from parsed values; the checksum is NOT authentication (tamper-resistance is the Write/Bash guards' job).
4. **Validate before any byte (Decision 1.9):** every record field and every plan path is checked against the value rules before append and at plan-build time; a non-UTF-8 path is rejected, never converted lossily.
5. **Repair the tail under the flock before the first append (Decision 1.9 step 2):** durable truncation to `valid_prefix_len`; never append behind garbage; `MidLogCorruption` or an invariant violation at open mutates nothing.
6. **Strict durability, no silent downgrade (Decision 1.9 step 5; ADR-052 §7d):** `F_FULLFSYNC` on macOS, `fsync` elsewhere; a failing barrier is an `Io` error and the WAL boundary is NOT reached; a directory sync follows creation.
7. **Chain discipline:** this story does NOT rename the txn field, does NOT add `decide_recovery` / `verify_plan_completion`, does NOT change `decide_intent_log_recovery` behavior, does NOT touch `finish_committing_migration` or the `recover()` arms (S-25.11), and does NOT scrape the log for `txn_id` or `fencing_generation`.
8. **Error codes: ONLY existing taxonomy entries (error-taxonomy v1.41).** This story introduces NO new code: `INTENT_LOG_CORRUPT` and `INTENT_LOG_VALUE_REJECTED` (both exit 2) are ALREADY in v1.41. None is exit 1 (exit 1 is reserved for `EXPIRY_ABORT` and `MIGRATION_LOCK_CONTENTION`). A `Display` that differs from its ADR-054 Decision 3.1 line fails the S-12.13 lint gate.
9. **No WASM-sandboxed executor (ADR-051 §Decision 7 / CLAUDE.md §WASM plugin fuel budgets):** the module runs native in the dispatcher binary, never in a hook plugin.
10. **Single-commit-per-burst / POL-3 (TD-VSDD-053, TD-FACTORY-HOOK-BYPASS-001):** no `.factory/` mutation by shell bypass; this story does not touch live cycle files.
