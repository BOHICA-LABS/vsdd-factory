# S-26.01: `stamp-state-timestamp` PostToolUse Mutation Races the Single-Write Protocol

## Narrative
- **As an** agent operating under the single-Write STATE.md protocol (CLAUDE.md
  §Operational Discipline TDs, D-441(a)+D-442(a)+D-443(a)+D-444(a)+D-449(a) —
  verbatim-strict single-Write discipline)
- **I want to** land my entire STATE.md content in exactly one `Write` call without
  `stamp-state-timestamp`'s PostToolUse re-stamp racing that landed content
- **So that** I am never forced into sequential `Edit` calls by a "file changed since
  read" refusal caused by the guard's own mutation of the file I just wrote

## Problem Statement (GH issue #839, P0, AXIS-2 current-source defect)

`stamp-state-timestamp` (`crates/hook-plugins/stamp-state-timestamp/`, `PostToolUse`,
matches `^(Edit|Write|MultiEdit)$`, capability-scoped to `.factory/STATE.md`; see
ADR-046 §Decision 1 / §Decision 5) re-stamps STATE.md's `timestamp:` frontmatter field
*after* the tool call that wrote it has already returned. When an agent issues a
single full-content `Write` (as the protocol mandates), the stamper's own subsequent
write changes the file's on-disk bytes out from under the agent's next read-modify-
write cycle. Any following single-Write attempt by that same agent session is refused
by the harness with "file changed since read," forcing the agent into a sequence of
smaller `Edit` calls instead — precisely the anti-pattern
D-441(a)/D-442(a)/D-443(a)/D-444(a)/D-449(a)'s verbatim-strict single-Write discipline
exists to prevent. Two guards (the single-Write protocol and the PostToolUse stamper)
land in direct, observed tension.

## Required BC Amendment (product-owner routing — NOT authored by this story)

BC-4.17.001 (the `stamp-state-timestamp` behavioral contract) needs one of two
amendment shapes, to be decided by product-owner in consultation with architect:

1. **Ordering fix:** amend BC-4.17.001's postconditions so the timestamp/lock-renewal
   stamp is folded into the SAME PostToolUse pass that validates the agent's write
   (i.e., the stamp is computed and applied before the harness considers the tool call
   complete, not as a second, later mutation the agent's own tooling can observe as a
   stale-read hazard); or
2. **Protocol-tolerance fix:** amend the single-Write protocol's own guard(s) (see
   BC-5.40.001, and any `validate-dispatch-advance`-adjacent single-writer enforcement)
   to recognize `stamp-state-timestamp`'s own byte-diff as an expected, self-consistent
   mutation rather than an unexpected concurrent write — i.e., make the "changed since
   read" check aware of exactly one class of expected post-write mutation.

Architect must weigh both options against ADR-046 §Decision 1's existing PC1/PC2
composition requirement (single shared read, single shared write, per the Call-site
asymmetry note in ADR-046 §Decision 1) before product-owner authors the amendment.
Whichever direction is chosen, BC-5.40.001's PC4 (mid-burst TTL renewal, now performed
by `stamp-state-timestamp` per ADR-046 §Decision 5's Traceability item 1) must remain
internally consistent with the amended BC-4.17.001.

### AC-001 (BC trace: pending BC-4.17.001 amendment)
- A single-content `Write` to `.factory/STATE.md` by an agent, followed immediately by
  `stamp-state-timestamp`'s PostToolUse pass, results in a file whose bytes reflect
  BOTH the agent's content AND the stamp — with no intervening state in which the
  agent's own subsequent read-modify-write cycle observes a "changed since read"
  refusal caused solely by the stamper's own mutation.
- **Test:** `test_BC_4_17_001_single_write_survives_stamper_race()`

### AC-002 (BC trace: pending BC-4.17.001 amendment)
- Reproduces GH issue #839's exact failure mode as a regression test: agent issues one
  full-content `Write`; assert the very next agent-initiated `Write` (not `Edit`) to
  the same file, using the byte content returned by the harness after the stamp, is
  NOT refused.
- **Test:** `test_BC_4_17_001_no_forced_sequential_edit_regression()`

### AC-003 (BC trace: pending BC-4.17.001 amendment)
- `stamp-state-timestamp`'s fail-open behavior (ADR-046 §Decision 1 — a stamping
  failure never blocks or reverts the agent's own write) is preserved by whichever fix
  direction is chosen; a negative-control test asserts the agent's original write is
  never lost even when the stamp step itself errors.
- **Test:** `test_BC_4_17_001_fail_open_preserved_after_fix()`
