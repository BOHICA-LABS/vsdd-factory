# BC-10.13.001: last-amended-migrate — Sanctioned Rust CLI for `last_amended`/`changelog:` Migration, Full-Recovery Split, and Changelog Rotation (POLICY 21-Compliant)

## Description

A committed, platform-agnostic Rust `bin/` binary (POLICY 21 `no_new_shell_scripts` — explicitly
NOT a new `.sh` script) that performs three functions mandated by ADR-049/S-15.03 AC-006 and this
amendment: (1) migration bringing `STORY-INDEX.md`, `BC-INDEX.md`, `ARCH-INDEX.md`, `VP-INDEX.md`,
and `STATE.md` fully into the ADR-049 shape (adding `changelog:` to `STORY-INDEX.md`, confirming/
enforcing `last_amended` is strictly current-entry-only on all five, and remediating the
pre-existing D-1144 unescaped-double-quote defect in `BC-INDEX.md`/`ARCH-INDEX.md`/`STATE.md`);
(2) **full-recovery split** (this amendment, human-directed) — where a target file's
`last_amended` instead holds an inline `[Prior: ...]` bracket chain (the pre-D-1149-style
unbounded-growth shape, at any scale up to and beyond the historical 323K-350K-char calibration
ceiling), the migration subcommand SPLITS the current entry from the chain and relocates every
chained entry into `changelog:` as new sequence items, newest-first (see Postcondition PC7),
instead of refusing the file; and (3) as a safety-net utility, rotation of an over-long
`changelog:` sequence into a per-cycle archive under `.factory/cycles/<cycle-name>/`, mirroring
how `burst-log.md`/`decision-log.md` already archive per cycle. With function (2), this tool is a
complete, robust replacement for D-1149's one-time human-authorized POL-3 exception — not merely a
maintainer of the already-migrated shape — satisfying S-15.03 AC-010's "no future POL-3 exception
needed for this class" without qualification. Invoking the tool is the sanctioned path going
forward for every occurrence of this failure class, present or future, removing the need for any
future POL-3/TD-FACTORY-HOOK-BYPASS-001 ad hoc exception request.

## Preconditions

1. The tool is invoked against one of the five ADR-049-governed files (or, for the migration
   subcommand, against all five in one run) by an operator or an orchestrator-dispatched agent
   with filesystem write access to `.factory/`.

2. For the migration subcommand: the target file has a `last_amended:` field whose raw value
   parses as one of two recognized shapes — **(a)** already in D-1149-slim current-entry form (a
   single dated entry, optionally with a trailing `[Prior history → <file>-amendment-history.md]`
   pointer note), for which Postcondition PC2 applies as a verified no-op; or **(b)** a current
   entry followed by one or more inline `[Prior: <date> (vX.Y) — ...]` bracket-chain entries — the
   pre-D-1149-style unbounded-growth shape, at any scale up to and beyond the historical
   323K-350K-char calibration ceiling — for which Postcondition PC7's **full-recovery split**
   applies. **Both shapes are ELIGIBLE for migration** (superseding this BC's v1.0 Precondition 2,
   which excluded shape (b) as `NotEligible`): an inline-chain file is no longer out of scope; the
   tool is a full replacement for the one-time D-1149 human-authorized POL-3 exception, not merely
   a shape-completion/escape-remediation utility for already-slim files. The tool's only remaining
   `NotEligible` outcome is a `last_amended:` field that cannot be located at all, or whose raw
   value does not parse as a YAML scalar (e.g. a corrupted frontmatter delimiter) — see EC-008; a
   malformed-frontmatter condition, not a chain-length or chain-presence condition.

3. For the rotation subcommand: the target file's `changelog:` sequence has grown past an
   operator-configurable or tool-default size threshold, and a destination cycle name (matching
   an existing or newly-created `.factory/cycles/<cycle-name>/` directory) is supplied.

## Postconditions

### PC1 — migration completes `changelog:` coverage across all five files

Running the migration subcommand against `STORY-INDEX.md` adds a `changelog:` top-level YAML
sequence to its frontmatter if absent (completing the D-448(b)/D-414(c) deferral already recorded
in `STORY-INDEX.md`'s own header blockquote). Running it against `ARCH-INDEX.md`, `BC-INDEX.md`,
or `VP-INDEX.md` — which already carry `changelog:` — is a verified no-op on that field (the tool
confirms presence and structural validity rather than re-adding it). Running it against
`STATE.md` never adds a `changelog:` field (ADR-049 Decision 4 — `STATE.md` relies on its
body-level `## Decisions Log`/`## Phase Progress` instead).

### PC2 — migration confirms current-entry-only `last_amended`, or performs a full-recovery split into that shape

For each of the five files, the tool brings `last_amended` into a single dated current-entry-only
form with no nested `[Prior: <date> (vX.Y) — ...]` bracket referencing a different dated entry.
Where the file is already compliant (Precondition 2(a)), this is a verified no-op (identical to
the pre-amendment v1.0 behavior). Where the file's `last_amended` instead holds an inline
`[Prior: ...]` bracket chain (Precondition 2(b)), the tool performs the **full-recovery split**
defined in PC7, which also brings the field into this same current-entry-only shape as a side
effect of relocating the historical entries to `changelog:`.

### PC3 — D-1144 escape remediation on the three defective files (and on any relocated split entry)

For `BC-INDEX.md`, `ARCH-INDEX.md`, and `STATE.md` — the three files carrying the pre-existing
D-1144 unescaped-literal-double-quote defect in their current `last_amended` entry — the tool
rewrites the offending entry with every embedded literal `"` escaped to `\"`, producing a value
that parses cleanly under strict YAML `safe_load`. The entry's substantive text (every character
other than the escape insertions) is preserved verbatim. `VP-INDEX.md` and `STORY-INDEX.md` are
unaffected by this postcondition on their OWN current entry (not part of the D-1144 defect set).
This same escaping discipline also applies, as needed, to every entry PC7's full-recovery split
relocates into `changelog:` — regardless of which of the five files is being split — since a
historical bracket-chain entry inherited from the pre-D-1149 write path may itself carry an
unescaped literal quote.

### PC4 — migration is idempotent

Running the migration subcommand a second time (or any subsequent time) against an
already-migrated file produces a verified-clean report with zero file mutations — the tool
detects the already-compliant shape and takes no destructive or duplicating action (it never
double-adds a `changelog:` field, never double-escapes an already-escaped quote, and never
re-wraps an already-current-entry-only `last_amended`). This includes the case where PC7's
full-recovery split has just run: the freshly-split file is now in the Precondition 2(a) shape, so
an immediate re-invocation is governed by this postcondition, not by PC7 again — PC7 fires at most
once per pre-existing chain, never re-detects a chain where none remains, and never re-splits.

### PC5 — rotation archives without data loss

Running the rotation subcommand against a file whose `changelog:` sequence exceeds the size
threshold moves the oldest N items (operator-specified count, or all-but-the-most-recent-K by
tool default) into a new or appended `.factory/cycles/<cycle-name>/<file-basename>-changelog-archive.md`
file, verbatim, and removes exactly those items from the source file's `changelog:` sequence,
leaving a discoverability pointer (e.g. a comment or a `changelog_archive:` frontmatter field
naming the archive path) in the source file. No `changelog:` item's `date:`/`change:` text content
is altered by rotation — only its location changes.
**The archive NEVER contains duplicate items across rotation cycles; a partial rotation cycle
(archive written, source-write failed) is detected and resolved idempotently on the next
invocation (see PC8).**

### PC6 — the tool never touches the frozen D-1149 sidecars

Neither the migration subcommand (including its PC7 full-recovery split path), the rotation
subcommand, ever writes to, reads for mutation, or deletes any of the five
`*-amendment-history.md` sidecar files. They remain a frozen pre-migration archive per
S-15.03 §Migration and ADR-049 Decision 5. The tool MAY read them read-only for reporting purposes
(e.g., confirming they exist and are referenced by a pointer note) but never mutates them. PC7
operates exclusively on the live target file's own `last_amended`/`changelog:` fields; recovering
an inline chain is never sourced from, nor written to, a sidecar.

### PC7 — full-recovery split (inline `[Prior:]` chain migration)

When the migration subcommand encounters a `last_amended` value containing one or more inline
`[Prior: <date> (vX.Y) — ...]` bracket-chain entries (Precondition 2(b)), the tool performs a
full-recovery split in the same run, making itself a complete, robust replacement for the one-time
D-1149/POL-3 human-authorized surgery (S-15.03 AC-010 — no future POL-3 exception needed for this
class):

1. **Split point.** The tool scans the raw `last_amended` value for the FIRST occurrence of the
   literal marker ` [Prior:` (a space followed by `[Prior:`), distinguishing it from the
   unrelated, non-growing `[Prior history → ...]` pointer note (never split; see BC-5.45.001 PC4
   parenthetical / EC-005). Everything from byte 0 up to (not including) that marker is the
   CURRENT entry.
2. **Current entry stays in `last_amended`.** The CURRENT entry is re-emitted as the new
   `last_amended` value, current-entry-only, D-1144-escaped per PC3 — identical in effect to the
   confirm/no-op path in PC2.
3. **Tail parsing.** Everything from the first ` [Prior:` marker to the end of the value is the
   TAIL. The tool splits the TAIL on every subsequent ` [Prior:` marker (a single linear
   left-to-right scan; see the bounded-scan requirement in step 7 below), yielding one substring
   per historical entry, ordered from newest-of-the-priors to oldest (the order in which they
   appear in the nested chain).
4. **Verbatim preservation.** Each split entry's text is preserved character-for-character, except
   for the strict-YAML escaping already required by PC3/Invariant 3 (e.g. escaping an embedded
   literal `"`). No entry's substantive text is truncated, reworded, or reordered relative to its
   neighbors.
5. **Destination: `changelog:` sequence, newest-first.** Each parsed historical entry becomes one
   new `changelog:` sequence list item (`- date: ... / change: "..."` — the same shape PC2/
   BC-5.45.001 PC2 already use for a single displaced entry). The N entries are PREPENDED to the
   existing `changelog:` sequence in newest-first order — the entry nested immediately inside the
   CURRENT entry's `[Prior: ...]` bracket becomes the first (topmost) new `changelog:` item, the
   next-nested entry becomes the second, and so on. Every pre-existing `changelog:` item is left
   byte-for-byte untouched, appearing after all N newly-inserted items. This is the ADR-049 Option
   2 destination for history — full-recovery split produces the exact same canonical
   current-entry-only-plus-`changelog:`-sequence shape as every other write under BC-5.45.001; it
   does not introduce a new history location.
6. **`STORY-INDEX.md` bootstrap case.** If the target file has no `changelog:` field yet (only
   `STORY-INDEX.md`, pre-migration), the tool creates the `changelog:` sequence in the same write,
   seeded with the N split entries in newest-first order (consistent with EC-002's initial-seed
   convention).
7. **Bounded/streaming scan — mandatory for arbitrarily long input.** The marker scan (steps 1 and
   3) and the escape pass (step 4) are each a single linear (`O(n)`) pass over the raw scalar
   bytes, performed via a bounded/streaming scanner (e.g. a byte-cursor forward scan, never a
   repeated substring re-scan or a backtracking regex) so the tool safely processes a chain of
   arbitrary length and arbitrary entry count — including the D-1149 calibration case
   (`STORY-INDEX.md`'s pre-surgery 323,499-char frontmatter scalar; the general class extends up
   to ~350K chars) — without unbounded memory growth or non-linear runtime blowup, satisfying
   Invariant 3. This is precisely the operation Edit/Write-tool-mediated manual editing cannot
   perform safely at this scale, which is why this capability — not just the maintain-only
   shape-confirmation in PC2 — is what makes the tool a full replacement for D-1149's one-time
   human-authorized POL-3 exception.
8. **Idempotent.** Once PC7 has run against a file, the file's `last_amended` is
   current-entry-only with no inline chain remaining (Precondition 2(a) shape) — re-running the
   migration subcommand against it is therefore a PC4 no-op; it does not re-detect a chain (there
   is none left) and does not re-split anything.

### PC8 — crash-recovery idempotency for the archive write

If `rotate_changelog_at` is re-invoked after a crash that succeeded at the archive write but
failed at the source write, the subsequent invocation is self-healing: the archive append is
idempotent — items already present at the archive's tail (matching the current invocation's
`move_items`, detected by a byte-level tail-match: the combined `move_items` string is compared
against the normalized trailing bytes of the existing archive content, stripped of trailing `\n`
on both sides — tail-anchored, never `String::contains`, to prevent false positives from recurrent
content) are not re-appended. Only the source rewrite is reattempted. The archive NEVER
accumulates duplicate items from partial rotation cycles. `RotationReport.mutated` is `true`
when the source was rewritten, even if the archive write was skipped — because the source WAS
mutated (the file state changed). `items_moved` reflects the semantic count (items logically
moved), not whether the archive write was physically performed. This extends Invariant 2's
idempotency guarantee to the partial-failure state where the source file is unchanged (write
failed) but the archive file has already been updated (write succeeded).

## Invariants

1. **Rust `bin/` binary, not a shell script (POLICY 21).** The tool is delivered as a compiled
   Rust binary under `plugins/vsdd-factory/bin/` (or an equivalent Rust workspace crate producing
   such a binary), never as a new `.sh` script, satisfying `no_new_shell_scripts`.

2. **Idempotent on every subcommand.** Both migration and rotation are safe to re-run; neither
   subcommand's second invocation against an unchanged target produces a different result or a
   file mutation (see PC4; the same property extends to rotation — re-running rotation
   immediately after a successful rotation, before the threshold is exceeded again, is a
   verified-clean no-op). It further extends to the full-recovery split (PC7): once a chain has
   been split, re-running migration against the now-slim file is a PC4 no-op — it does not attempt
   to re-split, because there is no longer a chain to find.
   **Re-running rotation immediately after a successful rotation against an unchanged source is a
   verified no-op (PC4 idempotency). Re-running after an archive-write-success +
   source-write-failure crash is also a no-op for the archive write (the idempotent-append tail-
   match dedup detects the already-archived overflow items and skips the archive write) — only the
   source rewrite is reattempted (PC8 crash-recovery clause).**

3. **Safe on arbitrarily long input, including full-recovery split of a chain of any length.** The
   tool processes files up to and including the pre-migration mega-line scale (D-1149's
   323,499-char `STORY-INDEX.md` frontmatter scalar as the calibration ceiling, with the general
   class extending to ~350K chars) without unbounded memory growth or non-linear runtime blowup —
   via a bounded/streaming, single-linear-pass marker scan (PC7 step 7), never a repeated
   substring re-scan or a backtracking-regex implementation. It is the sanctioned mechanism
   precisely because Edit/Write-tool-mediated manual editing cannot safely handle content at this
   scale (per the D-1149 justification for the original one-time POL-3 exception) — and, as of
   this amendment, the tool actively SPLITS such content rather than merely tolerating or refusing
   it (superseding this BC's v1.0 framing, which scoped this invariant to read-only scale
   tolerance for a maintain-only tool).

4. **Every write the tool performs satisfies BC-5.45.001's write-path invariants — and an existing
   chain the tool encounters is always resolved, never left in place.** The tool is itself a
   conforming writer under BC-5.45.001 — its own migration/rotation/split writes never introduce a
   NEW inline `[Prior: ...]` bracket chain, and every value it emits parses under strict YAML
   `safe_load`. Per PC7, an EXISTING inline chain the tool encounters on input is always resolved
   into the current-entry-only-plus-`changelog:` shape in the same run; it is never left in place,
   never re-wrapped, and never deferred to a future ad hoc exception.
