# VP-112: Rotation Archives the changelog: Sequence Without Data Loss or Duplication (Including Crash-Recovery Idempotency at the Archive Boundary)

## Property Statement

1. `rotate_changelog` moves the oldest N items (operator-specified count, or all-but-the-most-recent-K by tool default) into a new or appended `.factory/cycles/<cycle-name>/<file-basename>-changelog-archive.md` file, VERBATIM, and removes exactly those items from the source file's `changelog:` sequence (PC5).
2. A `date:`/`change:` item's text content is never altered by rotation — only its location changes.
3. Invoked against a file below the size threshold, rotation is a no-op (EC-004).
4. Invoked with a `<cycle-name>` that does not yet exist, rotation creates the target directory before writing the archive (EC-005).
5. A rotation immediately re-run after a successful rotation, before the threshold is exceeded again, is a verified-clean no-op (Invariant 2, rotation leg).
6. `Check` mode never writes (rotation leg of Invariant 2's `Check`/`Apply` distinction).
7. **Crash-recovery idempotent archive append — no duplicate items (NEW, cluster-4 hardening Obs B; BC-10.13.001 §PC8, §Invariant 2 crash-recovery extension, §PC5 no-duplicate sentence; BC-1.18.009 §Invariant Inv-6 via the shared `rotate_changelog_at` primitive).** `rotate_changelog_at`'s write sequence is archive-first, source-second (the ordering is load-bearing — source-first would lose data if the archive write then failed). If a crash or a `write_atomic` source-rewrite failure occurs AFTER the archive write succeeded, the source is left unchanged (temp-file-rename failure leaves the original intact — no partial write) and the trigger re-fires on the next invocation. On that retry, `rotate_changelog_at` self-heals: its idempotent-append logic detects that the current invocation's `move_items` are ALREADY present at the archive's tail — via a byte-level tail-match (the combined `move_items` string compared against the normalized trailing bytes of the existing archive content, both sides stripped of trailing `\n`; tail-anchored, NEVER `String::contains`, to avoid false positives from recurrent content) — and SKIPS the archive write, proceeding only with the source rewrite. The archive therefore NEVER accumulates duplicate items across partial rotation cycles: after an archive-write-success + source-write-failure + retry, the overflow items appear in the archive EXACTLY ONCE, not twice.
8. **`RotationReport.mutated` reflects source-file state, not physical archive-write occurrence (Obs B).** On the self-healed retry, `RotationReport.mutated` is `true` because the source WAS rewritten (file state changed), even though the archive write was skipped; `items_moved` reflects the semantic count of items logically moved, not whether the archive write was physically performed. This is the B1 analogue of ADR-051 §Decision 11's mechanism-A `E-SHD-006` self-heal — the same "detection-and-resume, not rollback" recovery philosophy applied to the archive-append-then-source-trim two-write sequence.

### Why unit-test

`rotate_changelog` is a deterministic file-move/rewrite operation exercised end-to-end against
tempfile fixtures; the five fixed fixtures already cover the full happy-path/no-op/idempotency/
check-mode decision table the BC's original `proptest` candidate (set-equality across
rotation-then-reconcatenation) targeted — a property-based sweep over arbitrary item counts/text
remains a valid future hardening step, not a precondition for this VP's initial registration.
